Imbue Studio, Cloudflare OS and Knowledge Medium

Imbue Studio gives each person a small computer with an AI agent living in it, and lets that agent rebuild anything on the machine, including the machine's own interface. This page explains how it works, sets it beside Cloudflare OS and Knowledge Medium, and picks out the ideas Knowledge Medium could use.

The short version

  • All three let people reshape their software by asking an agent. They differ in what gets reshaped: Cloudflare OS reshapes apps, Imbue Studio reshapes the whole computer, and Knowledge Medium reshapes the medium, one graph of blocks.
  • Imbue's strongest idea is its lifecycle: do the task live in chat, then promote what worked into a tested, durable tool, and repair or extend that tool the same way later.
  • Ideas worth taking: turn a successful agent run into an extension, fix a failing extension from its own error, add "change this with an agent" to any block, and make extensions describe themselves to agents.

1What Imbue Studio is Sourced

Imbue announced Studio on 1 October 2026, available by waitlist. Its launch post calls a studio "a computer where you can work together with AI agents and other people." It sets this against AI tools that live in a chat box, and points back to the Xerox PARC idea of personal computing as something creative and shared.

Concretely, a studio is a container that runs on Imbue Cloud or on your own machine, and a cloud studio can be downloaded and run locally. Inside is a persistent Claude agent and a workspace folder that is its home. The base workspace is open source as imbue-ai/default-workspace-template, which describes itself as a template for running a persistent Claude Code instance. You reach a studio from the Studio desktop app, a share link in a browser, or your phone.

The ideas that define it

Creations
Everything you make is a creation: an app (something you open as a tab), a skill (instructions and scripts for a kind of task), a routine (a skill on a schedule), or data. Changes to any of them are customizations, and the README says everything in a studio can be modified, the built-in apps included.
Live first, then made durable
The agent does a new task directly in chat. When the result is worth keeping, crystallize-creation promotes the finished work into a reusable, tested skill or app. A background worker builds it on a branch, and it merges only when you approve. heal-creation fixes a creation that errored or gave wrong results, and update-creation extends or refactors one.
Change anything by asking
You right-click anything, describe the change, and watch it happen. The agent can change Studio's own look (colours, fonts, window shapes), its skills, and its own standing instructions. Critical apps such as the shell and chat get a more careful edit flow.
Templates with lineage
A studio can publish its creations as a template that another studio adopts. Adopting merges the template into a scratch copy, checks that it boots, and only then updates the live workspace. Conflicts are handed to you instead of being resolved automatically. Every studio records its origin and lineage in an append-only history, pulls updates from its parent template, and is expected to send fixes to built-in code back upstream.
Apps describe themselves
Each app's manifest carries a description and an OpenAPI document generated from its route docstrings. An app's tests fail if a route has no summary. An agent arriving over a share link reads a primer that lists the apps and links each one's API, so it can use an app without reading its code.
Agents start with no access
Agents run in a container that holds none of your account credentials. Calls to your accounts go through a gateway outside it, which adds the credential and checks each request against the permissions you've approved. Approvals cover the whole workspace, not one agent. The launch post's example is an agent that can label your email but can't send or delete it.

Data stays out of git in data/ with continuous encrypted backup, and the launch post says traffic and storage are end-to-end encrypted so Imbue can't read them. That is the company's claim; the post gives no independent verification. The agent is also told that derived views must keep the raw source records they were built from, and that progress updates to you shouldn't mention internal machinery such as git or tickets.

2How a tool comes to exist Sourced

The launch post's own example is a live todo list built from your calendar, email and Slack. Here it is traced through the lifecycle from the template's skills. Figure 2 shows the stages.

Two details stand out. First, durability is a separate, deliberate step: the quick version and the maintained version are built differently, and the agent asks before investing in the second. Second, every change after the first goes through the same loop. A broken tool isn't a dead end. It goes back to stage 3 with the error attached.

3Three places to put malleability Our read

All three projects share the goal of people changing their own software with an agent's help, which is the Ink & Switch sense of malleable software. They disagree about which layer should be soft.

Cloudflare OS

Malleable apps

The unit is a gadget: code plus its own database. Apps are walled off from each other and from company systems, and the platform decides what crosses each wall. It's built for an organization, so governance comes first.

Imbue Studio

A malleable computer

The unit is a file in the workspace, and the agent may edit any of them, including the shell and its own instructions. Tools are processes that talk over HTTP. It's built for one person and the people they invite, so the agent comes first.

Knowledge Medium

A malleable medium

The unit is a block. Notes, types, settings and extension source share one graph, and tools are views and behaviours over it. It's built for a person's long-lived knowledge, so the data comes first.

One way to see the difference is how deep a change can reach while you're using the system, without forking and redeploying it. Figure 3 is our reading of each.

Imbue reaches furthest, and it pays for that reach with the substrate it chose: files and processes. Two tools in a studio share data the way two web services do, through an API. In Knowledge Medium two tools share data because it's the same blocks. A workout logged in a daily note shows up in the strength tracker, a query and the backlinks at once, with nothing to integrate. Neither choice is wrong. They're optimising for different things: Imbue for the range of what can be built, Knowledge Medium for how well what's built fits together.

5Ideas to incorporate Our read

Imbue's best ideas are about the process of changing software, which carries over to blocks without adopting its substrate. Most of these reuse pieces Knowledge Medium already has: agent-dispatch runs, extension approval, extension error boundaries and the action registry. Figure 4 shows how the first two would fit together.

1 · Crystallize a run into an extension cost: medium · fit: high

When a [[claude]] run does something you'll want again, an action on its reply turns the run into a durable tool. That might be an extension, a saved query, or an agent-dispatch watcher. A background run writes it as a disabled draft extension block, checks it with --verify and audit-extension, and leaves it for your approval. Knowledge Medium already has the run, the checks and the approval. What's new is the action and the brief it hands the run.

Example. You ask [[claude]] to pull this week's sleep numbers into a table. It works, so you crystallize it. Next week the table is an extension that renders on its own.

2 · Fix a failing extension from its error cost: low to medium · fit: high

Extension failures already surface through the render error boundary and the load-error toast. Add a "Fix with agent" button there that starts a heal run with the error, the extension's source and a sample of the blocks it was rendering. The patch comes back as a merge proposal. This shares the review flow with upstream updates (#1427), so it's worth designing the two together.

3 · "Change this with an agent" on any block cost: low · fit: high

Imbue's right-click-to-change, applied to blocks. The block's context menu gets an action that starts a run with the block's id, its types, the renderer drawing it, and the extension that renderer came from. Today you'd write a [[claude]] mention and explain all that context by hand.

Example. On a todo block: "show the due date in red when it's overdue". The run knows which renderer to change and where its source block is.

4 · Extensions describe themselves to agents cost: low · fit: high

Imbue makes each app publish what it does, and fails the app's tests when a route has no summary. Knowledge Medium already requires a description on every action. The same rule could cover each installed extension and everything it contributes (types, queries, mutators), with --verify flagging what's missing. describe-runtime could then list "what this workspace can do" per extension, which is what an agent needs before it changes anything.

5 · Kits: publish a whole setup cost: medium to high · fit: medium

An Imbue template carries several creations at once. The block version is a kit: a page subtree holding extension blocks, type definitions, views and example pages, shared as one unit and adopted with lineage. This builds on upstream tracking (#1427), and once kits pass between people it needs capability scoping (#1425). It should come after both.

Already aligned

  • Keep raw records under derived views. Imbue tells its agent this. Knowledge Medium's import rule already keeps the source property when it adds a typed one.
  • Zero access by default for agents. Imbue's "label email but can't send it" is the same idea as staged outward actions (#1426) and capability-scoped extensions (#1425).
  • Lineage and upstream fixes. Imbue and Cloudflare OS both record where a tool came from and route updates through review. That's #1427.

What not to take

  • A resident agent that owns a Linux container. It needs a server, gives up offline use, and can't read an end-to-end encrypted graph without a client. Running agents outside the app through the bridge and agent-dispatch is the right shape for a browser-first, local-first medium.
  • Files and processes as the substrate. They let you build anything, but tools then integrate through APIs and lose the shared block grain.
  • Git as the history of user data. Block history and undo already cover it, at the right granularity.

6Recommendation Our read

Cloudflare OS contributes a safety model, and Imbue Studio contributes a process for how a tool is born and kept alive. Knowledge Medium keeps its data model and takes both.

Suggested order, merged with the Cloudflare OS list

  1. "Change this with an agent" and self-describing extensions. Cheap, and both make every later agent run better informed.
  2. Upstream tracking (#1427) together with Fix with agent, since both end in the same merge proposal.
  3. Crystallize a run into an extension. Once the proposal flow exists, a crystallized draft is one more kind of proposal.
  4. Staged outward actions (#1426), as soon as runs post or send anything.
  5. Capability-scoped extensions (#1425), then kits, when extensions start moving between people.
