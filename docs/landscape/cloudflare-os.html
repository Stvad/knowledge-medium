Cloudflare OS and Knowledge Medium

Cloudflare OS is an open-source workspace where an agent builds small apps for you, and a security layer decides what those apps may touch. Knowledge Medium wants the same thing for personal knowledge work, starting from the other end: one local-first graph that you and your agents reshape. This page explains what Cloudflare OS is, where the two designs agree and disagree, and which of its ideas are worth taking.

The short version

  • Cloudflare OS makes apps malleable. Knowledge Medium makes the medium malleable: data, views and code all live in one graph of blocks.
  • The part of Cloudflare OS that transfers best is its safety model. Apps start with no access, every grant is a narrow capability, and actions that leave the system wait for a person's approval.
  • Recommendation: borrow upstream tracking for extensions now, staged approval for agents' outward actions next, and capability-scoped extensions once people share extensions with each other. Don't adopt Cloudflare OS as Knowledge Medium's backend.

1What Cloudflare OS is Sourced

Cloudflare open-sourced Cloudflare OS on 5 August 2026 and describes it as an "open platform for agents, apps, and work". The name is an analogy. It's a browser workspace that runs on Cloudflare's developer platform. Cloudflare staff have used it since May 2026, and thousands of them, many outside engineering, use it to write documents and slides, automate routine tasks and build small data apps.

It has three parts:

  • An agent workspace. You chat with an agent that does its work by writing and running code. It draws on a shared library of company context and skills that anyone can improve.
  • A security and governance layer. Nothing can reach anything until a person grants it, and every grant is narrow.
  • A platform for personal apps. You ask for a tool, the agent writes it, and you and your team keep changing it.

The repository names its parts after operating-system concepts, and the analogy is a good map of the system.

It's licensed Apache-2.0 and is in early access: version 2 is a rewrite, and the README calls the release capable but rough. You can deploy it into your own Cloudflare account today. Running it on your own servers with workerd is listed as coming soon. The project accepts only small fixes for now.

Six ideas that matter here

Apps written by an agent
A gadget has a client UI in a sandboxed iframe and a server in a Dynamic Worker, a V8 isolate started on demand, with its own SQLite database. The two halves talk over Cap'n Web, Cloudflare's open-source capability-based RPC. Gadget code is versioned with git.
No ambient authority
Agents and gadgets start with access to nothing. You introduce them to a resource, for example by pasting a repository link, and the code receives a typed binding such as env.REPO. A binding means one resource under one policy. An agent can ask for an introduction, and you approve or refuse it.
Gatekeepers
Each external service sits behind its own Worker. It holds the credentials, narrows access (one repository, issues but not code), logs every read, and simulates side effects so the agent can keep working while the real actions wait in a queue for your approval.
Observation tracking
The platform records what each gadget has read. When someone else opens it, they must pass access checks for everything it read, so sharing a dashboard can't leak the table behind it. Reading restricted data can put a workspace into a mode where web fetches stop and every action needs approval.
Blueprints with lineage
Publishing a gadget as a blueprint shares its code, the shape of its bindings and a description. It shares no data, chat history or credentials. A gadget made from a blueprint remembers its upstream, and updating produces a proposal you review: follow, fast-forward, or a three-way merge that the agent checks.
One method surface for people and agents
The UI and the agent call the same server methods. A tool built for a person works for an agent too, with no separate MCP server.

It also has workflows (mostly deterministic code that calls a model only where judgement helps), documents that stay connected to live data, portals to existing MCP servers, and AI Gateway for choosing models and tracking spend.

2A worked example: a team triage board Sourced

The scenario is ours, assembled from the mechanisms in Cloudflare's docs. The code is illustrative; the real API differs in detail.

You ask the workspace for a board of open priority-one bugs in your team's repository, grouped by owner. Figure 2 shows what gets built, and Figure 3 shows the conversation that builds it.

Illustrative gadget server
// Runs in a Dynamic Worker with outbound internet off.
export class TriageBoard {
  constructor(private env: {REPO: IssueTracker; db: SqlStorage}) {}

  async openP1s() {
    return this.env.REPO.issues({label: 'p1', state: 'open'})
  }

  async assign(issue: number, owner: string) {
    // The gatekeeper queues this write until you approve it.
    return this.env.REPO.assign(issue, owner)
  }
}

Two things happen later:

  • Sharing. A teammate opens the board. The gadget has read issues from your repository, so the gatekeeper first checks the teammate's own GitHub access. Without it, they can't open the board.
  • Reuse. You publish the board as a blueprint. Another team creates their own gadget from it, points env.REPO at their repository, and starts with empty storage. When you fix a bug and publish a new release, they get a merge proposal, not a silent update.

3Two kinds of malleability Our read

Knowledge Medium's README describes an outliner where everything is a block and everything is an extension. Pages, todos, settings and the source code of extensions are all rows in one blocks table. The app assembles itself from extensions you can edit live in the browser. Data lives in local SQLite on each device and syncs through PowerSync. Agents work on the live client through the agent bridge, the km MCP tools, and [[claude]] mentions that agent-dispatch turns into runs.

Both projects want people to reshape their tools with an agent's help. They put the malleable thing in different places.

In Cloudflare OS the unit of change is the app. In Knowledge Medium it's the block. A workout logged in a daily note shows up in the strength tracker, a query table and the backlinks panel at once, and deleting a tool leaves the data where it was. The repo's record-grain rule says this directly: anything you'd want to see, link, undo or edit on its own is its own block.

That difference explains most of what follows. Cloudflare OS can give each app a private database because apps rarely need each other's rows. Knowledge Medium can't wall extensions off the same way without losing the cross-linking that makes it useful. So any sandbox it adopts has to be described in terms of blocks and types, not databases.

5Where they disagree, on purpose Our read

These differences follow from who each system is for. Neither side is a mistake to fix.

Where code runs

CFGadget servers run on Cloudflare and work on plaintext.
KMCode runs in your browser. In an end-to-end encrypted workspace the server only holds ciphertext for block content.
Cloudflare-hosted compute over KM data works only for unencrypted workspaces, or with a client present to decrypt.

Online or offline

CFA web workspace. With no network, there's no gadget.
KMLocal-first. The tool and the data are on the device, and sync catches up later.
Anything KM borrows has to work with the network gone.

Who the threat is

CFAn organization: many people, regulated data, agent-written code nobody reviewed. Default-deny is right there.
KMA few users who write or approve their own extensions, so approve-and-trust has been enough.
That changes once extensions pass between people, or an agent installs code while you're away.

Where context lives

CFA curated library of company context and skills that agents read.
KMThe graph is the context: your notes, types and past decisions.
Stronger for personal work, weaker for a company that wants one curated source.

6How it could fit Our read

Cloudflare OS could fit in three ways, in order of how much of it you take: borrow its ideas, connect to it at one edge, or adopt it as infrastructure. Figure 5 places each option by rough cost and by how well it fits Knowledge Medium's design.

Borrow the ideas

Recommended

1 · Upstream tracking for extensions cost: low · #1427

An installed extension keeps a reference to the block or URL it came from. Updating from upstream fast-forwards when you haven't edited it, and opens an agent-assisted three-way merge when you have. The merged source is what you approve, so it slots into the existing per-device approval that pins a hash of the source.

Example. You changed how the Readwise extension surfaces highlights. Upstream then fixes a bug in its sync loop. Today you choose between overwriting your change and keeping a stale copy. With lineage you review one merge.

2 · Staged outward actions cost: low to medium · #1426

Writes inside the graph can already be undone. Actions that leave it can't: posting through the social-media publisher, sending mail, calling a paid API. Agent runs and extensions could stage those as proposal blocks that you approve one at a time or in bulk, the way gatekeepers queue simulated writes. Because the proposal is a block, it syncs, shows up in queries, and can be approved from your phone.

Example. You write [[claude]] post the weekly summary. The reply arrives as a child block with the draft and a pending post that waits for your tap.

3 · Capability-scoped extensions cost: high · #1425

Let an extension declare what it needs in terms Knowledge Medium already has: the block types it reads, where it may write, and the hosts it may fetch. Extensions you didn't write would run in a sandboxed iframe or worker that receives handles over RPC instead of the whole repo. Cap'n Web is open source and could carry it. Your own extensions keep running in the page as they do now.

Sketch, not a current API
export const needs = {
  read:  {types: ['habits:habit', 'habits:check-in']},
  write: {under: 'own-page'},
  fetch: [],           // no network at all
}

Example. A friend shares a habit tracker. It can read habit blocks and write under its own page. It can't see your journal, and it can't send anything anywhere.

The cost is real. The data layer and the renderer seams need an RPC surface, and every facet an untrusted extension contributes to needs a rule. Build it when sharing extensions between people is actually happening, not before.

Connect at one edge

Only with a concrete need

A Knowledge Medium gatekeeper for Cloudflare OS cost: medium

Cloudflare already ships gatekeepers for Notion, Confluence and Supabase. One for Knowledge Medium would expose a scoped slice of a workspace (a page's subtree, or blocks of one type) to gadgets and agents, with reads logged and writes queued. It would work for unencrypted workspaces only, since a gatekeeper runs on the server. It's worth building if a team keeps its notes in Knowledge Medium, or if you use Cloudflare OS at work and want your notes there. The project is in early access and its interfaces will move, so wait for them to settle.

Embed a gadget in a block cost: low

An iframe renderer for a gadget URL is easy to build and adds little. The gadget's data stays in its own database, outside the graph, so none of the linking, querying or undo applies to it.

Adopt it as infrastructure

Not recommended

Moving sync onto Durable Objects, or running extensions server-side in Dynamic Workers, would give up offline use and end-to-end encryption and redo work PowerSync already does. The one real attraction is automation that runs when no app tab is open, since agent-dispatch needs a live tab today. If that need becomes concrete, a small runner for unencrypted workspaces is a much narrower answer than moving the backend.

7Recommendation Our read

Cloudflare OS confirms the direction Knowledge Medium is already taking: people ask an agent for the tool they need, then keep changing it. What it adds is a safety model that makes those tools safe to share inside an organization. What Knowledge Medium adds is the data model, where tools are views over one graph you own, offline and encrypted.

Suggested order

  1. Upstream tracking for extensions. Cheap, useful now, and it fits the existing approval flow.
  2. Staged outward actions. Matters as soon as agent-dispatch runs post or send anything.
  3. Capability-scoped extensions. When extensions start moving between people.
  4. Skip adopting Cloudflare OS as infrastructure. Revisit a gatekeeper only for a team use case.

Open questions

  • How soon will extensions travel between people? That decides when the sandbox is worth what it costs.
  • Should agent runs ever act while no app tab is open? That is the only case that pulls toward server-side compute.
