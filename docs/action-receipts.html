Action Receipts

A small core plugin that hands the user a receipt after actions whose effect they cannot see: what just happened, to which block, where it lives, and how to take it back. Undo is the first customer.

1 Why 2 What gets a receipt 3 Plugin shape 4 Four visual options 5 Decisions 6 As built

1. Why: undo is currently silent

Cmd-Z runs repo.undo(), which pops the top entry of the active workspace's BlockDefault stack and replays its before snapshots. The only feedback is whatever happens to be on screen. Three shapes of that go wrong in daily use:

The revert lands off-screen.

You edited a task on the agenda, opened a note, pressed cmd-Z out of habit. The task reverted three panes away. Nothing on this page moved, so it reads as "undo is broken".

The stack is empty, or belongs to another workspace.

Undo is per workspace and starts fresh each session. Cmd-Z after a reload or a workspace switch does nothing at all, and nothing says so.

One press, unknown blast radius.

A grouped entry (a reschedule, a paste of fourteen blocks, a delete with a subtree) reverts as one step. The user sees one thing move and does not know eleven others did too.

The same silence after the action itself.

Refile a block to another page, delete a parent with children folded, move a block out of the visible window. The effect is real and invisible, and the undo affordance is nowhere.

2. What gets a receipt

Rule: an action earns a receipt when its effect is not fully visible where the user is looking. Off-screen, aggregate (a count the viewport hides), or no visible effect at all. Actions whose result is on screen get nothing. Receipts are for closing a perception gap, not for narrating the app.

Deliberately no receipt: indent/outdent, move up/down, paste, type changes, fold cycling, mode toggles. All visible. Sync-applied remote changes are not actions and are a different design.

3. Plugin shape

src/plugins/action-receipts/, a systemToggle like recents. It owns the surface (rendering, coalescing, the live Undo/Redo button, Go to) and nothing about any particular action. Two seams feed it.

Seam A: a history-replay event on the repo (small core change)

repo.undo() returns a boolean and nothing observes the entry it replayed. UndoManager.subscribe reports stack shape only. So the repo emits one event at the end of undo() / redo(), in both the replayed and the empty case, carrying the entry itself:

// src/data/repo.ts
export interface HistoryReplayEvent {
  kind: 'undo' | 'redo'
  scope: ChangeScope
  workspaceId: string
  entry: UndoEntry | null      // null: the stack was empty
}
onHistoryReplay(listener: (e: HistoryReplayEvent) => void): () => void

Emitted after the replay commits, before the redo push returns, so a listener that peeks the redo stack sees the entry on top. A failed replay rethrows as today and emits nothing; the error keeps its existing route. This catches every path (keyboard, palette, Edit menu, the reschedule toast's own Undo button, programmatic calls), which is why it beats the alternative below.

Fallback with zero core change: a before observer on actionDispatchVerb for the undo action stashes peekUndo(), and the after observer compares it to peekRedo(). It works for cmd-Z and the palette only. Anything that calls repo.undo() directly is invisible to it, and the reschedule toast already does. Not recommended, but it is how a prototype can be tried in a dynamic extension before the core PR.

Seam B: describers, keyed by action id

Mirrors rejectionToastFacet: a keyed-map facet where the plugin that owns an action says what its receipt reads. The receipts plugin registers a single actionDispatchVerb.after observer that looks the action up and renders the result. Ownership stays with the action's plugin; core never learns about receipts.

// src/plugins/action-receipts/facet.ts
export interface Receipt {
  key: string                      // same key within coalesceMs updates the toast in place
  verb: string                     // 'Undid edit' · 'Restored' · 'Moved' · 'Deleted'
  subject?: {blockId: string; workspaceId: string; label: string}
  count?: number                   // blocks touched beyond the subject ("and 7 children")
  peek?: {before: string; after: string}   // one-line content delta, truncated
  tone?: 'neutral' | 'empty'
  hint?: string                    // 'Undo history is per workspace'
  revert?: {kind: 'undo' | 'redo'; workspaceId: string; groupId?: string; txId: string}
}

export interface ReceiptDescriber {
  actionId: string
  context?: ActionContextType
  describe(
    invocation: ActionInvocation,
    outcome: VerbOutcome<ActionHandlerResult>,
    repo: Repo,
  ): Receipt | null | Promise<Receipt | null>
}
export const actionReceiptsFacet = keyedMapFacet<ReceiptDescriber>('action-receipts', d => d.actionId)

Turning an undo entry into words

entry.description is free-form and often missing ('paste multiline text', 'addType todo', or nothing). The uniform source is the snapshot map: per block, before and after. A pure summarizeEntry(entry, ctx) classifies each delta and picks a subject. It is plain vitest, the same way bucketing.ts is for the agenda.

Snapshot deltaUndo receiptRedo receipt
content differsUndid edit · label + peekRedid edit
before present, after nullRestored label and N childrenDeleted label again
before null, after presentRemoved label (undid create / paste)Re-created label
parent or order differsMoved label back to A ▸ BMoved label to C ▸ D
only properties differUndid status change on labelRedid …
mixed, many blocksUndid N-block change · dominant kind namedRedid …

Subject = the topmost touched block (its parent is not in the map), labeled with labelForBlockData; crumbs from repo.query.ancestors, the same helper Quick Find uses. A recognized description can override the verb ("Undid reschedule"), unknown ones are ignored rather than shown raw.

Lifecycle rules

  • Where. After the replay, the plugin checks whether the subject has a rendered instance in the active panel. Visible: the block flashes and the receipt stays short. Not visible: the receipt carries crumbs and a Go to button (navigateFromGlobalCommand). Undo never moves focus by itself.
  • Live revert button. Enabled while the entry is top of the opposite stack of its workspace, re-checked at click time. This is the reschedule toast's groupId check, lifted into the plugin so every receipt gets it and that toast loses its copy.
  • Coalescing. Same key within 1.5 s updates the same toast id: the count climbs, the subject shows the latest step. Sonner's id reuse does the update; no stacking.
  • Duration. 5 s, paused on hover. "Nothing to undo" 2.5 s. One receipt at a time per key; a new key replaces, it does not stack.
  • Scope. BlockDefault and References only, the undoable scopes. Automation and UI-state writes never produce receipts.
  • Off switch. The systemToggle, plus a per-key mute in the toggle's settings if a receipt turns out noisy.

4. Four visual options

Each artboard is the same page in the app's own sunset-warm palette, light and dark side by side, system font stack as in the app. Switch the scenario with the tabs: the state the mockups share is the one that matters most, an undo of an edit that is on screen, an undo of a delete that is not, an empty stack, and a burst of three presses.

5. Decisions (2026-09-21)

  • Core hook, not the dispatch-observer prototype. repo.onHistoryReplay fires for every path into undo and redo, with the entry, or null for an empty stack.
  • Option A, the Strip, is the surface. Every receipt carries a history button that opens the Ledger (Option D) as a session tray; the tray is also reachable from the palette as "Recent actions".
  • Go to is explicit. A receipt never moves focus by itself. When the subject is on screen the row flashes instead and the button is not offered.
  • Second wave in the same PR: delete with children, and move / refile. No receipt for a workspace switch.
  • The SRS reschedule toast folds in and its bespoke live-button lifecycle is deleted.

6. As built

The plugin lives in src/plugins/action-receipts/; the design maps onto files one to one.

FileOwns
src/data/repo.tsHistoryReplayEvent + onHistoryReplay, emitted at the end of replayGesture after the entry moved to the opposite stack; inverseOffered says whether that push landed (a history drop mid-replay refuses it). A replay that threw emits nothing; a drop-in-progress refusal emits nothing either, since the pass owning the drop has its own surface.
facet.tsReceipt, ReceiptDescriber, actionReceiptsFacet (keyed by action id), and the builders: recordedReceipt for an entry an action just recorded, historyReceipt for an undo / redo event, subjectOf / locationOf for the state a gesture leaves behind. A subject the gesture left deleted is navigable: false: no Go to, no flash.
summarize.tsUndo entry → words. Rows are classified (create / delete / move / content / properties), field rows are excluded, the subject is the topmost row of the highest-priority kind (content, move, delete, properties, create: the row the user acted on beats the rows a helper touched, so a move into a collapsed destination names the moved row, not the destination whose collapse flag flipped), riders are the rows under the subject, and a content change gets a prefix / suffix / two-middles peek. phrase() renders a direction: undo, redo, or forward.
receipts.tsThe toast slot (one receipt on screen; presses inside 1.5 s fold into one toast that shows the latest press in full with a +N chip for the earlier ones; each non-folded receipt gets a fresh sonner id because a dismissed id stays deleted; the empty "Nothing to undo" never touches the slot), the session ledger (50 entries; the toast holds only a ledger id, since sonner retains every toast's closure for the session), the on-screen check (data-block-shell row in the active panel, inside every scrollport, waited for up to 300 ms because a structural change reaches the DOM a query round-trip and a lazy mount after the commit) and the row flash. With the plugin off, showReceipt degrades to a plain toast so the flows that call it directly still confirm.
dispatch.tsBefore / after observers on actionDispatchVerb: sample the undo stack before, await the handler, ask the action's describer with the entry it recorded. Attribution is "the top changed while the handler ran", so a flow that can call showReceipt itself should.
describers.tsReceipts for core actions: delete_block and multi_select.delete_block when the deleted subtree took children along. A multi-select delete records one entry per block; the receipt names the last, which is what its Undo reverts.
src/plugins/move-blocks/receipts.tsThe move receipt, built by the move flow from its own result (the moved ids and the picked destination) so a dialog-backed flow cannot be misattributed; destination read live ("→ References"). Replaces the "Moved N blocks" success toast.
src/plugins/srs-rescheduling/index.tsCalls showReceipt with the reschedule message and the group entry; RescheduleToast.tsx and its test are gone, the liveness semantics moved to ReceiptToast.test.tsx.
ReceiptToast.tsx / LedgerTray.tsxThe two surfaces. The inverse button is enabled while the entry is the top of the matching stack of its workspace (entry identity, not group id) and re-checks at click time; its chord comes from the live binding. Go to is offered only in the active workspace and checks the block still exists. The buttons wrap under the sentence inside sonner's 356 px. The tray never takes focus (that would end edit mode), subscribes to nothing while closed, and follows the active workspace.

Verified live on a local-only dev build, driven through the agent bridge: undo of an on-screen edit (peek, flash, live Redo), redo, a foreign write disabling the button in place, a programmatic repo.undo() with no dispatch, three presses folding into "Undid 3 steps", cmd-Z on an empty stack, undo of a create (no Go to), a real cmd-Z keydown, delete with three children and its Undo, a leaf delete producing nothing, an off-screen undo with Go to landing on the block, the same receipt key arriving while an earlier toast is still up, move through the picker and its "Moved back", the SRS reschedule receipt and its Undo, and the ledger's counts, rows, Redo, focus and Escape.
