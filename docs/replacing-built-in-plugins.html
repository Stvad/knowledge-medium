Replacing a built-in plugin with your own copy

How someone, or an agent working for them, turns a file of a built-in plugin into one they own and edit. The app then loads their copy wherever it used to load the original, on every device that trusts it, and they find out when the original changes upstream. Built against current master, with ideas from Imbue Studio, Cloudflare OS and the malleable-systems catalog in #365.

The short version

  • A fork is an edited copy of one plugin file, stored in a block. On a device that has approved it, the page's import map points the file's module path (@/plugins/todo/index.js) at the fork. Everything that imported the original now imports the fork: the plugin list, other plugins, extensions. The original file is never loaded.
  • That needs one build change. Today every built-in is linked inside one bundled chunk, so imports between them never go through a URL (§2). Plugin files have to become modules the browser loads by path. That costs boot time for every user, so the first build PR measures it.
  • Because the fork is the module, it keeps its place in every list, its imports and the original's declarations.
  • A device that hasn't approved a fork maps nothing and loads the original, so no device runs neither. A fork that breaks boot is skipped on the next load.
  • A fork can't change how stored data is keyed or encoded. Files that define codecs or derived ids aren't forkable in v1, because devices still on the original would read or mint data differently.
  • Every later change goes through one loop: the source changes, each device keeps its approved version until someone approves the new one there, then a reload serves it.
  • Seven PR-sized pieces. The source provider (#1435) and the build change can start in parallel.

1The problem Observed

Say you want finished todos dimmed instead of struck through. That styling is one class string in TodoContentDecorator, inside src/plugins/todo/index.tsx, which ships in the app bundle. You can't edit it from the app.

What works today: copy the plugin into an extension block, change the line, and turn the built-in Todo off. The copy has to leave out todoDataExtension, because the extension loader rejects its system:todo/… seed keys (src/extensions/dynamicExtensionSeeds.ts:83-87). A copy that keeps it loads as an empty error shell. The copy imports the original's other modules through the page import map. Other plugins import only todo's action ids (srs-rescheduling) and schema constants (roam-import, onboarding), so for Todo nothing is left calling the original. For daily-notes that isn't true: five plugins import getOrCreateDailyNote itself. The workaround has five costs:

3Ideas borrowed Our read

The two landscape pages (docs/landscape/imbue-studio.html, docs/landscape/cloudflare-os.html) and the malleable-systems catalog in #365 each have something to say about owning a copy of software you didn't write. This design takes these ideas.

Imbue · templates

Check that it boots before it goes live

Adopting a template merges it into a scratch copy, checks that it boots, and only then updates the live workspace.

After approval, the fork check loads the fork once on its own and compares it with the original before it is ever mapped. If a mapped fork still breaks boot, the next load skips it (§7, §8).

Imbue · creations

One loop for every change

Crystallize, heal and update all build on a branch and merge on approval.

The same shape, without git (§8).

Imbue · critical apps

More care for the parts everything stands on

The shell and chat get a more careful edit flow.

Core and essential plugins aren't forkable in v1.

Cloudflare · blueprints

Remember the upstream; update by proposal

A gadget remembers its blueprint. An update is a proposal: follow, fast-forward, or a three-way merge the agent checks.

A base record on each forked file, shared with upstream tracking for shared extensions (#1427), so there is one owner for both (§9).

Cloudflare · one surface

The same methods for people and agents

The UI and the agent call the same server methods.

Eject is one action, reachable from the menu, the palette, the CLI and an MCP tool. The source tool is generated from the same table as the other graph read tools (§5).

Cloudflare #365 · §5

Say what code may do; diff it on update

Capabilities are granted narrowly. In #365, a manifest is shown at enable time and diffed when an update arrives.

Not enforced yet (that's #1425). Before approval, the review lists imports the original didn't have. After approval, the fork check compares exports and declarations with the original's (§8).

#365 · §1

Reveal codes

A block inspector that answers "which extension did this?" and links each answer to its source.

Every contribution gets an owning plugin and file. That's where "change this" and "make my own copy" start (§10).

#365 · validates

Compose before you fork

Model 2 (an additive override layer, like CSS) beats Model 1 (fork and modify).

Fork the smallest file that holds the change. The rest of the plugin stays upstream's and keeps receiving fixes with no merge (§4).

#365 · lithification

Fixes don't reach forks on their own

Once you own a copy, propagating upstream fixes to it is the unsolved cost.

An upstream check after each app update, with fast-forward when you haven't edited the copy (§9).

#365 · Hinsen

Keep the dependency graph a tree

Bound the blast radius by not letting extensions reach across.

Plugins that bundle another plugin's parts import them by path, so they get the fork too. Nothing reaches around it.

Not taken

  • Git branches for changes. Block history, undo and the approval already give the branch-and-merge shape.
  • A resident agent or server-side apps. These give up offline use and end-to-end encryption, as both landscape pages argue.
  • Enforced capabilities now (§11). Automatic upstream merges (§9).

4The model

Built-in
A plugin in the app bundle (src/plugins/<name>/), wrapped in a systemToggle({id: 'system:<name>'}) boundary (src/facets/togglable.ts:111-122).
Fork
A block holding an edited copy of one built-in file, plus extension:serves, the module path it answers (@/plugins/todo/index.js). It's approved and toggled like an extension, but the extension loader skips it: it isn't a contribution list, it's a module. A workspace has at most one fork per path.
Eject
Making a fork from a built-in file: copy it, swap its import specifiers for the ones the build resolved, record its base. (The word comes from build tools that hand you their hidden config.)
Base
The text of the file a fork was made from, in ejected form, the hash of the authored file, and the app version. It's what upstream changes are compared with and what a merge starts from. The same record serves #1427, where the upstream is a shared extension block instead of the bundle.
Fork check
The step after approval that loads the fork once on its own and compares it with the original file (§8). Only a fork that passes is mapped. The other check in this doc is the upstream check (§9).
Frozen identity
What stored data is keyed by: a property's name and encoding (presetId, codec.type), and a type's id (src/data/seedIdentityLedger.ts, header). A release can't change these, and neither can a fork.

Four rules

  1. A fork is the module. It's served at the original file's path, so every importer gets it: the plugin list, other plugins, extensions. The original file is never loaded.
  2. A fork is served only where it may run. That means approved on this device, passed its fork check, and enabled by intent, in the workspace the page opened. Anywhere else the original loads, and settings shows the usual "Enable here".
  3. A fork keeps the original's contract and identity. It exports at least what the original exported. It still declares every seed the original declared, under the same key and frozen identity. Seeds it adds are in a namespace it owns. Files that define a codec or a derived id can't be forked in v1.
  4. Changing what's served takes a reload. The import map is fixed when the page loads.

The fork and its base are blocks, following the record-grain rule: you'd want to see, link and edit each of them on its own. Here is the fork eject would create for Todo's entry file:

The eject rewrite

A fork runs from a blob URL. It has no usable base, and nothing resolves its imports the way the build did. Observed Plugin files import in every form the build accepts:

  • relative paths, spelled several ways (./actions.ts, ./config);
  • 583 @/ imports without an extension, some of them directories (@/data/api is src/data/api/index.ts);
  • npm packages, in about 99 files: lucide-react, zod, uuid, @codemirror/*, unified and the remark and mdast helpers, lodash-es and others, plus the aliased @knowledge-medium/agent-cli/protocol;
  • re-exports (export {…} from './actions.ts'), which are imports too.

So the rewrite doesn't reimplement resolution. When the build emits a plugin's source file, it records the runtime specifier it resolved each import and re-export to. A relative import becomes its @/plugins/…js path, an extensionless or directory @/ import becomes the emitted file (@/data/api/index.js), and a package keeps its name, which the import map resolves (§6). Eject swaps each authored specifier for the recorded one. Everything else in the file stays as it was: its exports, its systemToggle, its seeds. Babel is loaded lazily to compile extensions anyway, so this is an AST pass, not text surgery.

Vite-only syntax. Observed A blob module gets no Vite processing, and four plugin files rely on it:

  • import.meta.env, read by geo/googlePlacesClient.ts, agent-runtime/bridge.ts and db-mirror/store.ts. The fork compiler rewrites it to a small core module, @/appEnv.js, that exports the variables plugin files read, with the values the running build already has. Nothing is copied into the fork's block.
  • import.meta.glob and ?raw imports, in agent-runtime/authoringCatalog.ts. These need the build's file list, so files that use them aren't forkable in v1.

The source provider marks every file eject refuses, with the reason: Vite-only syntax, an essential plugin, or identity code (§8). P1's test runs the rewrite over every plugin file, so a new import form or Vite feature fails the test instead of a fork.

6Serving a fork at the original's path

The import map can already point any specifier at any URL. What stops it from replacing a built-in file today is that built-ins never import each other through a specifier: the build links them inside one chunk (§2). So the one build change is this: imports of plugin files stay real imports, written as @/plugins/… specifiers that the import map resolves when the page loads. Core stays bundled.

The build change (P2)

  • Plugin imports stay imports, in one spelling. Every import that resolves into src/plugins/, static or dynamic, is emitted as @/plugins/<name>/<file>.js. Today they're written three ways (with .js, without an extension, with .ts), some name a directory, and the two lazy ones in §2 use relative URLs. Import-map keys match by exact string, so one spelling is what lets a single map entry catch every importer. A build check fails on any other form.
  • Packages get a URL. A stable re-export file for each package and subpath that plugin files import (vendor/zod.js), with an import-map entry for each, so a fork gets the instance the app uses. Extension blocks, which today can import only react, get them too.
  • No cycle between core and plugins. Plugin files call core at top level (defineFacet results' .of(…) in nearly every plugin). So the chunk they import core from must finish evaluating before they run, and it must not import them back. Observed Lint forbids core from importing plugins except in the two composition-root files, staticAppExtensions.ts and staticDataExtensions.ts (eslint.config.js:347-355). Five modules import those two today: context/repo.tsx, data/repoProvider.ts, bootstrap/workspaceBootstrap.ts, AppRuntimeProvider.tsx and the settings plugin's useToggleTree.ts. P2 makes main.tsx their only importer and passes the lists to those five, as createRepoBoot already receives prepare. main.tsx and the two lists are emitted as their own entry chunk, outside the core chunk. A build check fails if the core chunk reaches src/plugins/. Cycles among plugins remain, and ESM evaluates them exactly as it does in dev, where every module is already its own file.
  • Boot files stay in one generation. Observed Install precaches the whole graph, but when precaching didn't finish, a cache miss falls through to the network, which serves the newest deploy's file (src/sw/worker.ts:658-678). That was tolerable for lazily loaded facades. For a plugin file on the boot path, a newer file would import a newer core chunk, and the page would run two cores. So the plugin files the plugin lists reach join the first-paint set, the one held in the iOS boot store (src/sw/bootStore.ts, which exists because the first Cache Storage call of a worker costs about 600 ms on iOS). Alternatively the base import map points plugin paths at content-hashed names, so a miss fails loudly instead of mixing builds.

Every user pays this cost, forks or not, so P2 measures both shapes on the iPhone and on desktop, with the boot store in place, before it merges. Cutting the cost further can come after.

Why the import map, and why now. #289 §7 explored this variant and set it aside for compiled bytes at rest and for needing several import maps. Neither applies now. The approval store already keeps compiled output at rest, and the loader writes a single map (§7). The service-worker variant (#253) would need fork bytes in Cache Storage and a worker that knows which workspace the page is opening. It can come later if needed.

7Boot: write the import map, then start the app

The import map has to be complete before the first module loads, and which forks to map depends on this device's approvals. Those are in IndexedDB, which can only be read asynchronously. So a Vite HTML transform replaces the page's static import map, its module script and Vite's modulepreload tags with one classic loader script. The loader decides the map, writes it as the page's only import map, and only then adds the module script and the preloads. A preload that started earlier could fetch a module before the map exists, and browsers then refuse a later map. The service worker's first-paint list, which inject-sw-build-id.ts reads from those tags today, comes from a manifest the transform emits.

The loader is built from TypeScript as a small self-contained script. It imports the same helpers the app uses for every decision it shares: the hash parser, the overrides-cache decoder, the approval-record predicate (isApprovalRecord), the essential-plugin list and the compiler version. None of those decisions gets a second copy.

What the loader does

  1. Set the crash flag, before anything asynchronous. If the flag is already set, the last boot never painted. Then map nothing this time, mark the forks it had mapped as suspended, and start the app.
  2. If ?safeMode is in the URL, write the base map and start the app.
  3. Read the workspace being opened, synchronously: the URL hash, else ftm.lastWorkspaceId.
  4. Read that workspace's fork index (§4). If it's empty, write the base map and start the app. That's the path for nearly every user, and it reads nothing asynchronously.
  5. Drop forks whose intent is off in the overrides cache, files of essential plugins, forks recorded under a different compiler version, and forks whose seed identities the running build's ledger has retired or changed. All of this is a static comparison; nothing runs.
  6. Read each remaining fork's approval from IndexedDB, with a timeout of about 1.5 s. Check its hash, which covers the source and the served path, against the index, and make a blob URL from its compiled output. On a timeout, start without forks.
  7. Write one import map: the base entries (react and its integrity hashes, "@/": "./src/", the package files) plus, per fork, the bare key and the file's URL form, both pointing at the blob, so an import of either spelling gets the fork. Then add the module script and the preloads.
  • Crash guard. The flag is cleared at the app's firstContentPaint mark (src/App.tsx:99), so a fork that fails to link, throws while loading or breaks the first render costs one bad load, not a stuck app. The loader also listens for module errors while the app starts, and reloads once without forks, rather than leaving a blank page until the next launch. That matters most in the home-screen app, which has no address bar for ?safeMode. A forked file loaded lazily, after paint, reports a failed import to the same suspension. Blob URLs stay alive for the page's lifetime, so lazy imports can still reach them. Intentional reloads ("Reload to apply", the workspace reload below) clear the flag first. Two tabs booting at the same moment can still trip it, which costs one load without forks.
  • The workspace check runs before any write. The loader's guess can be wrong, and the user can switch workspaces inside the page. Either way, resolveInitialLayout compares the resolved workspace's fork set with what's mapped right after resolveWorkspace returns. That's before setActiveWorkspaceId and before bootstrap, whose landing resolvers write (daily notes, seed rows). If the sets differ, it writes the workspace into the URL hash and reloads, so one workspace's forks never run against another workspace's data. A one-shot sessionStorage marker stops a workspace that can't be opened from reloading forever.
  • Is the map current? After sync settles, the app compares what was mapped with what should be. A fork turned off or re-approved on this device, a new fork that passed its fork check, or a fork recompiled after a compiler bump shows "Reload to apply".
  • Compiler bumps. The loader has no Babel, so it never maps output compiled by an older compiler. After paint, the app recompiles a stale fork from its approvedSource, runs the fork check again, updates the index and offers the reload.
  • Cost, reasoned, not measured. With no forks, the loader adds a few synchronous localStorage reads. With N forks, it adds one IndexedDB open and N reads before the first module loads, plausibly a few tens of milliseconds.
  • To verify first. Writing the import map from script before any module loads, after an awaited IndexedDB read, should work wherever import maps do. iOS Safari is the browser that matters, and nothing here has run on it yet. P4 starts with that experiment: on current and previous iOS Safari, Chrome and Firefox, check that a mapped bare specifier resolves, with and without modulepreload tags.

8One loop for every change

Imbue builds every change on a branch and merges it when you approve. Knowledge Medium already has that shape, without git. A change to a fork's source is a block edit that syncs at once. But no device serves it until that device approves it, and until then it keeps serving its pinned version. The edited source is the proposal, and approval on a device is the merge. So eject by an agent, fix with agent (#1433), crystallize (#1434) and an upstream update (§9) need no new state. They all end in the needs-approval or update-available prompt that exists today.

Worked example: "dim done todos" from the bullet menu

  1. On a todo block you choose Change this… (#1432) and type "dim done todos, don't strike them through".
  2. The run's brief lists what draws the block, and which plugin and file each part comes from (§10). The checkbox is todo/index.tsx.
  3. The run calls plugin_source for that file, then eject_file. That creates "My todo: index.tsx" with its base, enabled by intent and approved nowhere.
  4. It changes one line in the fork's content with edit_block.
  5. Nothing runs yet. Each of your devices shows the existing prompt, now reading "My todo would replace todo/index.tsx — review".
  6. You review the diff on the phone and approve. The fork check passes, so the fork goes into the index and settings shows "Reload to use My todo". After the reload, every importer of todo/index.js on the phone gets the fork. The laptop keeps the original until you approve there too.

Nothing runs before approval. Everything the review shows is read from the source: the diff, the imports and the path it serves. The diff is always against this device's pin, or against the base for a first approval. Running unapproved code in order to describe it is what the approval gate exists to prevent. The comment above resolveExtensionInIsolation (src/plugins/agent-runtime/commands.ts:281-302) allows it only for an explicit --verify from the paired bridge, and a fork's review never does that. The pin covers the served path as well as the source, so a synced edit that only changes extension:serves needs approval like any other.

The fork check, after approval

Approval lets this device run the fork, so the app loads it once on its own, as a module in the running page, and compares it with the original. The original is loaded from its file URL, not through the specifier, which may already point at an older fork. Forks approved together are checked together: each sees the others through their own blob URLs. Every way a fork gets approved goes through this check: the prompt, settings' Update, and the bridge's enable. A fork that fails isn't added to the index, and revoking an approval removes its entry.

  • Exports. If the fork dropped an export another module imports, a page that mapped it would fail to link. The check refuses it, for example "My todo no longer exports todoPlugin, which the plugin list imports".
  • Seeds. The check collects the seeds the original file declares, whether exported directly or contributed through an exported extension. The fork must declare every one of them under the same seed key, with the same name, encoding and type id. Dropping or re-keying one would orphan stored values (a renamed property reads as unset), and changing one would reinterpret them. Seeds the fork adds must use a key it owns (@extension/…, bound to the fork block as the extension loader binds them). A system: key the original doesn't declare is refused, so a fork can't claim a key a later release will use. So is any key the running build's ledger lists as retired. Widening config, like adding an enum option, is allowed. A device still on the original then shows the new value as an unknown option (enum decoding only checks for a string, src/data/api/codecs.ts:294-327), and refuses to write it.
  • Identity code. Some stored identity lives in code the ledger can't see. One example is a plugin's own codec: the ledger freezes the preset id but can't tell what the codec parses. Another is a deterministic id derivation, like dailyNoteBlockId in daily-notes/dailyNotes.ts, which exists so that two devices booting at once create the same note. A fork running on one device and the original on another would decode or mint differently, and that duplicates or misreads data. So in v1, files that define a preset core or a derived id aren't forkable. The source provider marks them. Moving a derivation into its own file makes the rest of the plugin forkable. The check also refuses a fork whose content adds such definitions, or imports the plugin lists.
  • Loading. If importing the fork throws, it isn't added to the index, and the error toast offers "Fix with agent".

The #365 manifest-diff idea is computed here, from what the module actually exports and declares, instead of from a manifest someone has to keep up to date.

Who may approve. A gesture you make yourself in the UI can approve immediately, as #289 §5.7 argued: the source is the trusted bundle's own, plus the mechanical rewrite. Eject approves the exact text it generated, not whatever the block holds by then. A run reached through the km MCP tools never approves; it can only write. The paired dev bridge approves through enable, as it does today (agent-runtime/commands.ts:1576-1578), because whoever paired the CLI has already chosen to trust it on that device.

9Keeping up with upstream

After an app update, each device runs the upstream check once per new version. For every forked file whose upstream is the bundle, it fetches that plugin's source file (§5) and compares the authored file's hash with the fork's base-hash. Both are hashes of authored text, before eject's rewrite, so an unchanged file compares equal. Nothing writes during the check; it only sets a status. The check is the same for the other kinds of upstream in #1427 (a shared extension block, a URL). Only how it reads the current upstream differs.

StatusWhenWhat you can do
Up to datebase-hash matches the current upstream file's hash.Nothing.
Upstream changedThe file changed upstream, and the fork's content still equals the base text, which is the file as ejected.Update: replace the content with a fresh eject and move the base forward, in one write. Then it's an ordinary update-available review on each device.
Upstream changed, and so did youBoth sides moved.Merge with agent: a run gets three texts in the same ejected form: the base, yours, and the new upstream run through the same rewrite. It writes the merged source and moves the base to that upstream version in the same write. Then it goes through the same review.

Can't checkOffline, or the source file is from a newer app than the running page.Retried later. No status change.

Base and pin. The base is shared: it records which upstream the fork's content came from and is what a merge starts from, so it moves in the same write as the content. The pin is per device (§4). A review always diffs against this device's pin, so it shows what this device is about to start serving even after another device approved first and moved the base.

Upstream changes that break a fork. A fork imports the plugin's other files by path, so a fix inside actions.ts reaches it with no merge. An update that changes a seed the fork declares is caught before the fork is mapped (§7, step 5). An update that removes something the fork imports, or adds an export the rest of the app now imports from the forked file, makes the page fail to link. The crash guard then turns the fork off, settings says why, and "Fix with agent" can start a merge.

Why updates are never automatic. The content write syncs. If every device fast-forwarded on its own, several devices would race to write the same change. A click on one device writes once, and every device then reviews it. That's the same rule as "a data migration runs once per graph", applied to a smaller write.

11Limits Our read

  • Not forkable in v1: core, essential plugins, files with Vite-only syntax (one today), and files that define a codec or a derived id (§8).
  • json payloads aren't frozen. The ledger doesn't freeze the shape inside a json property. A fork that changes the shape it writes there is trusted like any extension, and devices on the original read what it wrote.
  • Only the page's module graph. Workers have their own graphs, and the import map doesn't apply to them. As far as I know, no plugin code runs in a worker today.
  • No sandbox. A fork runs with the authority the original had. Forking a built-in doesn't widen that, but "edit a built-in" will bring more people to the approval prompt, so its wording carries weight. Enforcement is #1425.
  • Module paths become stored references. extension:serves stores a file path, so renaming a plugin file orphans the forks of it. The upstream check reports "File gone". That seems enough without freezing paths the way the ledger freezes seeds.
  • Slightly slower renders. Forks skip the build-time react-compiler pass. That's cosmetic at plugin scale.

13Open questions

  • Per file or per plugin. P2's numbers decide. Leaning per file for its simpler model, unless it costs clearly more than per plugin on the iPhone.
  • Dev mode. Vite's dev server serves each module at its own URL and adds query strings on hot reload. Map those URLs, or serve forks from a dev-server plugin? Needs a spike.
  • Making daily-notes forkable. Its getOrCreateDailyNote lives next to dailyNoteBlockId, so today that file isn't forkable. Moving the id derivation into its own file is a small refactor, best done when someone first wants that fork.
  • Where the base text lives. Leaning toward a child block per forked file, as sketched in §4: visible, editable, consistent with end-to-end encryption.
  • Everywhere or per workspace. Forks are workspace blocks, like every extension. "Fork daily-notes in all my workspaces" can wait for kits (#1430).
