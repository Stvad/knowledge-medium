Replacing a built-in plugin with your own copy

How someone, or an agent working for them, turns a built-in plugin into an extension they own and edit, so that it takes the built-in's place on every device that trusts it, and finds out when the built-in changes upstream. Rebuilt against current master, with ideas from Imbue Studio, Cloudflare OS and the malleable-systems catalog in #365.

The short version

  • An extension block can name the built-in it replaces (extension:replaces = system:todo). On a device that has approved it and can load it, it runs in the built-in's place in the plugin list, from the first paint. Every other device keeps running the built-in, so nothing ever runs neither.
  • A copy replaces a built-in's behaviour, never its declarations. Types, properties, codecs, local schema and backfills stay the built-in's, because stored data is keyed by them.
  • The built-in's source reaches any run, including graph-only agent runs, through one read tool backed by a per-plugin source file the build emits. The source maps #289 planned to read no longer fit the build.
  • Every later change goes through one loop: someone changes the copy's source, each device keeps running its approved version, and a review on that device approves the new one. That covers an agent's edit, a fix, and an update from upstream. The review prompt already exists. What's new is what it shows.
  • Seven PR-sized pieces. The first is the source provider (#1435).

1The problem Observed

Say you want finished todos dimmed instead of struck through. That styling is one class string in TodoContentDecorator, inside src/plugins/todo/index.tsx, which ships in the app bundle. You can't edit it from the app.

What works today: copy the plugin into an extension block, change the line, and turn the built-in Todo off. The copy has to leave out todoDataExtension. That extension declares Todo's type and properties under system:todo/… seed keys, and the loader rejects any seed key outside @extension/… (src/extensions/dynamicExtensionSeeds.ts:83-87). A copy that keeps it loads as an empty error shell, so on that device Todo is gone and nothing replaces it. The copy imports the original's other modules through the page import map, so it gets the same module instances the app runs. Other plugins import only todo's action ids (srs-rescheduling) and schema constants (roam-import, onboarding). Action ids are looked up by string, so no plugin is left calling the original. 3Ideas borrowed Our read

The two landscape pages (docs/landscape/imbue-studio.html, docs/landscape/cloudflare-os.html) and the malleable-systems catalog in #365 each have something to say about owning a copy of software you didn't write. This design takes these ideas.

Imbue · templates

Check that it boots before it goes live

Adopting a template merges it into a scratch copy, checks that it boots, and only then updates the live workspace.

Approving a fork lets this device run it. It then loads on its own first and takes the slot only if that works; a fork that fails leaves the built-in running. The check comes after approval, not in the review, because checking means running the code (§8).

Imbue · creations

One loop for every change

Crystallize, heal and update all build on a branch and merge on approval.

Here the device's approval is the branch point. Edited source syncs at once, but each device keeps running its approved version until someone approves the new one there (§8).

Imbue · critical apps

More care for the parts everything stands on

The shell and chat get a more careful edit flow.

Essential boundaries can't be replaced, for the same reason they can't be turned off.

Cloudflare · blueprints

Remember the upstream; update by proposal

A gadget remembers its blueprint. An update is a proposal: follow, fast-forward, or a three-way merge the agent checks.

A lineage record on the fork, shared with upstream tracking for shared extensions (#1427), so there is one owner for both (§9).

Cloudflare · one surface

The same methods for people and agents

The UI and the agent call the same server methods.

Eject is one action, reachable from the menu, the palette, the CLI and an MCP tool. The source tool is generated from the same table as the other graph read tools (§5).

Cloudflare #365 · §5

Say what code may do; diff it on update

Capabilities are granted narrowly. In #365, a manifest is shown at enable time and diffed when an update arrives.

Not enforced yet (that's #1425). Before approval, the review lists the modules the fork imports that the built-in didn't, read from the source without running it. After approval, the first load reports what the fork contributes compared with the built-in (§8).

#365 · §1

Reveal codes

A block inspector that answers "which extension did this?" and links each answer to its source.

Every contribution gets an owning plugin. That powers the inspector, which is where "change this" and "make my own copy" start (§10).

#365 · validates

Compose before you fork

Model 2 (an additive override layer, like CSS) beats Model 1 (fork and modify).

The default copy is a wrapper. It copies only the plugin's entry module and imports the rest, so upstream fixes inside those modules reach it with no merge (§4).

#365 · lithification

Fixes don't reach forks on their own

Once you own a copy, propagating upstream fixes to it is the unsolved cost.

An upstream check after each app update, with fast-forward when you haven't edited the copy (§9).

#365 · Hinsen

Keep the dependency graph a tree

Bound the blast radius by not letting extensions reach across.

When one plugin bundles another's parts, that's the edge where a replaced original would sneak back in. A replaced plugin's parts are removed wherever they appear (§6).

Not taken

  • Git branches for changes. Block history, undo and the approval already give the branch-and-merge shape.
  • A resident agent or server-side apps. These give up offline use and end-to-end encryption, as both landscape pages argue.
  • Enforced capabilities now. A fork of a built-in runs the same code the bundle already runs. Sandboxing matters once extensions pass between people (#1425).
  • Automatic upstream merges. Updates are always a gesture. A synced write that several devices would each try to make is a race, so no device writes on its own (§9).

4The model Our read

Built-in
A plugin in the app bundle, wrapped in a systemToggle({id: 'system:<name>'}) boundary (src/facets/togglable.ts:111-122).
Fork
An extension block whose extension:replaces names a built-in's toggle id. It's an ordinary user extension in every other way: TS/JSX content, compiled in the browser, enabled by intent, run only from this device's approval.
Eject
Making a fork from a built-in's source: copy its entry module, rewrite its imports, record its lineage. (The word comes from build tools that hand you their hidden config.)
Wrapper, entry fork, deep fork
A wrapper copies only the entry module and imports everything else from the original; that's what eject produces. An entry fork is a wrapper into which someone pasted a function to change it. A deep fork edits several modules as separate blocks. That needs cross-block imports, which is #253 and out of scope.
Identity contributions
Contributions that name or shape stored data: type and property seeds, value-preset codecs, local schema, workspace backfills, system pages (the Journal page daily-notes ensures, say). Their facets would say so where they're defined (defineFacet({…, identity: true})), so there's one owner for the list.
Lineage
Where a fork's source came from: an upstream (a built-in at an app version, or for #1427 a shared extension block or URL) and the base text of every file it copied.

Four rules

  1. A fork replaces behaviour, never identity. The built-in's identity contributions stay in its slot whatever the fork does. A fork may include the built-in's own identity objects, imported from the original modules. The loader passes those through untouched instead of throwing. A fork may not declare different ones for the same names.
  2. A fork replaces only where it runs. The swap happens on a device where the fork is enabled by intent, approved here, and loaded without error. Anywhere else the built-in runs, and settings shows the usual "Enable here".
  3. A fork takes the built-in's slot. It goes into the plugin list where the built-in was, so order-sensitive facets behave as before. It loads before first paint, like the built-in did.
  4. A replaced built-in doesn't come back in through another plugin. Its behaviour parts are removed wherever another plugin bundled them, unless the fork carries them too.

The fork and its lineage are blocks, following the record-grain rule: you'd want to see, link and edit each of them on its own. Here is the fork eject would create for Todo:

  • My todo extension
    • extension:name My todo
    • extension:replaces system:todo — a toggle id, not a block, so a string is right here
    • content: the ejected entry, about 70 lines (§5)
    • Upstream extension-upstream
      • extension:upstream-kind bundle
      • extension:upstream system:todo
      • extension:base-version the app version at eject
      • index.tsx extension-base
        • extension:base-path src/plugins/todo/index.tsx
        • extension:base-hash sha256 of the content below
        • content: the file as ejected, the base of a later merge

The base text has to be stored. Pages deletes the previous build's files on every deploy (clean-exclude keeps only PR previews), so the version a fork came from can't be fetched again later. All new properties and types are seeds and go in src/data/seedIdentityLedger.ts. For #1427 the same extension-upstream block takes upstream-kind = block with an optional-ref to the source extension.

The rewrite

A fork runs from a blob URL, which has no usable base, so relative imports must become absolute @/ paths. Plugins write relative imports several ways (./actions.ts, ./config, ../other/x.js), so the rewrite resolves each one against the file list. It also unwraps the plugin's systemToggle(…).of([…]) into the module's default export, so the fork carries no system: boundary of its own. Babel is already loaded to compile extensions, so this can be an AST transform rather than text surgery.

6Taking the slot

The swap is a pure function over the static tree, run before resolution. It needs no change to the walker and no new manifest shape, because the toggle boundary already carries the id. Observed getBoundary reads it, src/facets/togglable.ts:78-81.

// src/extensions/replacements.ts (sketch)
/** Swap each replaced built-in for its fork, in place. Identity contributions stay
 *  in the built-in's slot (rule 1); parts of a replaced built-in that another plugin
 *  bundled are dropped there (rule 4). The fork is already loaded and approved (rule 2). */
export const substituteReplacements = (
  tree: readonly AppExtension[],
  forks: ReadonlyMap<string, AppExtension>,   // 'system:todo' → the fork's boundary
): AppExtension[] => tree.map(node => substitute(node, forks))

const substitute = (node: AppExtension, forks: ReadonlyMap<string, AppExtension>): AppExtension => {
  if (!Array.isArray(node)) return node
  const boundary = getBoundary(node)
  const owner = boundary ?? getOwnerMark(node)
  const fork = owner && forks.get(owner.id)
  if (fork) {
    const kept = identityContributionsOf(node)
    return boundary
      ? withBoundary(boundary, [kept, fork])   // the built-in's own slot: its toggle still gates it
      : kept                                  // a part bundled by another plugin
  }
  return withSameMarks(node, node.map(child => substitute(child, forks)))
}

Slots in the data list

The Repo gets its first data runtime, before React, from staticDataExtensions.ts. That list holds bare data extensions with no boundaries, so the sketch would find no slot in it. A replaced plugin's marked part would lose its behaviour, and nothing would put the fork's in its place. So each entry in that list is wrapped in its own plugin's boundary, the same handle the plugin's index uses (todoToggle.of(todoDataExtension)). Observed Nothing changes today. The data runtime is collected without looking at boundaries (resolveFacetRuntimeSync, src/facets/facet.ts:476-484, called from src/context/repo.tsx:67). The settings tree is built from the app list only (src/plugins/extensions-settings/useToggleTree.ts:69), so no row appears twice. The boundary only marks the slot. The boot step (§7) then runs the same substituteReplacements over this list, and the fork's data contributions are installed where the built-in's were, before bootstrap. The whole fork goes in; its UI contributions sit unread until the app runtime replaces this one, just as the static plugins' do when the app runtime installs.

Parts bundled by another plugin

Some plugins compose another plugin's parts by importing them. Observed srs-review bundles the data extensions of srs-rescheduling, daily-notes, references and block-tagging (src/plugins/srs-review/index.ts:77-80). Geo composes the whole references plugin, boundary included (src/plugins/geo/index.ts:27). If references is replaced, its original processors would come back in through srs-review, which bundles referencesDataExtension. srs-review sits later in the list, and processors are keyed last-wins, so the original references.parseReferences would beat the fork's.

Rule 4 needs a mark that says who owns those bundled parts. The plugin's own boundary marks its slot. An ownedBy('system:daily-notes', […]) mark, a non-gating twin of the boundary symbol, goes on each exported part that another plugin composes. Today that's four data extensions; geo's composed copy already carries the references boundary. Marking by owner rather than by "reachable from the replaced plugin" matters, because shared infrastructure like the dialog mount is reachable from many plugins and must not be dropped when one of them is replaced.

After assembly, a check covers what marks can't catch. For every key the fork contributes to a keyed facet, the fork's value must be the winner. A loss is reported at review time, before the fork goes live, for example "srs-review still provides references' original references.parseReferences".

The same path when you reload, not only at boot

Toggling a fork, approving an update or editing a fork's source dispatches refreshAppRuntime(). The provider's async resolve then uses the same substituteReplacements over the forks the loader just returned. Observed Effects are diffed by id across the swap (EffectReconciler, src/extensions/liveRuntime.ts:278-291), so only the replaced plugin's effects restart.

7Boot: load forks before anything runs

To take the slot from the first paint, a fork must be loaded before the static plugins resolve. Its data contributions must also be installed before the workspace bootstrap runs its landing and seeding. The boot already has the right gap.

  • What the new step does. It queries the workspace's extension blocks that carry extension:replaces. For each one enabled by intent and approved on this device, it instantiates the pinned output, using loadApprovedExtension as today. It applies substituteReplacements to the static data list, whose entries now carry their plugins' boundaries (§6), and installs the result on the Repo before bootstrapWorkspace.
  • One instance per module. The loaded forks reach AppRuntimeProvider through the boot result. The compile cache keys modules by block and source hash anyway (compileExtensionModule.ts:201-232), so even a second load is a lookup.
  • Safe mode skips the step entirely, so recovery never depends on any of this.
  • Cost, reasoned, not measured. With nothing forked, the step is one query that returns nothing, so boot is effectively today's. With N forks it's N approval reads from IndexedDB and N imports of already-compiled strings. Plausibly tens of milliseconds for a few forks; the build should measure it with markStartup marks. The slow case is the first boot after a compiler-version bump, which recompiles from the approved source.
  • Local schema and backfills are identity contributions (rule 1), so they stay the built-in's. They already run at Repo setup for every static data extension, whatever its toggle state (repoProvider.ts:644), so forking changes nothing about them.

8One loop for every change

Imbue builds every change on a branch and merges it when you approve. Knowledge Medium already has that shape, without git. A change to a fork's source is a block edit that syncs at once. But no device runs it until that device approves it, and until then it keeps running its pinned version. The edited source is the proposal, and approval on a device is the merge. So eject by an agent, fix with agent (#1433), crystallize (#1434) and an upstream update (§9) need no new state. They all end in the needs-approval or update-available prompt that exists today.

Worked example: "dim done todos" from the bullet menu

  1. On a todo block you choose Change this… (#1432) and type "dim done todos, don't strike them through".
  2. The run's brief lists what draws the block and who owns each part: the default renderer (core), and decorators from Character counter, Todo, the update indicator and Contributors (§10).
  3. The run calls plugin_source for system:todo, then eject_plugin. That creates "My todo" with its lineage, enabled by intent and approved nowhere.
  4. It changes one line in the fork's content with edit_block.
  5. Nothing runs yet. Each of your devices shows the existing prompt, now reading "My todo would replace Todo — review".
  6. You review the diff on the phone and approve. My todo loads on its own first, then takes Todo's slot, and settings reports what it contributes compared with Todo. The laptop keeps the built-in until you approve there too.

Nothing runs before approval. Everything the review shows is read from the source: the diff, the imports, the replaces target. What a fork contributes can only be known by running it. Running unapproved code in order to describe it is exactly what the approval gate exists to prevent; the comment above resolveExtensionInIsolation (src/plugins/agent-runtime/commands.ts:281-302) says the same about --verify. So approval authorizes running the fork, and the contribution checks happen on its first load after that.

What the checks catch, after approval. The fork loads on its own before it takes the slot. A failed load leaves the built-in running. A fork that loads goes in, and settings reports any difference from the built-in. If the run had also dropped todoActionsExtension, the report would read "My todo drops 2 actions that other plugins run by id: todo.cycle (srs-rescheduling)", next to Use built-in instead. The winner check from §6 is reported the same way. That's the #365 manifest-diff idea, computed from what the fork actually registers instead of from a manifest someone has to keep up to date.

Who may approve. A gesture you make yourself in the UI can approve immediately, as #289 §5.7 argued: the source is the trusted bundle's own, plus the mechanical rewrite. A run reached through the km MCP tools never approves; it can only write. The paired dev bridge keeps the install-and-pin it has today (agent-runtime/commands.ts:1438-1442), because whoever paired the CLI has already chosen to trust it on that device.

9Keeping up with upstream

After an app update, each device checks once per new version. For every fork whose upstream is the bundle, it fetches that plugin's source file (§5) and compares hashes with the fork's base records. Nothing writes during the check; it only sets a status. The check is the same for the other kinds of upstream in #1427 (a shared extension block, a URL). Only how it reads the current upstream differs.

StatusWhenWhat you can do
Up to dateEvery base hash matches the current upstream file.Nothing.
Upstream changedA base file changed upstream, and the fork's content still equals what eject produced from the base.Update: replace the content with a fresh eject and move the base forward, in one transaction. Then it's an ordinary update-available review.
Upstream changed, and so did youBoth sides moved.Merge with agent: a run gets base, yours and upstream, writes the merged source, and it goes through the same review. The base moves only when you approve.
Built-in goneThis app version has no toggle with the replaces id.The fork doesn't run, and settings says so. "Run it on its own" clears replaces.
Can't checkOffline, or the source file is from a newer app than the running page.Retried later. No status change.

Wrappers rarely trip this. A wrapper copied only the entry module and imports the rest, so a fix inside actions.ts reaches it with no merge. If an upstream change breaks an import the wrapper relies on, the fork fails to load. Rule 2 then falls back to the built-in and the error toast offers "Fix with agent". Code you paste into a fork by hand isn't tracked. Eject can copy a named submodule instead, which records a base for it too.

Why updates are never automatic. The content write syncs. If every device fast-forwarded on its own, several devices would race to write the same change. A click on one device writes once, and every device then reviews it. That's the same rule as "a data migration runs once per graph", applied to a smaller write.

11What this doesn't fix Our read

  • Behaviour imported by other plugins still reaches the original. Five plugins import getOrCreateDailyNote directly. A fork of daily-notes that changes it gets split-brain: its own calls use the new code, theirs the old. The fix is #289's stage 2: move those entry points behind string-keyed seams, which are mutators, queries, actions and, now, verbs (src/facets/verbFacet.ts). Eject can name the affected importers up front, because they are statically known.
  • Deep forks need cross-block imports (#253). Until then, a fork stays one block and pulls in the original's other modules.
  • Types and properties can't be forked as code. They're identity (rule 1). Editing a built-in type is a separate design. #289 §8's "shadow it with a block" no longer works, because the registry is declaration-authoritative.
  • No sandbox. A fork runs in the page with full authority, like every user extension. Forking a built-in doesn't widen that, but "edit a built-in" will bring more people to the approval prompt, so its wording carries weight. Enforcement is #1425.
  • Toggle ids become stored references. replaces stores system:<name>, so renaming a built-in breaks the forks of it. Pin the set of toggle ids with a test, the way the seed-identity ledger pins seeds, so a rename is a deliberate step.
  • Slightly slower renders. Forks skip the build-time react-compiler pass. That's cosmetic at plugin scale.

Seven pieces, each its own PR. The numbers in brackets are the costs from §1 that a piece removes.

  1. P1 · Source provider (#1435). Tests: the rewrite over every plugin's entry (each rewritten import resolves), the version mismatch, the bounded response.
  2. P2 · Eject, lineage and identity. The extension:replaces, extension-upstream and extension-base seeds, with ledger entries. identity: true on the identity facets, and the loader passing a replaced built-in's own identity objects through, so the ejected entry loads as written. The eject action (menu, palette, CLI, and an MCP write tool through the existing write guard), which approves only on a user gesture.
  3. P3 · Replaces and taking the slot. substituteReplacements, the plugins' boundaries on the data-list entries, the ownedBy mark on the four composed data extensions, the warm-reload path, and the "replaced by" settings row. Tests: position kept for an order-sensitive facet, unapproved device keeps the built-in, a failed load keeps the built-in, a bundled original doesn't come back, identity stays.
  4. P4 · Load before paint. The step in resolveInitialLayout, passing loaded forks to AppRuntimeProvider, and a markStartup measurement. Tests: a fork's data contribution is visible to bootstrap, and safe mode boots static-only.
  5. P5 · Review content. Before approval, in the existing prompt: the diff against the base, imports the built-in didn't have, and the replaces target, all read without running anything. After approval, on the first load: the contribution summary against the built-in and the winner check, reported in settings.
  6. P6 · Upstream check, shared with #1427: the per-version check, Update (fast-forward), and Merge with agent.
  7. P7 · Owners and inspector. Owner attribution in the resolver, the inspector, and the per-plugin describe-runtime listing.

13Open questions

  • Where the base text lives. Leaning toward one child block per copied file, as sketched in §4: visible, editable, consistent with end-to-end encryption. The alternative is a hash only, with the text fetched from a versioned asset, which Pages' deploy-time cleanup rules out unless the build starts keeping old source files.
  • The built-in is gone. Leaning toward not running the fork, with a "Run it on its own" button (§9). Running it alongside whatever replaced the built-in could double up decorators.
  • Additive extensions before paint. Not in this design. Move them only if a user extension needs a type that bootstrap can see, and measure first.
  • Everywhere or per workspace. Forks are workspace blocks, like every extension. "Replace daily-notes in all my workspaces" can wait for kits (#1430).
  • How much of @/ a fork may rely on. Leaning toward accepting drift, as #289 did: a wrapper's breakage is shallow, a failed load falls back to the built-in, and P6 flags it.
