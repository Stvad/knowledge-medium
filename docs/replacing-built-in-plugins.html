Replacing a built-in plugin with your own copy

How someone, or an agent working for them, turns a file of a built-in plugin into one they own and edit. The app then loads their copy wherever it used to load the original, on every device that trusts it, and they find out when the original changes upstream. Built against current master, with ideas from Imbue Studio, Cloudflare OS and the malleable-systems catalog in #365.

The short version

  • A fork is an edited copy of one plugin file, stored in a block. On a device that has approved it, the page's import map points the file's module path (@/plugins/todo/index.js) at the fork. Everything that imported the original now imports the fork: the plugin list, other plugins, extensions. The original file is never loaded.
  • That needs one build change. Today every built-in is linked inside one bundled chunk, so imports between them never go through a URL (§2). Plugin files have to become modules the browser loads by path. That costs files at boot, so the first build PR measures it.
  • Because the fork is the module, it keeps its place in every list, its imports, and its own type and property declarations. Nothing has to be swapped, pruned or passed through.
  • A device that hasn't approved a fork maps nothing and loads the original, so no device runs neither. A fork that breaks boot is skipped on the next load.
  • Every later change goes through one loop: the source changes, each device keeps its approved version until someone approves the new one there, then a reload serves it.
  • Seven PR-sized pieces. The source provider (#1435) and the build change can start in parallel.

1The problem Observed

Say you want finished todos dimmed instead of struck through. That styling is one class string in TodoContentDecorator, inside src/plugins/todo/index.tsx, which ships in the app bundle. You can't edit it from the app.

What works today: copy the plugin into an extension block, change the line, and turn the built-in Todo off. The copy has to leave out todoDataExtension. That extension declares Todo's type and properties under system:todo/… seed keys, and the extension loader rejects any seed key outside @extension/… (src/extensions/dynamicExtensionSeeds.ts:83-87). A copy that keeps it loads as an empty error shell. The copy imports the original's other modules through the page import map. Other plugins import only todo's action ids (srs-rescheduling) and schema constants (roam-import, onboarding), so for Todo nothing is left calling the original. 3Ideas borrowed Our read

The two landscape pages (docs/landscape/imbue-studio.html, docs/landscape/cloudflare-os.html) and the malleable-systems catalog in #365 each have something to say about owning a copy of software you didn't write. This design takes these ideas.

Imbue · templates

Check that it boots before it goes live

Adopting a template merges it into a scratch copy, checks that it boots, and only then updates the live workspace.

After approval, the fork is loaded once on its own in the running page and compared with the original before it is ever mapped. If a mapped fork still breaks boot, the next load skips it (§7, §8).

Imbue · creations

One loop for every change

Crystallize, heal and update all build on a branch and merge on approval.

Here the device's approval is the branch point. Edited source syncs at once, but each device keeps serving its approved version until someone approves the new one there (§8).

Imbue · critical apps

More care for the parts everything stands on

The shell and chat get a more careful edit flow.

Core and essential plugins aren't forkable in v1.

Cloudflare · blueprints

Remember the upstream; update by proposal

A gadget remembers its blueprint. An update is a proposal: follow, fast-forward, or a three-way merge the agent checks.

A base record on each forked file, shared with upstream tracking for shared extensions (#1427), so there is one owner for both (§9).

Cloudflare · one surface

The same methods for people and agents

The UI and the agent call the same server methods.

Eject is one action, reachable from the menu, the palette, the CLI and an MCP tool. The source tool is generated from the same table as the other graph read tools (§5).

Cloudflare #365 · §5

Say what code may do; diff it on update

Capabilities are granted narrowly. In #365, a manifest is shown at enable time and diffed when an update arrives.

Not enforced yet (that's #1425). Before approval, the review lists imports the original didn't have. After approval, the check compares exports and declarations with the original's (§8).

#365 · §1

Reveal codes

A block inspector that answers "which extension did this?" and links each answer to its source.

Every contribution gets an owning plugin and file. That's where "change this" and "make my own copy" start (§10).

#365 · validates

Compose before you fork

Model 2 (an additive override layer, like CSS) beats Model 1 (fork and modify).

Fork the smallest file that holds the change. The rest of the plugin stays upstream's and keeps receiving fixes with no merge (§4).

#365 · lithification

Fixes don't reach forks on their own

Once you own a copy, propagating upstream fixes to it is the unsolved cost.

An upstream check after each app update, with fast-forward when you haven't edited the copy (§9).

#365 · Hinsen

Keep the dependency graph a tree

Bound the blast radius by not letting extensions reach across.

A served fork needs no pruning: when srs-review bundles daily-notes' data extension, it imports it by path, so it gets the fork too.

Not taken

  • Git branches for changes. Block history, undo and the approval already give the branch-and-merge shape.
  • A resident agent or server-side apps. These give up offline use and end-to-end encryption, as both landscape pages argue.
  • Enforced capabilities now. A fork runs with the authority the original had. Sandboxing matters once extensions pass between people (#1425).
  • Automatic upstream merges. Updates are always a gesture. A synced write that several devices would each try to make is a race, so no device writes on its own (§9).

4The model Our read

Built-in
A plugin in the app bundle (src/plugins/<name>/), wrapped in a systemToggle({id: 'system:<name>'}) boundary (src/facets/togglable.ts:111-122).
Fork
A block holding an edited copy of one built-in file, plus extension:serves, the module path it answers (@/plugins/todo/index.js). It's approved and toggled like an extension, but the extension loader skips it: it isn't a contribution list, it's a module.
Eject
Making a fork from a built-in file: copy it, make its relative imports absolute, record its base. (The word comes from build tools that hand you their hidden config.)
Base
The text and hash of the file a fork was made from, and the app version it came from. It's what upstream changes are compared with and what a merge starts from. The same record serves #1427, where the upstream is a shared extension block instead of the bundle.
Frozen identity
What stored data is keyed by: a property's name and encoding (presetId, codec.type), and a type's id (src/data/seedIdentityLedger.ts, header). A release can't change these, and neither can a fork.

Four rules

  1. A fork is the module. It's served at the original file's path, so every importer gets it: the plugin list, other plugins, extensions. The original file is never loaded.
  2. A fork is served only where it may run. That means approved on this device, passed its check, and enabled by intent. Anywhere else the original loads, and settings shows the usual "Enable here".
  3. A fork keeps the original's contract. It exports at least what the original exported. It still declares every seed the original declared, under the same key and with the same frozen identity, and may add new ones. The check refuses a fork that breaks any of this.
  4. Changing what's served takes a reload. The import map is fixed when the page loads.

The fork and its base are blocks, following the record-grain rule: you'd want to see, link and edit each of them on its own. Here is the fork eject would create for Todo's entry file:

  • My todo: index.tsx extension
    • extension:name My todo
    • extension:serves @/plugins/todo/index.js — a module path, not a block, so a string is right here
    • content: the file, with relative imports made absolute (§5)
    • Base extension-base
      • extension:upstream-kind bundle
      • extension:base-path src/plugins/todo/index.tsx
      • extension:base-version the app version at eject
      • extension:base-hash sha256 of the authored file at eject, as the source provider reports it — not of the content below
      • content: the file as ejected, the base of a later merge

A change that spans several files is several fork blocks, usually under one page. The base text has to be stored, because Pages deletes the previous build's files on every deploy (clean-exclude keeps only PR previews), so the version a fork came from can't be fetched later. The new properties and types are seeds and go in src/data/seedIdentityLedger.ts. For #1427 the same extension-base block takes upstream-kind = block with an optional-ref to the source extension.

The rewrite

A fork runs from a blob URL. It has no usable base, and nothing resolves its imports the way the build did. Observed Plugin files import in every form the build accepts. Relative imports are written several ways (./actions.ts, ./config). There are 583 @/ imports without an extension, some of them directories (@/data/api is src/data/api/index.ts). About 99 files import npm packages: lucide-react, zod, uuid, @codemirror/*, unified and the remark and mdast helpers, lodash-es, and others. The aliased @knowledge-medium/agent-cli/protocol is another case. So the rewrite doesn't reimplement resolution. When the build emits a plugin's source file, it also records, for every import in it, the runtime specifier it resolved to. A relative import becomes its @/plugins/…js path, an extensionless or directory @/ import becomes the emitted file (@/data/api/index.js), and a package keeps its name. Eject swaps each authored specifier for the recorded one. Packages then need a URL: P2 emits a stable re-export file for each package and subpath plugin files import (vendor/zod.js), with an import-map entry for each, so a fork gets the same instance the app uses. (Extension blocks get those packages too, which today only have react.) The fork keeps the file's exports, its systemToggle and its seeds exactly as they were, because it is going to be that module. Babel is already loaded to compile extensions, so the rewrite can be an AST pass rather than text surgery.

Vite-only syntax. Observed A blob module gets no Vite processing. Four plugin files rely on it:

  • import.meta.env, read by geo/googlePlacesClient.ts, agent-runtime/bridge.ts and db-mirror/store.ts. The fork compiler rewrites it to a small core module, @/appEnv.js, that exports the variables plugin files read, with the values the running build already has. Nothing is copied into the fork's block.
  • import.meta.glob and ?raw imports, in agent-runtime/authoringCatalog.ts. These need the build's file list, so files that use them aren't forkable in v1. The source provider marks such files, and eject refuses them with the reason.

The P1 test that runs the rewrite over every plugin file also fails on any new Vite-only form, so the list can't grow silently.

6Serving a fork at the original's path

The import map can already point any specifier at any URL. What stops it from replacing a built-in file today is that built-ins never import each other through a specifier. The build links them inside one chunk (§2). So the one build change is this: imports of plugin files stay real imports, written as @/plugins/… specifiers that the import map resolves when the page loads. Core stays bundled as it is.

The build change, and what it costs

A build setting keeps every import that resolves into src/plugins/ external, emitted as a bare @/plugins/… specifier. Each plugin file's own module imports core from the app chunk as rolldown already does between chunks. scripts/check-dist-exports.ts keeps gating the emitted shape. There are two ways to cut it, and the first build PR measures both with the existing markStartup marks:

ShapeWhat loads at bootWhat a fork of an inner file needs
Per fileThe app chunk plus every plugin file the plugin list reaches, roughly the 492 the map lists. About a third of the 1,500 files the bundling removed. Our read If cost is linear, that's around 0.15–0.2 s of iPhone cold launch, not measured.Nothing more. Any file forks alone, and the original is never fetched.
Per pluginThe app chunk, one chunk per plugin (about 60), and a re-export file for each path another plugin imports.Imports inside a plugin are bundled, so forking todo/actions.ts also needs every todo file that imports it, up to the entry. Eject can compute that list from the source provider's import lists. The original's chunk still loads and its top-level code still runs; only its contributions are never registered.

Per file is the simpler model, so the design starts there and treats per plugin as the optimisation if the numbers call for it. Either way the cost is paid by every user, forks or not, so it gets measured on the iPhone before the change merges, and reduced afterwards if it has to be. One reduction worth testing early: make the import map's plain @/plugins/… entries point straight at each module's file, skipping any re-export hop.

No cycle between core and plugins. Plugin files call core at top level, for example definitionSeedsFacet.of(…) in every data extension. So the chunk they import core from must have finished evaluating before they run. If that chunk also contains the plugin lists, it imports the plugins that import it. That's a cycle, and the plugins would see core's bindings before they're initialised and throw at boot. Observed Five modules import the lists today: src/context/repo.tsx, src/data/repoProvider.ts, src/bootstrap/workspaceBootstrap.ts, src/extensions/AppRuntimeProvider.tsx, and the settings plugin's useToggleTree.ts. P2 makes main.tsx the only importer of staticAppExtensions and staticDataExtensions, and passes the lists to those five sites. createRepoBoot already receives prepare this way, for the same reason (src/context/repo.tsx). Core then reaches no plugin, since lint already forbids core from importing one directly. Plugins load after the core chunk has evaluated, and a build check fails if the core chunk ever reaches src/plugins/. Cycles among plugins themselves remain. ESM evaluates those exactly as it does in dev today, where every module is already its own file.

Why this is a stage-1 mechanism now

#289 §7 set the import-map variant aside for three reasons. Two of them no longer apply:

  • Bytes at rest. The approval store already keeps each approved extension's compiled output in IndexedDB (CompiledRecord.compiled), so serving a fork from it adds no new copy of plaintext.
  • Remapping by URL, with several import maps. Neither is needed. The build emits bare @/ specifiers, so the map remaps specifiers, the original feature. The loader writes one map, before any module loads (§7).
  • Reload to apply. Still true, and accepted (rule 4).

The service-worker variant (#253) would serve fork bytes at the file's URL instead. It needs the bytes in Cache Storage and a worker that knows which workspace the page is opening, so the import map is the smaller step. The two can coexist later.

What no longer needs building

The first draft of this doc swapped forks into the plugin list. That needed a substitution pass run from four separate places, marks on parts other plugins bundle, slots in the data list, special handling inside forks, and a loader exception for a built-in's seeds. Two review rounds kept finding places it didn't reach. Serving the module removes all of it. Every list, bootstrap's landing runtime, srs-review's bundled data extensions and other forks all import by path, so they all get the fork. And the fork keeps its system: seeds because it isn't loaded as an extension.

7Boot: write the import map, then start the app

The import map has to be complete before the first module loads, and which forks to map depends on this device's approvals. Those are in IndexedDB, which can only be read asynchronously. So index.html's module script becomes a small classic loader, emitted by a Vite HTML transform. It decides the map, writes it as the page's only import map, then adds the app's module script.

What the loader does

  1. Leave if ?safeMode is in the URL: write the base map, start the app.
  2. Read the workspace being opened: the URL hash, else ftm.lastWorkspaceId (src/utils/lastWorkspace.ts). Both are synchronous.
  3. Read that workspace's fork index from localStorage. It lists the forks that passed their check on this device, with the path each one serves. It's written by the check in §8, never by sync. If the index is empty, write the base map and start the app.
  4. Drop forks whose intent is off in the overrides cache (extensions.overrides.<workspace>, also synchronous). Drop files of essential plugins.
  5. Read each remaining fork's approval from IndexedDB, check its source hash against the index, and make a blob URL from its compiled output.
  6. Write one import map: the base entries (react, integrity, "@/": "./src/") plus one entry per fork, "@/plugins/todo/index.js": "blob:…". Set the crash flag, then add the app's module script.
  • Crash guard. Before starting the app, the loader writes which forks it mapped to a localStorage flag. The app clears the flag once it has painted. If the next load finds the flag still set, the last boot never finished. The loader maps nothing this time, and settings explains which forks were suspended and offers to retry. A fork that fails to link, throws while loading, or breaks the first render therefore costs one bad load, not a stuck app. A tab closed mid-boot also trips the guard, and costs one load without forks.
  • Wrong workspace guess. If the workspace the app actually opens isn't the one the loader guessed, and their fork sets differ, the app reloads once into the right one. Switching workspaces in the app does the same when the sets differ.
  • Is the map current? After sync settles, the app compares what was mapped with what should be. A fork turned off or re-approved on this device, or a new fork that passed its check, shows "Reload to apply".
  • Cost, reasoned, not measured. With no forks, the loader adds a few synchronous localStorage reads. With N forks, it adds one IndexedDB open and N reads before the first module loads, plausibly a few tens of milliseconds. The build change in §6 is the larger cost, and it's paid with or without forks.
  • To verify first. Writing the import map from script before any module loads should work wherever import maps do, but iOS Safari is the browser that matters and nothing here has run on it yet. That's the first thing P4 checks.

8One loop for every change

Imbue builds every change on a branch and merges it when you approve. Knowledge Medium already has that shape, without git. A change to a fork's source is a block edit that syncs at once. But no device serves it until that device approves it, and until then it keeps serving its pinned version. The edited source is the proposal, and approval on a device is the merge. So eject by an agent, fix with agent (#1433), crystallize (#1434) and an upstream update (§9) need no new state. They all end in the needs-approval or update-available prompt that exists today.

Worked example: "dim done todos" from the bullet menu

  1. On a todo block you choose Change this… (#1432) and type "dim done todos, don't strike them through".
  2. The run's brief lists what draws the block, and which plugin and file each part comes from (§10). The checkbox is todo/index.tsx.
  3. The run calls plugin_source for that file, then eject_file. That creates "My todo: index.tsx" with its base, enabled by intent and approved nowhere.
  4. It changes one line in the fork's content with edit_block.
  5. Nothing runs yet. Each of your devices shows the existing prompt, now reading "My todo would replace todo/index.tsx — review".
  6. You review the diff on the phone and approve. The check loads the fork once on its own, compares it with the original, and records it in the fork index. Settings shows "Reload to use My todo". After the reload, every importer of todo/index.js on the phone gets the fork. The laptop keeps the original until you approve there too.

Nothing runs before approval. Everything the review shows is read from the source: the diff, the imports and the path it serves. The diff is always against what this device last approved, or against the base for a first approval. Running unapproved code in order to describe it is exactly what the approval gate exists to prevent; the comment above resolveExtensionInIsolation (src/plugins/agent-runtime/commands.ts:281-302) says the same about --verify.

The check, after approval. Approval lets this device run the fork, so the app loads it once on its own, as a module in the running page, and compares it with the original file:

  • Exports. If the fork dropped an export another module imports, a page that mapped it would fail to link. Then "My todo no longer exports todoActions, which other modules import", and it isn't mapped.
  • Frozen identity. The check collects the seeds the original file declares, whether exported directly or contributed through an exported extension. The fork must declare every one of them, under the same seed key, with the same name, encoding and type id. Dropping or re-keying one would orphan the stored values (a renamed property reads as unset). Changing one would reinterpret them. So the check refuses either, for example "My todo no longer declares status under system:todo/property/status". Changing a stored identity needs a data migration, which a fork can't carry in v1. New seeds are fine. Widening config, like adding an enum option, is allowed too. It comes with a note that devices still on the original will read the new value as invalid until they approve.
  • Loading. If importing the fork throws, it isn't mapped, and the error toast offers "Fix with agent".

A fork that passes goes into this workspace's fork index on this device, and the next load serves it. The #365 manifest-diff idea is computed here, from what the module actually exports and declares, instead of from a manifest someone has to keep up to date.

Who may approve. A gesture you make yourself in the UI can approve immediately, as #289 §5.7 argued: the source is the trusted bundle's own, plus the mechanical rewrite. A run reached through the km MCP tools never approves; it can only write. The paired dev bridge keeps the install-and-pin it has today (agent-runtime/commands.ts:1438-1442), because whoever paired the CLI has already chosen to trust it on that device.

9Keeping up with upstream

After an app update, each device checks once per new version. For every forked file whose upstream is the bundle, it fetches that plugin's source file (§5) and compares the authored file's hash with the fork's base-hash. Both are hashes of authored text, before eject's import rewrite, so an unchanged file compares equal. Nothing writes during the check; it only sets a status. The check is the same for the other kinds of upstream in #1427 (a shared extension block, a URL). Only how it reads the current upstream differs.

StatusWhenWhat you can do
Up to datebase-hash matches the current upstream file's hash.Nothing.
Upstream changedThe file changed upstream, and the fork's content still equals the base text, which is the file as ejected.Update: replace the content with a fresh eject and move the base forward, in one write. Then it's an ordinary update-available review on each device.
Upstream changed, and so did youBoth sides moved.Merge with agent: a run gets three texts in the same ejected form: the base, yours, and the new upstream run through the same import rewrite. It writes the merged source and moves the base to that upstream version in the same write. Then it goes through the same review.

Can't checkOffline, or the source file is from a newer app than the running page.Retried later. No status change.

The base and the pin answer different questions. The base is shared. It records which upstream the fork's content came from, and it is what a merge starts from, so it moves in the same write as the content. The pin is per device: approvedSource in this device's approval record. A review always diffs the new source against this device's pin. That shows what this device is about to start serving, even after another device has approved first and moved the base.

Upstream changes that break a fork. A fork imports the plugin's other files by path, so a fix inside actions.ts reaches it with no merge. If an upstream change removes something the fork imports, or adds an export the rest of the app now imports from the forked file, the page fails to link. The crash guard (§7) then turns the fork off for the next load, settings says why, and "Fix with agent" can start a merge.

Why updates are never automatic. The content write syncs. If every device fast-forwarded on its own, several devices would race to write the same change. A click on one device writes once, and every device then reviews it. That's the same rule as "a data migration runs once per graph", applied to a smaller write.

11Costs and limits Our read

  • Every user pays for the build change. Plugin files loaded by path cost boot time whether anyone forks or not. It's measured in the first build PR and optimised after (§6).
  • Changes take a reload. The import map is fixed per page.
  • Exports are a contract. A fork can add exports but not drop ones the rest of the app imports. The check enforces it, and the crash guard catches what the check can't, like an upstream change after approval.
  • Core isn't forkable. It stays bundled, so changing core still means a build and a deploy. Essential plugins' files aren't forkable in v1, and neither are files that use import.meta.glob or ?raw imports (one today).
  • Dev mode isn't designed yet. Vite's dev server serves each module at its own URL and adds query strings on hot reload. Whether the loader's map entries match those, or a dev-server plugin should serve forks, needs a spike.
  • Only the page's module graph. Workers have their own graphs, and the import map doesn't apply to them. No plugin code runs in a worker today, as far as I know.
  • No sandbox. A fork runs with the authority the original had. Forking a built-in doesn't widen that, but "edit a built-in" will bring more people to the approval prompt, so its wording carries weight. Enforcement is #1425.
  • Module paths become stored references. extension:serves stores a file path, so renaming a plugin file orphans the forks of it. The upstream check reports it ("File gone"). That seems enough without freezing paths the way the seed ledger freezes seeds.
  • Slightly slower renders. Forks skip the build-time react-compiler pass. That's cosmetic at plugin scale.

13Open questions

  • Per file or per plugin. P2's numbers decide. Leaning per file for its simpler model, unless it costs clearly more than per plugin on the iPhone.
  • After an app update, map forks at once or hold them? Mapping at once keeps your fork across deploys, and the crash guard catches a fork the update broke. Holding them until they are rechecked costs one load without forks per deploy. Leaning toward mapping at once.
  • Dev mode. Map Vite's own module URLs, or serve forks from a dev-server plugin. Needs a spike.
  • Where the base text lives. Leaning toward a child block per forked file, as sketched in §4: visible, editable, consistent with end-to-end encryption.
  • Everywhere or per workspace. Forks are workspace blocks, like every extension. "Fork daily-notes in all my workspaces" can wait for kits (#1430).
  • How much of @/ a fork may rely on. Leaning toward accepting drift, as #289 did. A fork imports by path, a broken import trips the crash guard, and P6 flags the change.
