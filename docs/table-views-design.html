Table Views

Tana-style query tables over the type system — a proposed tables plugin: editable table views fed by a text query language compiling onto TypedBlockQuery.

Status: proposed design — no implementation.
Last verified against code: 2026-11-20 (master @ 1cb73b08). Earlier verifications: 2026-09-10 @ 203de003, 2026-07-12 @ 44d8631d. The design works on both property storage modes (§2).

Decisions proposed in this doc (each argued in its section):

  • Ship as a core plugin (src/plugins/tables/): a table block type (name pending §7) plus table:view child blocks, real npm dep on TanStack Table (headless), reusing the property panel's ValuePreset editors for cells (§4.2, §4.6). No bespoke embed type — a table is a block; embedding a table (or one specific view) is the generic ((id)) block-embed affordance, the media model (§4.4).
  • One table substrate, two row sources: a query, or a block's own children ("view any node as a table"). Children-as-rows is a query term (childof=self), not a second mechanism. No row source returns property field or value rows (§4.1).
  • The query is text, and text is the only stored artifact — no shadow copy of resolved ids. The UI saves terms as name^fieldId; bare names are legal for hand and agent authoring; an unresolvable name is a visible term error, never a silent empty (§4.3).
  • Compile to TypedBlockQuery where the engine can express a term; evaluate the residue in JS over the pre-filtered set, with client-side terms marked in the UI (§4.3, §4.7).
  • Columns are property schemas keyed by stable definition-block id, never display name. Every schema has one, so one header affordance covers all columns (§4.2).
  • Cells read the cell projection and write through tx.setProperty — correct in both storage modes. A cell whose key holds a value the cell cannot show is marked, not editable in place. Commit on Enter/blur (never per keystroke); sort/group re-evaluation is held while a cell editor is open; a new row stays pinned until commit, with query-condition back-fill (§4.5).
  • Render cap + "show more" first; row virtualization deferred until it is designed together with the focus model it constrains (§4.6).
  • View config is layered: durable view definitions live as props on table:view child blocks, plus a UiState-scoped tweak layer; casual interactions write the tweak layer, an explicit "save view" promotes. Both layers sync; whether tweaks key per device is open (§7).

1. Why: the type system has no collection surface

KM already has the Tana-shaped half of a database feature: additive multi-typing (types on any block), user-defined types as blocks (block-type), property schemas as blocks (property-schema) with codecs and ValuePreset editors, and a SQL-compiled typed query engine. What it lacks is the surface that makes a type system legible: nowhere to see all #book rows with their fields as columns, sort by a property, edit a value without opening each block's property panel.

The design deliberately follows Tana's model rather than Notion's, because KM's data model already made that choice. Notion bundles schema and views on a database container; a page has properties only by living inside one. Tana (and KM) attach schema to the type — instances live anywhere in the outline and are gathered by search. The consequence worth stating up front: collection views are node-anchored, not type-anchored — a table hangs off whichever block displays it, exactly like Tana's view config and unlike Notion's database views.

2. Platform facts this design relies on: properties as children

In a child-backed workspace a property is stored as child blocks — a field row (::((fieldId))) with value children — and the properties_json cell is a projection of them, maintained in the same transaction. Storage is selected per workspace by workspaces.properties_migration: 'cell' | 'children' | 'cell-off' (owner-only, forward-only): new workspaces are created child-backed, older ones stay cell-backed until their owner flips them, and no client reaches 'cell-off'. Both modes are in the field, so the governing rule is: read the cell, write through the typed seam — correct in cell-backed, child-backed and mid-backfill workspaces alike. The rule has two limits the design must own, rows 3 and 5 below.

3. The query engine, as it is

3.1 What TypedBlockQuery gives today

Verified against src/data/api/typedBlockQuery.ts and src/data/internals/typedBlockQuery.ts:

  • types (contains-any), where over codec-encoded properties — eq / lt / lte / gt / gte / between / exists, NULL-safe excludes (IS NOT TRUE), JSON paths inlined so expression indexes match. A comparator matches only a cell in its codec's storage shape (WhereStorage: text / number / boolean / iso-date): a cell of another shape — what a re-type leaves behind — matches no comparator, equality included, so no exclude removes it either; dates compare within years 0000–9999. The test is module-private SQL (STORAGE_TEST); §3.2 lists what the JS tail needs from it.
  • where.<field>.target traverses a ref (equality join) or refList (json_each fan-out) into inner predicates on the referenced block (compileTargetTraversal).
  • referencedBy: {id, sourceField?} on a predicate compiles to EXISTS(… block_references br WHERE br.source_id = <candidate>.id AND br.target_id = ?) (compileReferencedByExists) — i.e. "the candidate references X (optionally via field F)". This is both ref-equality and refList-contains, already production-used (typeExtraction.ts: findCandidatesByPropertyShape). Ref codecs are deliberately not where-comparable; the compiler's own error message routes to referencedBy. Caveat: block_references is a projection maintained for schemas registered as ref/refList at write time — values written while a defining plugin was disabled aren't in it.
  • match (AND) / exclude (NOR) predicate lists with self / ancestor scope; the ancestor walk is a recursive CTE that is both depth-bounded and gated: assertAncestorWalkBounded rejects the query unless a candidate-bounding filter exists (types / referencedBy / a self-scope id / selective self-where). A bare "everything under X" is not compilable — the grammar must account for this (§4.3).
  • Reactivity: per-dimension deps (type channel, per-property channel, reference channels) for membership, plus per-row deps from hydration — one subscribed handle re-fires on any change to any matched row, including properties and content not mentioned in the query. It also over-fires — property channels are keyed by (workspace, property name), so any block writing that property re-resolves the view, and any member-row edit re-runs the query + full rehydrate. Direction is right (no under-fire; a table's cells stay live through one subscription); cost is budgeted in §4.7.
  • Surfaced as repo.queryBlocks / subscribeBlocks (+ active-workspace shorthands); hydrated rows include content. The underlying core.typedBlocks handle also takes a limit (created order only) that these do not forward, and has ids-only and count projections (core.typedBlockIds / core.typedBlockCount) that skip row hydration.
  • Free-text is SQL-able too: blocks_fts is a trigger-maintained trigram FTS5 index over live blocks.content (clientSchema.ts) — true case-insensitive substring semantics on an index. A content term compiles as an FTS join intersected with the typed candidates (exhaustive — core.searchByContent's top-N limit is that query's choice, not the index's), and the narrow KERNEL_CONTENT_CHANNEL dep (searchByContent's own pattern) provides exactly the invalidation an SQL-pushed content term needs: it fires when a non-member starts matching via a content edit, which per-row deps alone would miss. Residue: sub-trigram-length terms (< 3 chars, isTrigramSearchable) fall back to the JS tail. On a child-backed workspace the join must also exclude value rows, whose text matches too (§2 row 5); core.searchByContent pays for its own exclusion with a whole-workspace dep rather than the narrow channel, so what this costs a table is to be measured in phase 1.

4. Design

4.1 One substrate, two row sources

A table block renders a query's results as rows. "View any node's children as a table" — the pure outliner↔table flip — is the same substrate with a one-term query: childof=self. Every row source excludes property machinery (§2 row 5): a property is a column, never a row, whatever the outline's display mode shows. A children-term routes to the children query with propertyChildren: 'none' (the engine has no direct-children predicate), and the query's remaining terms evaluate in JS over those children — a block's children are few. Everything else routes to subscribeBlocks with the exclusion §3.2 asks of the engine. Either way it is one subscription, and the view definition, the embed mechanism and the table component see one shape. Rows are always live references to real blocks — an editing view, not a report.

Embedding follows the media model: a table is a block, so pinning it elsewhere is the generic ((id)) block embed — of the table block (its default/active view) or of one table:view child block (that view, pinned). No bespoke embed type (§4.4).

4.2 Column model

  • A column = a property schema, identified by its definition block id (§2 row 7) — never by display name. The leftmost column is the block itself (title/content; navigates on click).
  • Default column set: for a type-backed query (#book), the type's declared properties — read off the block-type definition block's property-schema refList, the same registry the property panel's render-only ghost rows already draw from (nothing is materialized on type-add). Union-of-present-fields for untyped queries and mixed children — and post-synthesis every present key resolves a definition block, so even those columns have identity (§2).
  • Every column header links to the schema's definition block. In child-backed workspaces every field row references its definition, so the definition block's backlinks are a live "where is this field used" list.
  • Add column = pick an existing schema (typeahead over the registry + definition blocks) or create one (reuse AddPropertyForm / the ValuePreset picker; new names must be round-trippable [[…]] labels, §2 row 7). Adding a column does not touch the type; when the query is type-backed, offer — never auto-apply — "add to #type's template", Tana's exact split.
  • Cell display/editing resolves by codec shape through the existing property-panel machinery (resolvePropertyDisplay, ValuePreset editors) — a table cell editing property P on row B is semantically the property panel's row for (B, P). Ref cells render as chips that navigate.
  • A multi-valued cell (list / refList) edits member-wise — add, remove, reorder one member — and commits a delta, not the editor's array: setProperty(row, schema, current => apply(current, delta)), so the array is computed inside the tx from what is stored then. Writing the array the editor opened on would delete any member that arrived meanwhile, its row subtree included (§2 row 4). The cell never writes value children itself.
  • Resolving a name or handle to its fieldId from UI code needs a named seam. tx.resolvePropertySchema returns a workspace-bound schema inside a tx, and the resolved / identity-unavailable result belongs to same-tx processors (resolvePropertySchemaName). Phase 1 either reads definition blocks through a query or asks core to surface that resolution on the repo.

4.3 The query language — text-first, agent-authorable

Requirements: a readable one-liner; writable by coding agents and by the UI (the UI writes text — text is canonical); compiles onto TypedBlockQuery; degrades to the JS tail for the residue, honestly marked.

The grammar has three term shapes plus grouping — small enough that an outline-style query builder can round-trip it later:

Terms AND by juxtaposition — matching the engine's shape (match=AND, exclude=NOR, types=OR) — so the compiler's job is a clean split: every SQL-marked term joins the TypedBlockQuery; or-groups, pseudo-fields, and any term the engine rejects join the JS tail, and the UI marks tail terms ("evaluated client-side"). One term, one answer, wherever it evaluates. For where-capable codecs a tail comparison applies the engine's storage-shape rule (§3.1), through the predicate §3.2 asks core to export. Negation is complement: != is !(=), so an unset or wrong-shape cell satisfies every negated term and no positive one — SQL's IS NOT TRUE exclude. List codecs and unregistered keys have no storage shape; the tail compares their decoded values. The or-group syntax exists precisely so boolean trees have a surface, not just an escape hatch — field evidence (§6) shows real corpora use them.

Name resolution & renames follow the platform rule (§2 row 7): durable text is fieldId-addressed, names are display-resolved. The text is the sole stored artifact; there is no shadow copy of resolved ids — a second storage location would need a sync invariant and a which-wins rule, and hand edits (CLI, agents) would bypass it. The grammar's name^fieldId form is the canonical spelling:

  • The UI/query-builder saves terms as name^fieldId — id authoritative and rename-proof (the text-grammar sibling of the field rows' own ::((fieldId)) form), name kept as inline decoration and refreshed opportunistically at parse/save.
  • Bare-name terms stay legal for hand/agent authoring and resolve at parse time (through the seam §4.2 names). A rename rewrites them best-effort in the tx that renames the definition, which — like the platform's own fan-out (§2 row 8) — runs only on the initiating client. A bare name the rewrite missed becomes a term error, below; that is why the UI never saves one.
  • An unresolvable name (or dangling ^fieldId) is a visible term error on the table (that term shows as errored; the rest of the query still runs) — never a silent empty result and never a silent fallback to a different schema.

4.4 View definition storage

  • Content = the query, in a ```table fence — an unambiguous boundary (the plain-text alternative leaves "is line 2 more query or prose?" undefined), edit-mode-friendly (edit = raw text, parse errors render as an error placeholder, never a crash), and greppable/authorable by agents.
  • Named views = table:view child blocks of the table block, each holding its view config in props (columns, sort, group, view type, column widths; the block's content is the view's name). Views thereby have block identity — addressable by ((id)) (which is how per-view embedding works, no bespoke embed type), referenceable, commentable — and the stable-id-not-name lesson comes free. The table block's own props hold only the default-view ref. View children are typed and excluded from row sources: a childof= row set skips table:view blocks as well as property machinery (§4.1) — otherwise a node viewed as a table would show its own view-config blocks as rows.
  • Tweak layer = UiState-scoped props: active view on the table block; unsaved sort/filter/column tweaks on the view block they tweak. Casual interactions (header-click sort) write this layer; an explicit "save view" promotes tweaks into the view block's durable props. ChangeScope.UiState uploads and syncs — it is a second synced layer distinguished by undo-exclusion and convention, not a per-user store. In a single-user workspace that behaves exactly like Tana's personal layer; true per-user tweaks need a per-user ui-state home and are future work, not claimed now. On a child-backed workspace each tweak write also mints or rewrites synced field and value blocks, so a tweak is written at the end of a gesture (a finished column drag, not its frames).
  • Children-as-rows mode keeps its one view's config in props on the viewed block itself, not in a table:view child: a view child under an arbitrary user node would appear in its outline, its child count and every other children consumer. Named views are a table block's feature. Whether a pane shows the block as outline or as table is the pane's (panelViewModeProp); how the table looks is the block's, so every pane in table mode sees the same one.

4.5 Editing model

  • Write path: cells write setProperty(rowId, schema, value), one undo group per gesture; multi-cell gestures use the atomic tx.setProperties batch, and new rows go through createTypedChild (§2 row 2). Never raw cell JSON, never field-row children.
  • What the cell cannot see (§2 row 3). One batched query per view finds the rows whose key has a field row but no cell value. Such a cell renders a marker ("unreadable value — open the row") and is not editable in place: typing there would overwrite text the user cannot see. The repair happens in the expanded row, where the value row is visible. Clearing a cell is unsetProperty, which deletes the key's field rows and anything nested under its value rows; when those value rows have children, the clear asks first.
  • Commit cadence: Enter/blur, not keystrokes. A per-keystroke setProperty would be a per-keystroke transaction and a per-keystroke re-resolution of the view (§4.7). The editor holds local state until commit.
  • Sort/group hold while editing. Editing the sorted column would otherwise move the row under the open editor (the subscription re-fires on your own write; remounting an active editor mid-typing is a known bug class). The hold covers a row while one of its cell editors is open or focus or edit mode is anywhere inside its expansion — a property row edited there re-projects the cell as it is typed, and a half-typed value projects as unset. Membership and sort changes are applied to the model, but that row's position and membership are pinned; the view settles on commit or when focus leaves the row.
  • New row lifecycle: the bottom placeholder creates the block, applies back-fill, and stays pinned (out of sort order, exempt from membership filtering) until the user commits the row — otherwise a row that doesn't yet satisfy the query vanishes mid-typing, and a sorted view teleports it away as soon as it matches. Back-fill taxonomy, explicit: type terms → add the type; = predicates → set the value; childof=/under= → choose the parent (direct child for childof; for under, create under that ancestor); refs=[[X]] → not back-filled; comparisons, negations, or-groups, content terms → not back-filled. If non-back-fillable positive terms remain unsatisfied at commit, the row keeps its pin with a "doesn't match this view's query" marker rather than disappearing. A query with neither childof= nor under= names no parent for the new row; that rule is open (§7).
  • Row expansion: an expanded row mounts the real nested block renderer (the row's sub-outline, editable) — the thing Tana tables can't do. The expansion is an ordinary outline: it shows the row's property rows when the user's display mode does (§2 row 6), and the same value is then editable in the cell and in the expansion, both through the one write seam.
  • Row-level actions reuse block actions (open in panel, etc.) rather than inventing table-specific ones.

4.6 Grid implementation

Survey of React table/spreadsheet libraries (2026-07-12; sizes from bundlephobia, licenses/peers from the repos): TanStack Table v8 — headless — is the fit. MIT, ~15 KB gz, React-19-native, actively maintained; sorting, grouping, row expansion, column sizing/order/pinning all exist as headless state and the DOM is entirely ours. That last property is the decisive one three times over: cells are ValuePreset editors and ref chips (real React components with app context), expanded rows mount the nested block renderer, and keyboard handling must compose with KM's shortcut-surface dispatch and class-based logical focus rather than fight them with a packaged grid's global handlers. Runner-up: adazzle's react-data-grid (15 KB gz, zero deps, MIT, React ^19.2, excellent built-in keyboard nav) if build-it-yourself proves too costly. Eliminated: AG Grid Community & MUI X (row grouping / master-detail paywalled), Glide Data Grid (canvas: React 18 peer cap, custom cells are hand-drawn, grouping half-shipped), Handsontable (non-commercial license), react-datasheet-grid (no sort/group/expand).

Cap + "show more" first; virtualization deferred — deliberately. KM's focus restoration and scroll-to-focused read the DOM; with windowed rows the focused block's row may not be mounted at all. Virtualizing in v1 would re-open that class of bug while keyboard nav doesn't even exist yet. v1 renders a capped page (grouping-aware) with "show more"; row virtualization lands only together with the keyboard/focus work, designed as one unit — and core has most of that unit's substrate: LazyBlockComponent (IntersectionObserver mounting) plus FocusedRowLazyMount/lazyMountRegistry (the focused row is kept mounted even when scrolled away; panel scroll restores by cursor, not pixel offset). The deferred phase adopts that mechanism rather than inventing windowing.

Focus model: KM logical focus stays on the table block itself (the viewport); cell focus is table-internal, in-memory state. Table rows are not KM-focusable blocks in v1 (the blocks inside an expanded row are, scoped to that row's subtree) — the alternative (every row a focusable block location) collides with panel-level focus arbitration and is exactly the seam virtualization breaks; revisit with evidence.

Other rendering rules, inherited from hard-won list-view experience downstream: never subscribe to a second block per row (ref-chip labels come from a shared lookup built once per view, cover images are IntersectionObserver-gated); keep per-row work O(1). Mobile: v1 tables are read-only on narrow viewports (horizontal-scroll container; cell editing is desktop-first) — a dense editable grid is the worst iOS surface to debug and shouldn't gate the rest.

4.7 Reactivity & cost budget

One row-source subscription per table (§4.1), plus the one batched unreadable-value query (§4.5). Per-row hydration deps mean out-of-band edits (another pane, another device) reach cells with no per-row subscriptions — verified plumbing, and the reason cells can be "live" cheaply. The costs to budget, not hide:

  • Any write to any matched row re-runs the query (SQL + full rehydrate + JS tail). At thousands of matched rows this is the dominant cost — mitigations, in order: the render cap bounds React work (the tail sort still runs over the full set); commit-on-Enter bounds self-inflicted re-runs; LIMIT/ORDER pushdown (§3.2) if profiling says the tail hurts.
  • Property channels over-fire (name-keyed per workspace) — a busy property on unrelated blocks re-resolves the view. Acceptable at current scales; the fix, if ever needed, is engine-side channel narrowing, not view-side caching.

5. Phasing

  1. Read-only substrate. Fenced query text → parser → TypedBlockQuery compiler + JS-tail evaluator; one subscription; TanStack table with cap+show-more; named views as table:view children + tweak layer; embedding via the generic block-embed affordance. Needs the two small engine changes of §3.2. Tests run the view on cell-backed, child-backed and mid-backfill workspaces, child-backed first — it is where new workspaces start. (A tested JS evaluator for filter trees + sort/group/limit exists downstream — §6 — and ports directly.)
  2. Editing. ValuePreset cell editors + setProperty; commit/hold/pin semantics (§4.5); add-column flow with the "add to type template" suggestion; new-row back-fill; keyboard nav (cell-focus store + shortcut context).
  3. Children-as-rows. childof=self routing (the children query with propertyChildren: 'none'), "view as table" affordance (natural attachment: panelViewModeProp, the per-panel view-mode prop with a view= URL-grammar slot), row expansion mounting the nested renderer.
  4. Depth. Grouping UI (kanban drag in a cards variant writes the grouped property), query-builder UI emitting the text grammar — built on the backlinks propertyFilter.ts adapter (per-codec operator affordances already compiling to BlockPredicate) — engine pushdowns as warranted, virtualization + focus as one unit on the lazy-mount substrate (§4.6), per-type default views only with evidence.

6. Field evidence: the downstream corpus

A downstream deployment (spolakh's workspace) has run a predecessor for a month: an Obsidian-Bases port ("bases v1") rendering read-only tables from .base YAML over a workspace-wide byType('page') scan with JS filtering. Its corpus is the best available evidence for what real queries need:

  • 116 live table definitions (124 at import). 18 of 116 use or: groups across predicates — or-groups are not a theoretical need; a grammar without an OR surface cannot express ~16% of a real corpus. (Hence §4.3's group syntax, and hence "JS tail" rather than "unsupported".)
  • Constructs in live use that shaped the grammar beyond types + properties: title-contains (KM's content term, §4.3), mtime/ctime comparisons (the timestamp pseudo-fields), string-list contains, and a path-prefix folder test (import-provenance-specific; maps to under= only where vault folders became ancestry — a per-corpus migration judgment, not a grammar rule).
  • Most of that corpus filters on unregistered (import-provenance) props, which compileWhereClause rejects by design — so migrated-corpus terms evaluate in the JS tail unless schemas are minted for them. The SQL-pushdown win applies fully to typed queries (#task status=open), which are the design center here; the honest statement for legacy corpora is "same evaluation as before, behind a real grammar".
  • Operational lessons already folded in above: render caps beat naive full renders (its 100-row cap); one shared query, never per-row subscriptions; edit mode = raw text with error placeholders is a fine authoring UX.

7. Open questions

  • Per-user/per-device tweak layer: UiState uploads and syncs; the platform's per-device pattern is keying by client id (clientContext / layout-session-block precedent). Adopt that keying for tweaks from the start, or ship the simpler synced tweak layer first? Also open here: the column list's codec. A refList is the doctrinal pointer, but it adds a backlink per view to every definition block and crowds §4.2's usage list; plain field-id strings keep that list clean.
  • Saved-queries seam: projectorRuntime names "commands / saved queries" as the planned third definition-block projector. The table block may be that seam's first real instance — coordinate the table/table:view types with it rather than landing a parallel mechanism.
  • New-row parent: where does a row created from a query with no childof= / under= live? createTypedChild needs a parent. Candidates: today's daily note, where captures already go, or a per-type home.
  • Stale cells on a cold device: on a freshly synced child-backed device a cell can lag its children until the projection pass sweeps. Scalar edits are last-write-wins and list edits are deltas (§4.2), but a delta is computed from the in-tx cell, which can itself be stale. Gate list editing until the sweep has finished, or accept it?
  • Naming: core styles markdown pipe tables inside a block. A table type and a ```table fence sit close to that in a user's vocabulary while being a different thing (a live query view, not literal cells). Keep table, or name the type for what it is (a query/collection view) and leave "table" to mean one of its view types beside cards?
