Handle lifecycle in hidden subtrees

Why <Activity mode="hidden"> permanently blanks a KM subtree, and the smallest fix that closes it.

The ask. A KM subtree hidden with React's <Activity> can come back permanently blank — no error, no pending work, no recovery short of remounting it. The cause is a lifecycle gap between HandleStore's ref-counted GC and the fact that a hidden subtree can still render while its effects are unmounted. Two small changes close it: make handle disposal observable (a 'disposed' status), and have useHandle re-acquire when the handle it holds is dead.

Why this matters

<Activity> is React's sanctioned primitive for "keep this mounted but inactive" — how you preserve state, scroll position and media playback across a hide/show without paying a remount. It is stable in the React version this repo ships (19.2.6) and is currently used nowhere in the codebase; this report is the first attempt to use it. Today that attempt fails, and the failure is worse than an obvious crash because it is:

  • Silent. No throw, no console error, no pending React work. The subtree simply renders nothing, forever.
  • Time-dependent. Hide for three seconds and all is well; hide past gcTimeMs (5 s) and it can die. Quick manual testing passes.
  • Not specific to Activity in principle. Anything that lets a committed subtree render while its effects are unmounted lands in the same hole. Activity is simply the first thing to do it.

The motivating consumer is a fork-side session host that keeps several layout sessions warm so switching perspectives stops remounting the world; it is on a CSS-hiding workaround until this lands, which costs it the input isolation Activity's effect cleanup would have given for free. (Optional background, fork-internal: perspective keep-alive design.)

The defect

Three separately-reasonable behaviors compose into a trap. Line references in this section are to the code as it stood before this PR (upstream master 587136700) — several of them are what the fix below changes, so they will not resolve to the same thing on the merged branch.

1. A handle schedules its own GC at construction. src/data/internals/handleStore.ts:506–522

A handle is inserted into the store before anything retains it, so the constructor schedules a gcTimeMs sweep that "the first retain() (load/subscribe) cancels". The comment already names a near-miss of this case: "an abandoned React concurrent-render lookup whose subscribe effect never commits". Ours differs in one decisive way — the render commits; only its effects never run.

2. Subscribing to a disposed handle is a silent no-op, and disposal is unobservable. src/data/internals/handleStore.ts:759–773 
subscribe(listener: (value: T) => void): Unsubscribe {
  if (this.disposed) {
    // Listening to a disposed handle is a no-op + immediate
    // unsubscribe; callers should re-acquire via the factory.
    return () => {}
  }

The contract — "callers should re-acquire via the factory" — is sound but unsatisfiable from where the caller stands: the factory (repo.query.*) runs during render, and the only thing that would cause another render is a notification from a subscription that no longer exists. The caller cannot even detect the situation: dispose() resets status_ to 'idle' (handleStore.ts:899–916), disposed is private (:470), and HandleStatus has no disposed member (src/data/api/handle.ts:1). So a dead handle is indistinguishable from a fresh one — which is why useHandle's ensure-load effect cheerfully calls load() on it, and that rejection lands in a swallowed catch (src/hooks/block.ts:175–182, pre-fix).

3. A hidden Activity subtree renders, but does not run effects.

That is Activity's defining behavior, not an accident: components stay mounted, effects unmount (disappearLayoutEffects / the Offscreen case of commitPassiveUnmountOnFiber). React also re-renders hidden Offscreen content in the background — notably when a context value an ancestor provides changes, which marks hidden descendants dirty. Crucially, when such a render mounts new hook state inside a hidden tree, its passive effects are skipped, not deferred (recursivelyTraverseAtomicPassiveEffects never calls commitHookPassiveMountEffects for function components). Since useHandle's subscription and its ensure-load both live in effects, a hidden subtree can acquire a handle that nothing ever retains.

How they compose

Note first what does not happen: dispose() never notifies. It clears listeners and returns, and by then the listener set is empty anyway. Nothing is pushed out of the store when a handle dies — every render below is driven by React, not by us.

  1. The subtree is hidden. Effects unmount, useHandle's subscription is released, handle H1 drops to refCount 0 and schedules GC (handleStore.ts:885–897).
  2. Five seconds later H1 disposes and drops its value; the store removes its key (:915), so the factory will mint a fresh handle next time it is called.
  3. React re-renders the still-hidden subtree — e.g. because an ancestor's context value changed. The consumer reads peek() on the dead H1, gets undefined, renders its empty state (and unmounts its children — real DOM removal, inside a hidden container), and that render calls the factory, minting H2.
  4. Effects still do not run, so H2 is never retained — and by (1) it disposes on its own constructor GC timer.
  5. On reveal, effects reconnect and subscribe to the already-dead H2: subscribe() no-ops (2), and ensure-load calls H2.load(), which rejects with Handle … has been disposed into the swallowed catch.
  6. No subscription, no pending render, no error. Permanently blank.
Why React's own recovery doesn't save you — and why a small test case will mislead. useSyncExternalStore installs a second effect (updateStoreInstance) that on reconnect re-reads the snapshot and calls forceStoreRerender if it changed. With one death that fires: the snapshot goes from real data to empty, React forces a render, the factory is re-invoked, and the subtree heals by itself. That is why a shallow one-component repro recovers and looks fine. The permanent failure needs the second death at step 3–4: by reveal, the pre- and post-snapshots are both the consumer's empty sentinel — e.g. LayoutRenderer's frozen EMPTY_ROWS, returned by its selector for any unloaded value — so the comparison sees no change, no render is forced, and the reconnected subscription attaches to a corpse.

Proposed fix

1. Make disposal observable

Extend HandleStatus (src/data/api/handle.ts:1) with 'disposed' and have status() report it. This is deliberately preferred over exposing a disposed getter: status() is already on the Handle<T> interface, so nothing new is added to the contract, and the other implementer — Block (src/data/block.ts:43), which has no disposal concept — simply never returns it. A getter would have to be added to the interface and stubbed on Block.

Separately, subscribe() on a disposed handle should warn in development rather than silently returning a no-op. The silence is the single biggest reason this took as long to find as it did.

2. useHandle re-acquires when its handle is dead

useHandle is the one funnel every consumer goes through, so the repair belongs there rather than at each call site. In the subscribe callback — which React invokes from a passive effect, so dispatching state there is ordinary usage — ask for the render that re-acquires:

const [, forceReacquire] = useReducer(n => n + 1, 0)
const attempts = useRef(0)

// Capped: re-acquiring only helps if the caller then yields a LIVE handle,
// and the two shapes above never will. Past the cap, say so instead of
// looping — only the caller can fix it.
const requestReacquire = useCallback(() => {
  if (attempts.current >= REACQUIRE_ATTEMPT_LIMIT) {
    if (import.meta.env.DEV) console.warn(/* … still disposed after N attempts … */)
    return
  }
  attempts.current++
  forceReacquire()
}, [handle])

const subscribe = useCallback(
  (listener: () => void) => {
    // A handle can die while this subtree is committed but its effects are
    // unmounted (<Activity mode="hidden">): nothing retains it, so it hits
    // the store's GC. Subscribing to a disposed handle is a no-op, and only
    // a RENDER re-acquires from the factory — so ask for one.
    if (handle.status() === 'disposed') {
      requestReacquire()
      return () => {}
    }
    return handle.subscribe(listener)
  },
  [handle],
)

Recovery gets exactly ONE owner — the subscribe callback. The ensure-load effect guards the same condition but only to decline: it neither asks a corpse to load (that only rejects) nor falls through to reset the attempt budget described below. Two owners would each spend from that budget for one logical recovery.

Re-acquisition converges: the fresh handle is retained by the very subscription that follows, which cancels its constructor GC (handleStore.ts:876–883), and dispose() removes the key synchronously before any later getOrCreate can run.

Superseded — see the correction below. That rests on an invariant the hook cannot enforce: the caller's factory must run on every render and return a live handle. Two shapes violate it — one that memoizes the handle (useMemo(() => repo.query.subtree(…), [id])), which hands back the same corpse, and one that mints a fresh dead handle per render. Every call site in core satisfies it today (useChildIds, useChildren, useSubtree, useParents, useBlockQuery all call the factory inline; the memoized ones memoize repo.block(…), and a Block never disposes).

So the hook caps re-acquisition at REACQUIRE_ATTEMPT_LIMIT attempts and then stops, warning in dev. Be clear about what that means: for a violating caller the outcome is still a permanently stale subtree — bounded and diagnosable instead of an unbounded render loop, but not recovered. The limit carries headroom for StrictMode, whose dev-only double-invoke of passive effects spends two attempts on one logical recovery.

Alternatives considered

OptionWhy not
Revive on subscribe Have a disposed handle re-register itself with the store. getOrCreate is a bare synchronous map lookup (handleStore.ts:310–316), so a handle re-inserting under its old key after another consumer's render already minted a replacement would split ownership — double loads, split notifications. Re-acquiring through the factory keeps one owner per key.
Raise gcTimeMs Only widens the window. A subtree left alone for a minute still dies, and the failure stays silent and time-dependent — the worst property of the bug is untouched.
Don't GC never-retained handles Reintroduces exactly the leak the constructor sweep exists to prevent (abandoned concurrent-render lookups; handles orphaned at an old key by a registry-epoch bump).
Leave it; hide with CSS instead The fork's current workaround, and it does work. But it forfeits Activity's effect cleanup, so every hidden subtree keeps its action contexts registered and input isolation must be rebuilt by hand — and it leaves a silent trap in the data layer for the next consumer.

Correction: the compiler memoizes the factory

The invariant above — "every call site in core satisfies it today; they call the factory inline" — is true in the source and false in the build. This app compiles with React Compiler (vite.config.ts:77, babel({presets: [reactCompilerPreset()]}), unconditional, so it applies in dev too), and the compiler hoists the factory call into its memo cache. From the served LayoutRenderer:

if ($[1] !== block.id || $[2] !== block.repo.query) {
  t1 = block.repo.query.subtree({id: block.id, hidePropertyChildren: true});
} else {
  t1 = $[3];        // cache hit — the disposed handle, forever
}

block.id and block.repo.query never change, so the render forced to re-acquire gets the same corpse back. Every compiled consumer memoizes; the invariant is not something callers can be asked to uphold. Worse, the dev-only warning that was supposed to make this diagnosable is stripped from production builds, so it failed silently.

The repair moves into the handle. A disposed handle now resolves to whatever is live at its key: peek/status forward to an existing replacement (pure — safe on the render path), and subscribe/load/read resolve, adopting a replacement if the store has one and otherwise resurrecting the instance itself, which it can do because it still holds its key and loader. Adoption-before-resurrection is what keeps one owner per key — the objection that ruled this out the first time. The hook-side re-acquire machinery is removed: it cannot work under the compiler, and its subscribe branch actively blocked the new path.

Measured end to end against a locally-patched build (the perspective host under <Activity>, hidden 9 s): unpatched blanks the lane; patched recovers in 4 of 5 clean runs. The one failure followed a mid-run extension re-pin and is probably confounded, but that is not established — treat "reliably fixed end to end" as not yet proven, while the unit-level contract is pinned per clause.

Pinning it

One caveat is worth stating for whoever writes the regression test, because the obvious test passes either way: a single hide/GC/reveal cycle self-heals through React's own updateStoreInstance check, with or without the fix. The test has to reproduce the second death — a real <Activity mode="hidden"> tree (not a conditional unmount, which discards the hook state that carries the bug), with at least one additional render of the still-hidden subtree between the first handle's disposal and reveal — and then assert on the recovered value, since the broken path throws nothing. Reverting the fix should make that named test fail.

Scope

Deliberately narrow: no change to GC policy or to the store's key model. One behavior on the public Handle<T> surface does change: read() on a disposed handle now throws a synchronous Error instead of falling through to throw this.load(). That path handed a Suspense boundary a freshly rejected promise on every retry — render, throw, reject, re-render, forever, with nothing surfacing — so an error boundary is strictly better. No live caller reaches it today (only Block is Suspense-read, and it never disposes), but it is part of this diff rather than a separate concern.

Otherwise this is the minimum that makes <Activity> usable with KM's data layer, and it removes a silent failure mode whether or not core adopts Activity anywhere.

One known gap is left deliberately unfixed. useHandle is not the only way a component subscribes to a store-backed handle: GroupedBacklinksLiveBridge (src/plugins/grouped-backlinks/GroupedLinkedReferences.tsx:642–660) acquires its handle during its parent's render and subscribes in a raw useEffect, so it carries the identical hazard and none of this fix. It is dormant today (nothing uses <Activity> yet) and routing it through useHandle means restructuring its snapshot/query-epoch logic — real work, not a one-liner. A sweep of src/ found no other live instance of the shape. Flagged rather than fixed so whoever wires up the first <Activity> consumer doesn't rediscover it the hard way.
