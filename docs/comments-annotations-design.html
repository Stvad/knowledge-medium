Comments and annotations

Comments, highlights and edit suggestions on notes, as blocks — 2026-10-28

What has to be true

  1. Comments and annotations are blocks in the workspace, with everything blocks get: sync, undo, search, references, hand-editing, E2EE.
  2. A separate side surface shows them beside the notes, and can be turned on and off.
  3. A comment can point at part of a block: select some text, comment on that.
  4. They sit sensibly next to references. A block already shows how many blocks reference it; comments are the adjacent idea, "what is being said about this block", and the UI shows the two side by side without counting one as the other.
  5. Something outside the UI (an agent) can subscribe to comments in a scope (a page, a subtree, one block), read them, and reply.
  6. Every comment shows who wrote it, human or agent.
  7. Edit suggestions ("replace this with that", accept or reject) fit the same model.
  8. Text elsewhere can quote part of a block, the way a block reference quotes a whole block. A quote shows up on the source block as an annotation.

The idea in one picture

  • The target block is never written to, except when someone accepts an edit suggestion. Everything about the annotation lives on the thread root.
  • A thread with no comments is a highlight; a thread with comments is a discussion; a thread with an annotation:replacement is an edit suggestion. They are all the same record.
  • The target's block id lives in exactly one place, the annotation:target ref. Everything else about the anchor is text: the quote, which is the root's content, plus where it started and a little context on each side.
  • Quoting part of a block from other text is an ordinary ((root)) reference to a thread root. The reference renders the quoted text live, and the quoting block shows up in the source's margin (see Quoting part of a block).
  • Discovery runs through the references index: block_references rows with source_field = 'annotation:target'.
Explainer — block_references. A local, trigger-maintained index with one row per edge: (source_id, target_id, alias, source_field). Content references ([[Page]], ((id))) have an empty source_field. A ref-typed property projects a row whose source_field is the property name. It is indexed on (target_id, workspace_id), so "which threads point at B" is an index lookup. (src/plugins/references/localSchema.ts)

Data model

A thread is a metadata block, and its children are the comments

The thread root holds the anchor and the status. Its content is the quoted text, or empty for a whole-block thread. Each comment is a child block, and a reply to a comment is a further child. So a thread is just an outline:

  • Enter at the end of a comment starts the next one.
  • A nested reply is an indented block.
  • [[links]], ((refs)) and formatting all work inside comments.

Putting the first comment's text on the root would save one block per thread. That is rejected for two reasons:

  • Agent writes to the metadata. When an agent resolves a thread, re-anchors it, or answers a suggestion, the contributors processor attributes that write to the block it lands on. With a separate root it lands on the metadata block, not on somebody's comment. (Human-only writes record no attribution either way, so this is about agent writes.)
  • Uniform rendering. The card renders the root's subtree, so every comment is a comment at whatever depth it sits, rather than "the root" plus "the rest". Nested replies need nothing extra (see Nested threads).

Comment blocks carry no type: a comment is simply a visible descendant of a thread root. A second marker would be a second source of truth, and hand-typed replies would not carry it.

Where threads live

Threads live as children of one workspace kernel page, Comments (km).

  • Creation. getOrCreateKernelPage creates the page at the first comment, inside the same undoGroup as that comment, so creating the first comment is one undo step. It uses markerType: null, because the page is found by its derived id.
  • The alias. Like System Migrations (km), it is a name nobody types. A plain Comments would not abort when the user already has such a page: the kernel page would just be created without the alias. But that leaves two pages titled "Comments", and [[Comments]] resolving to the user's.
  • Deleting it is refused while it holds live threads, through a blockDeletionGuardsFacet guard. Deleting a page deletes its subtree, so one stray delete would otherwise hide every comment in the workspace. A restore of the page alone would not bring them back. The recovery path, if it ever happens anyway, is undo or a subtree restore.

The anchor

  • The quote is the root's content: a substring of the target's raw markdown. That is the same text an agent reads through the API, so an agent can annotate a range just by quoting it, and edit mode can decorate the range without any translation.
  • Why content, not a property. Three things follow from it.
    • Deletion. A ((root)) reference to a deleted thread is inlined as the root's content (inlineDeletedBlockRefsProcessor), so a quote someone embedded in their text survives as plain text instead of vanishing.
    • Without the plugin, the thread reads as the quoted text with comments under it, the way an imported highlight with notes does.
    • Rewrites. The reference processors rewrite every referrer's content, and the root's content is now one of them. A page rename ([[Old]] → [[New]]), a merge retarget, or the inlining of a deleted ((x)) therefore changes the quote in step with the target, on every workspace.
    A quote is a copy, not a mention. The root's content is parsed like any block's, and that has to stay: the processors above find referrers through block_references. But a quote containing [[Page]] or [[claude]] is not the thread mentioning anything. If it counted as a mention, it would duplicate the target's backlink, and highlighting text with a watched page in it would launch a billed agent run. So the backlinks sources owner excludes content edges whose source is an annotation:thread root (see Comments and references). The exclusion is at display level, never at parse level.
  • annotation:quoteStart records where the quote began when it was made.
  • annotation:quotePrefix and annotation:quoteSuffix hold up to 16 characters of text on either side of the quote, as it was when the anchor was made.
  • No quote means the thread annotates the whole block.
  • A quote never splits a reference span ([[…]], ((…)), [label](((…)))). Creation widens the selection to cover whole spans, so the reference plugins always see complete spans inside a highlight.
  • Targets are content blocks. A property field row or value row is refused at creation, because scope queries never descend into them, and accepting a suggestion there would splice text into an encoded property value.

A blockContentRendererFacet contribution renders the root wherever it appears:

  • As a reference (isReference): the live text of the resolved range in the target, linked to the target. That is what a range reference shows.
  • Elsewhere, for example on the container page or in a breadcrumb: "on ⟨target excerpt⟩ · “quote”".
  • When the anchor is stale: the stored quote, marked as changed.

The root's content is display-only in these renderings. Editing it would move the anchor, so that goes through re-anchoring.

Anchoring against changing text

Resolution is a pure, synchronous function of the target's content, the quote (the root's content) and the three anchor properties. It is recomputed at render time and never persisted. It returns one of three states.

  • exact: the quote sits at quoteStart, and the text on each side of it, taken over the same 16-character window, equals the stored prefix and suffix. It is equality, not "starts with". So a stored context shorter than 16 characters, which means the quote was near the block's start or end, must still reach that boundary. A quote that ended the block must still end it.
  • moved: the quote occurs elsewhere and its surrounding text still agrees with the stored context. The occurrence picked is the one with the most context agreement; ties go to whichever is nearest quoteStart. "Agrees" means at least 4 matching characters of context. If the stored context is shorter than 4 characters, all of it must match. When the stored context is empty (the quote was the whole block), any occurrence qualifies.
  • stale: no occurrence qualifies. The thread stays on the block, and its card shows the original quote marked as changed. The user can select new text to re-anchor, or anchor the thread to the whole block.

With no quote, the thread annotates the whole block, and none of this applies.

Why the context matters (measured). The block was Ship the fix, then test the fix., and the second the fix was quoted, at quoteStart = 24. Its stored prefix is " fix, then test " and its suffix is ".". Then someone prepends a note:
•Note to self: Ship the fix, then test the fix.

at 1951 character (a space)
at 381417 characters (the whole prefix, plus the suffix)
The nearest-to-hint rule this design first used picks 19, which is the wrong text. Context agreement picks 38, and the state is moved.
  • Quoted occurrence deleted. If the quoted occurrence is deleted instead (…then test it.), the remaining the fix agrees on one character, so the anchor goes stale rather than jumping to the other one.
  • Merge. After a Backspace merge, the retargeted thread finds its text by its prefix, even though quoteStart now points into the other block's half.

"Moved" can still be wrong in contrived cases, for example identical sentences with identical surroundings. Wrong place is worse than stale, so two rules follow:

  • Anything that writes requires exact: creating, accepting a suggestion, re-anchoring.
  • A moved highlight still shows, but its card says the text around it changed.

Re-anchoring is an explicit user action: "confirm position", or select new text. It rewrites quoteStart and the context from the content as of its own transaction. If the confirmed text is no longer there, the transaction refuses.

Quoting part of a block

A block reference ((B)) quotes a whole block. To quote part of one, reference a thread root: ((T)), where T anchors that part of B.

No new syntax is involved. It is an ordinary block reference, so the parser, backlinks, copy and paste, undo and the deletion inlining all apply unchanged. What is new is only how a thread root renders when it appears as a reference.

Why not new syntax, such as ((B "the quoted text"))?

  • It would put a second copy of the anchor in X's content. Context, re-anchoring and merge retargeting maintain the thread root, but not that copy.
  • The quoted text would be parsed as X's own text, so a [[Page]] inside it would become X's mention.
  • References are edges without positions (BlockReference = {id, alias, sourceField}). Finding the range references to B would mean re-parsing the content of every backlink source.

The cost of the chosen shape is that X's raw text holds an opaque ((id)). In the app it renders as the quote. Without the plugin it renders as the quote snapshot, which is the root's content.

UI

Highlights

  • Edit mode. A CodeMirror extension, added through codeMirrorExtensionsFacet, turns resolved ranges into mark decorations. The offsets are exact because the quote is raw content. Moved ranges and suggestions get distinct styles.
  • Read mode. A remark plugin, ordered before the reference plugins, splits positioned text nodes at range boundaries and wraps the pieces in an annotation-mark node.
    • The risk is ordering: text slices that other plugins split out lose their positions (src/markdown/blockSeparators.ts notes this).
    • Spike this first. If it can't be made exact, read mode shows the pill but no inline highlight.
  • Where highlights render. Only in a panel's primary outline and in the focused editor. Nested surfaces show none: backlinks, embeds, block refs and breadcrumbs.

The side margin

  • Toggle. The margin is per panel. It is switched by the action annotations.toggleMargin or a header item. The flag is stored on the panel's UI-state block, so it survives a reload.
  • Mount. A panelMountsFacet component draws the margin beside the panel's scrollport.
    • It composes with the video-notes and SRS layouts. A blockLayoutFacet contribution would not: that facet is last-wins, and both of those already use it.
    • It also sits outside the text's max-w-3xl frame, so on a wide panel the margin uses space that is empty today instead of squeezing the text.
    • The cost is scroll sync. The mount reads the scrollport's scroll offset and the rows' positions, and moves the cards on scroll and resize within one animation frame.
  • Placement. Each card goes at its target row's top in the panel's primary render scope. Rows mount lazily (LazyBlockComponent), so a row that has not mounted yet is placed from its placeholder's estimated position, and its card moves once the row mounts. The order is by target position, then by quote start. A card's top is its anchor's height or just below the previous card, whichever is lower.
  • Collapsed blocks. Threads anchored inside a collapsed subtree are shown as a single stub on the nearest rendered ancestor.
  • The card. A card renders the thread root through BlockComponent in a nested surface, so its comments are normal editable blocks. The header shows the quote ("whole block" when there is none), a moved or stale badge when it applies, and Resolve. Suggestion cards also show the diff, with Accept and Reject. Below the comments, "Quoted in" lists the blocks that quote this range. Each comment has its own Reply.
  • Threads on comments. A thread anchored to a comment, such as a quote-reply or an embellishment on a phrase in a comment, renders inside that comment's card, as a highlight with its attachment. It never gets a margin card of its own.
  • Closed threads (resolved, accepted or rejected) are hidden behind "show closed".
  • Narrow panels and mobile. When the panel is too narrow for text plus margin, the margin turns off, and the comment pill expands the threads inline under the block.
  • "All comments" is an action that opens the container page, where the thread renderer shows each target. A filtered query view (open threads, by author, by scope) comes later.

Creating, replying, resolving

Comment on a selection

The action is annotations.commentOnSelection, in the edit-mode context. Its default binding is chosen against the shortcut-conflict check. It gets a mobileKeyboardToolbarItemsFacet entry, so it appears in the mobile toolbar.

  1. Call flushEditorContent(view). The stored row lags the editor by its debounce, and the anchor must be computed from what the user sees.
  2. Read the selection and widen it to whole reference spans. Then compute the quote, its start and its context.
  3. Open a composer, in the margin or inline. The draft lives in UI state and is written only on submit, so an abandoned comment leaves no empty thread behind.
  4. On submit, run one undoGroup. It ensures the container exists, then runs a transaction that creates the root with createTypedChild (passing its references) and the first comment. Inside that transaction the anchor must still resolve exact. If the text changed under the user, the transaction refuses and the draft is kept, so the user can reselect.

Other gestures

  • Block-level comment: the same action in normal mode, or the bullet context menu.
  • Highlight: the same flow without the composer, giving a thread with no comments.
  • Reply: creates an empty child of the comment being answered (or of the root, for a reply to the thread) and focuses it. From there it is ordinary block editing.
  • Resolve and reopen: set annotation:status.
  • Delete:
    • Deleting a thread deletes the root's subtree.
    • Deleting the last comment from its card also deletes the thread. That is a UI rule only.
    • Deleting a comment that has replies, from its card, blanks it to "[deleted]" instead of removing it. Deleting a block deletes its children, and those replies may be someone else's, for example an agent's. Deleting in the outline still removes the subtree, and undo restores it.
    • A root with no comments that arises any other way (sync, an agent, hand-editing) is simply a highlight, which is a valid state.

Not in v1

  • Commenting on a read-mode selection. It needs a mapping from the DOM selection to raw offsets, and none exists. It also needs a guard so that a drag-select does not end in the click that enters edit mode (plain-outliner/clickToEditAction.ts). That guard would decorate the action through the action-dispatch seam, the way vim-normal-mode does.
  • A selection spanning several blocks. One thread has one target.

Nested threads

Replies are children of the comment they answer, so a thread is already a tree. Nested, LessWrong-style threads need no data change, only these rules, which the sections above already follow:

  1. Replies go under the comment they answer: one Reply per comment, and agent replies land under the comment the agent is answering.
  2. Agent context is a chain, from the thread root down to the comment being answered, plus the anchor, never the whole tree.
  3. Scope is recursive: threads anchored to comments of in-scope threads are in scope too.
  4. A comment with replies is blanked, not removed, when deleted from its card.
  5. Navigating to any comment lands on the target, with the card focused and that comment in view.
  6. A thread anchored to a comment renders inside that comment's card.

Two sources shaped these, and point at what a later nested UI could add.

  • LessWrong: nested replies with collapse, sorting and permalinks; "[deleted]" placeholders that keep replies alive; quote-replies; and side-comments in the margin, which is the margin design here.
  • Max Krieger's Chatting with Glue: conversation as an outline of atomic messages, where a tangent nests under its parent instead of moving to a side panel. That is this thread model. Its other ideas map onto pieces that already exist:
    • Its "highlight as a bidirectional reply" is a range reference: a child comment containing ((T)), where T anchors the span in the parent comment.
    • Its "embellishments" (a reaction, a pointer, a reminder with a checkbox) are threads whose root also carries another type, such as todo. The root may compose other types.
    • Its "edits as messages, marked accepted" are edit suggestions.

Not adopted yet, though nothing here blocks them:

  • splitting a comment into bullets to reply to each part (Glue's "expand", which is an ordinary block split);
  • hand-written summaries on collapsed branches;
  • a "what's new, each with a little context" view;
  • per-message unread markers.

Per-reader state, meaning unread markers and per-reader collapse, belongs in each user's UI state, never on comment blocks. Today's collapse is a synced block property, so collapsing a branch collapses it on every device. That is fine for one reader.

Authorship

  • Author: the comment's first attribution:creators entry if it has one, which is the case for every agent comment. Otherwise it is the user page of created_by, which covers every human comment, because human-only writes record no attribution.
    • created_by alone would be wrong for agents: bridge and MCP writes run inside the tab and stamp the tab's human user id.
    • Attribution alone would leave every human comment without an author.
  • Display: the existing ContributorBadges decorator, in a card-scoped mode that also shows humans. It already loads profiles and separates creators from other editors. A second chip would show twice on agent comments.
  • Time: relative, from created_at.

No "edited" marker in v1. Human edits to human-only blocks record nothing, and dispatch bookkeeping stamps user_updated_at, so neither signal says "the text changed".

Edit suggestions

A suggestion is a thread whose root carries annotation:replacement: "replace the quoted text with this". Everything else is shared with comments: the anchor, the resolver, the card, the discussion underneath. The additions are one property, two status values, and one accept transaction.

Suggested edit
We moved the launch to ThursdayThursday 9am
🤖Claude · agent · 5m
Matches the vendor's email.
AcceptRejectReply

Accept is one transaction, so it is one undo step:

  1. Refuse if the target is deleted.
  2. Resolve the anchor against the target's content as of this transaction, and require exact: the quote is at quoteStart, and the windows on either side equal the stored prefix and suffix. Anything else refuses with "the text changed since this was suggested" and offers "confirm position", which re-anchors.
  3. Splice replacement into the content, and set annotation:status = accepted.

Reject only sets rejected.

  • Exact also stops a second application. Suppose Thursday has become Thursday 9am. A duplicate of that suggestion, or the same one reopened, still finds Thursday at its offset. But the suffix is now " 9am because…", not " because…". So the anchor is moved rather than exact, and accept refuses instead of writing Thursday 9am 9am.
    • The same holds at the end of a block. Take Meet Thursday: its stored suffix is empty. After accepting, the window after Thursday is " 9am", not empty, so the anchor is not exact.
    • And at the start. A stored prefix shorter than 16 characters must still begin the block.
    • Except where the text repeats. In Say very very very very very very good., accepting very → very very leaves the quote at its offset between the same 16-character windows, so a duplicate would still be exact. Accept therefore refuses any application after which its own anchor would still resolve exact; there the user edits the block directly. "Confirm position" can also put a copy's anchor back on applied text, where it is exact again, so accept also refuses where the text around the quote already reads as the replacement.
  • The editor. A pending debounced write in the target's editor could flush stale text over an accepted change. But Accept is a click in the card, which blurs the editor. Blur flushes the pending write (BlockEditor.tsx:306-307), and that write is queued on the write lock ahead of the accept's transaction. v1 has no programmatic accept, so nothing else can accept while the target is open. An agent proposes changes; a person accepts them. An agent that should change text directly uses edit_block.
  • No anchor rewrite on accept. Closed suggestions are hidden and not highlighted. In "show closed", their card reads "replaced “quote” with “replacement”" directly from the properties.
  • Non-empty replacement. v1 requires the replacement to be non-empty, so telling an empty value from an absent one never decides whether a thread is a suggestion. To suggest a deletion, replace a slightly wider span (very large → large).
  • Attribution. The accepted text is attributed to whoever accepts it. The suggestion's own author stays on the thread.
  • Concurrent edits elsewhere. Another client editing the same block can still overwrite the accepted text with its next write. Ordinary content last-writer-wins applies, and the status stays accepted. This is accepted.
  • Not in scope. A "suggesting mode", where typing itself produces suggestions as in Google Docs, and suggestions spanning several blocks.

Queries and subscriptions

In the app

Slice 1 adds one new query. The rest are existing queries with arguments.

  • The pill count: the backlink batcher with the annotation:target edge field (see Comments and references), batched over the rendered blocks like the reference count.
  • One block's threads (inline expansion, highlights): core.typedBlockIds({types: ['annotation:thread'], referencedBy: {id, sourceField: 'annotation:target'}}), filtered by status.
  • One thread: the card renders the root through BlockComponent. Any non-UI read uses core.subtree({id, hidePropertyChildren: true}), with authors resolved through contributors.profilesByIds.
  • Every thread anchored under a scope is the one genuinely new read. Its consumers are agents, so it lands in slice 2. Scope is recursive. It covers threads anchored to blocks under the scope, and also threads anchored to the comments of those threads, such as quote-replies and annotations on a comment. Those live under Comments (km), not under the page, so a plain subtree walk would miss them. The typed query language can't express it, because its target operator matches the target's properties, not its ancestry (src/data/api/typedBlockQuery.ts).

For agents: tools

Slice 2 adds two km MCP tools, with matching bridge verbs. Both declare a blocked-wikilink policy, as every MCP write tool must (blockedWikilinks.ts).

  • comments({scope | block, includeClosed}) returns the threads. Each comes with its anchor state (exact, moved or stale), the quote, any replacement, an excerpt of the target, and the comments with author names and kinds.
  • add_comment({target, quote?, occurrence?, content?, replacement?}) creates a thread.
    • It computes the start and the context from the target's current content.
    • It refuses an ambiguous quote unless occurrence is given, and it refuses property-row targets.
    • With a replacement, the thread is a suggestion (slice 4).
    • It returns the root's id, which is what a ((T)) quote references.

Everything else already exists:

  • A reply is append_markdown({target: <thread root>}).
  • Resolving or reopening is update_block on annotation:status.

add_comment({target: "^3f2a9c1d", quote: "Thursday", replacement: "Thursday 9am",

For agents: being woken

There are two paths. Neither needs a new watcher kind.

  1. A mention inside a thread. [[claude]] can you check this? in a comment is a backlink to the watcher's target page, so today's backlinks watcher claims it and replies under it. That is a nested reply in the thread, with the existing per-mention semantics unchanged: claim, attempts, stale sweep, cancel, chips and session resume. Two changes:
    • Bookkeeping writes are unattributed.
      • Every agent:* write to the source goes through a client with contributorId: null, for which the contributors processor records nothing (processor.ts:113). In packages/agent-dispatch/src/graph.ts that is setTaskProps and clearCancel, plus setActivity and setSession, which the engine calls on every progress and session event (engine.ts:414,447).
      • The split: the daemon gets two graph handles. An unattributed one carries all bookkeeping. An attributed one exposes only createReply and reconcileReplyTree. A bookkeeping method added later then cannot end up attributed by accident.
      • The effect: today those writes list the agent as an editor of any block that mentions it. With the split, a person's comment, or note, keeps exactly the authors who wrote it, and the reply itself stays attributed to the agent.
    • Prompt context. When the mention sits inside a thread, the prompt builder adds the target block's content, the quote, the page path, and the chain from the thread root down to the mentioning comment, with authors. Without that, the agent would see only the container and the thread. A chain rather than the whole tree keeps the prompt bounded on long threads; siblings can be fetched on demand through the tools.
  2. Monitoring a scope without being mentioned is a query watcher running a comments recipe. That watcher already exists: it fires once per batch of new ids, sets a first-run baseline so old comments are not replayed, and keeps a seen-ids cursor that advances before the run, so it survives restarts and never re-bills a failed prompt. It already pushes through a watch-events sql watcher, whose fingerprint changes whenever a new id appears. The recipe, shipped in the guide's comments topic, selects comment ids in the scope that are:
    • visible descendants, at any depth, of open threads in the (recursive) scope;
    • non-empty, and last edited at least a quiet period ago, measured on coalesce(user_updated_at, updated_at).
      • Why: the query watcher fires on the first appearance of an id and advances its cursor before the run. Its push settle is only one second (QUERY_SETTLE_MS in push.ts). Without the condition, a reply caught on its first debounced write would be answered half-typed, and its finished version never seen.
      • The period: use the mention watcher's 15 seconds (quietMs), so both paths wait alike.
      • Latency: time passing changes no table, so the push watcher cannot see a comment go quiet. The poll sweep picks it up, which makes the latency the quiet period plus up to one poll interval.
    • not created by an agent or automation contributor, which is the loop guard, and also stops two agents on one scope from ping-ponging;
    • not mentioning a dispatch target page, so a [[claude]] comment is answered once, by the mention watcher.
    The run replies with append_markdown under the comment it is answering, as the agent's contributor, with the same root-to-comment chain as its context.

Tests

These follow the repo's testing rules.

  • Resolver:
    • the prepend, deleted-occurrence and merge cases above, each landing on the right occurrence or going stale;
    • moved versus exact;
    • an empty context;
    • non-ASCII text;
    • widening to whole reference spans.
  • Creation: an edit still waiting in the editor's debounce is anchored against what the editor shows, and a target changed under the user refuses with the draft kept.
  • Backlinks: for each of the two exclusions (the anchor edge, and content edges from a thread root), delete the clause and a named test fails on each route: batch count, batch list, filtered forBlock, grouped. Also, a highlight whose quote contains [[claude]] creates no dispatch task, while a comment with the same text does.
  • Merge: a merge run through the production processor order moves the thread, and the anchor resolves as moved.
  • Lifecycle: delete and restore the target; deleting the container is refused while it has live threads.
  • Accept:
    • refuses on stale, moved or deleted targets;
    • is one undo step;
    • refuses a duplicate of an applied suggestion, both mid-block and with the quote at the very start or the very end of the block, where the stored context is shorter than 16 characters or empty;
    • refuses, before writing, a change after which the anchor would still be exact (text that repeats around the quote), and a copy re-anchored onto applied text.
  • Nested threads:
    • the scope read returns a thread anchored to a comment of an in-scope thread;
    • deleting a comment with replies from its card keeps the replies;
    • navigating to a deep comment lands on the target with that comment in view.
  • Range references:
    • a ((T)) renders the live range, then the stored quote once stale;
    • deleting T leaves the quote as plain text in X;
    • copying the same range twice reuses one thread;
    • clicking the quote lands on B;
    • B's reference pill does not count X.
  • Dispatch: a full mention run (claim, activity events, session, completion, cancel) leaves the mentioning block's attribution untouched, while the reply is attributed to the agent. The recipe excludes agent-authored, empty and mentioning comments. It also excludes a comment edited within the quiet period, which is selected once it goes quiet, with its finished text.

Decisions

  1. Comments appear in search and recents. Decided 2026-10-28.
    • #332 hid threads from those surfaces instead, through an ancestor-based filter that each list of blocks routes through. That was rejected: it is a seam that every future list has to remember, and it leaks wherever one forgets it.
    • Showing them means a search for "fix the intro" finds the comment that says it, and a comment just written is one recents click away.
    • The accepted cost is agent replies in recents.
  2. Edit suggestions are in. Decided 2026-10-28, as slice 4.
  3. The container is Comments (km). The precedent is System Migrations (km). A kernel-page variant with no alias, which #332 proposed, would be new machinery for a cosmetic difference.
  4. A quote of B does not count in B's reference pill. Decided 2026-10-29.
    • X references the excerpt, and it shows up as an annotation on B's card. The two pills stay disjoint.
    • Counting it would take one more join in the backlinks sources owner, and would show X twice: once in B's backlinks and again on B's card.
  5. A thread with no comments shows as a highlight. Decided 2026-10-29, "for now".
    • The rejected alternative showed a thread only when something is attached to it: comments, quoters or a replacement. That would have made a copied-but-never-pasted range reference invisible.
    • Keeping highlights accepts that stray instead, as listed under Quoting part of a block.
    • Visibility stays behind one predicate, so switching later is a one-line change.
  6. Open: agents before the margin, or the margin first? The two slices are independent. My pick is agents first: the mention path needs only unattributed bookkeeping and prompt context, while the margin waits on the read-mode spike.

Compared with the earlier design (#332)

This design was drafted before reading #332.

Where they agree

  • Threads are blocks under a workspace container.
  • The anchor is stored as properties on the thread root, never as markers in the content.
  • Threads are found through a ref property and source_field.
  • Anchors resolve lazily, fall back to stale, and are never rewritten automatically.
  • Creation starts from an edit-mode selection.
  • Deleting the target orphans the thread, and restoring the target brings it back.
  • There is no synced annotations table.
  • Suggestions share the thread and anchor model.

Taken from #332

  • A metadata root with the comments as its children.
  • Prefix and suffix context in the anchor. This design first dropped them for a start hint alone, until a measured case showed the hint picking the wrong occurrence.
  • Flushing the debounced editor write before anchoring.
  • Re-validating an anchor inside the transaction that saves it.
  • Showing highlights only on primary surfaces.
  • A status enum that can widen.
  • An accept that re-resolves and refuses on mismatch, inside one transaction.

Where this one differs

  • Storage of the anchor. One ref target plus scalar text properties, instead of a refList mirror plus a JSON segments payload.
    • The generic merge retargeter rewrites ref-property values as well as their entries (mergeRetargetProcessor.ts:217-275, since 9d93fd9bfe8). So a block id that lives only in a ref property follows a merge with no help.
    • What the retargeter cannot see is a block id inside a JSON payload. That copy of the id is what forced #332's dedicated annotation merge processor, its mirror invariant, and the tests for both.
    • The cost: a comment spanning several blocks would need a new property, because changing ref to refList is a frozen codec change. But no model for selecting across blocks exists yet to need one.
  • No hiding seam. Comments are blocks, and search and recents show them. The only special case is the anchor edge in the backlink routes, and that has one owner in the backlinks plugin.
  • Exact versus moved. Writes require exact; moved highlights are shown and flagged. #332 had one "resolved" state, and rewrote the anchor on accept to detect an accepted suggestion that no longer applies. Here the exact rule refuses a second application up front, and closed suggestions need no highlight.
  • Simpler suggestions.
    • A replacement property, instead of a kind property plus a patch payload.
    • No programmatic accept in v1, so the editor question shrinks to "a click blurs and flushes first". #332 proposed dispatching into the mounted editor, or an awaited editor-commit API.
  • A lazy container through the existing getOrCreateKernelPage, with a deletion guard, instead of an eager systemPagesFacet ensure that writes a page into every workspace on open.
  • The quote is the root's content, not a property, so the reference processors keep it in step with the target, and a deleted quote leaves readable text behind.
  • Added: the side margin, authorship, agent tools and wake-ups through the existing watchers, mentions, and range references. #332's non-goal still holds: references themselves never carry ranges. A range reference is a plain reference to an anchor record.
