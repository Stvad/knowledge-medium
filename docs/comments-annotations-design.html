Comments and annotations

Comments, highlights and edit suggestions on notes, as blocks — 2026-10-28

What has to be true

  1. Comments and annotations are blocks in the workspace, with everything blocks get: sync, undo, search, references, hand-editing, E2EE.
  2. A separate side surface shows them beside the notes, and can be turned on and off.
  3. A comment can point at part of a block: select some text, comment on that.
  4. They sit sensibly next to references. A block already shows how many blocks reference it; comments are the adjacent idea, "what is being said about this block", and the UI shows the two side by side without counting one as the other.
  5. Something outside the UI (an agent) can subscribe to comments in a scope (a page, a subtree, one block), read them, and reply.
  6. Every comment shows who wrote it, human or agent.
  7. Edit suggestions ("replace this with that", accept or reject) fit the same model.

The idea in one picture

  • The target block is never written to. Everything about the annotation lives on the thread root.
  • A thread with no comments is a highlight; a thread with comments is a discussion; a thread with an annotation:replacement is an edit suggestion. They are all the same record.
  • The target's block id lives in exactly one place, the annotation:target ref. Everything else about the anchor is text.
  • Discovery runs through the references index: block_references rows with source_field = 'annotation:target'.
Explainer — block_references. A local, trigger-maintained index with one row per edge: (source_id, target_id, alias, source_field). Content references ([[Page]], ((id))) have an empty source_field. A ref-typed property projects a row whose source_field is the property name. It is indexed on (target_id, workspace_id), so "which threads point at B" is an index lookup. (src/plugins/references/localSchema.ts)

A comment, end to end

1Alex is editing block B, "We moved the launch to Thursday because the vendor slipped." They select Thursday, run Comment, and type "Is Thursday confirmed?".

2One transaction writes two blocks and nothing else:

Comments (km)
└─ (thread root)                 types: annotation:thread
     annotation:target    ((B))
     annotation:quote     Thursday
     annotation:quoteStart 23
     annotation:status    open
   └─ Is Thursday confirmed?     attribution:creators → Alex's profile

block_references:  (source = thread root, target = B, source_field = 'annotation:target')

3Later Alex rewrites B as "Because the vendor slipped, we moved the launch to Thursday." The text at offset 23 is no longer Thursday, so the resolver takes the occurrence nearest 23, which is at 51. The highlight follows the word. Nothing is written.

4An agent watching the page is woken. It reads the thread together with block B and replies "The vendor confirmed Thursday 9am." The reply is written as a new child of the thread root and attributed to the agent's contributor profile.

5The agent also suggests an edit: replace Thursday with Thursday 9am. That is a second thread with annotation:replacement = "Thursday 9am". Alex clicks Accept. One transaction rewrites B's text and sets that thread's status to accepted, and a single undo reverts both.

Data model

A thread is a metadata block, and its children are the comments

The thread root has empty content and holds the anchor and the status. Each comment is a child block, and a reply to a comment is a further child. So a thread is just an outline:

  • Enter at the end of a comment starts the next one.
  • A nested reply is an indented block.
  • [[links]], ((refs)) and formatting work inside comments, because a comment is not special in any way.

Putting the first comment's text on the root would save one block per thread. That is rejected for two reasons:

  • Attribution. Contributors attribute any meaningful write to the block it lands on (src/plugins/contributors/processor.ts:21-29). If the root were also the first comment, three kinds of write would list someone as an editor of that comment: resolving the thread, repairing its anchor, and an agent claiming it. With a separate root, those writes land on the metadata block. A comment's authors are then exactly the people who wrote it.
  • Uniform rendering. Every comment is a sibling under the root, so the side surface renders one list rather than "the root" plus "the rest".

Comment blocks carry no type: a comment is simply a visible descendant of a thread root. A second marker would be a second source of truth, and hand-typed replies would not carry it.

Where threads live

Threads live as children of one workspace kernel page, Comments (km), which getOrCreateKernelPage creates at the first comment. The alias is deliberately ugly, as with System Migrations (km). Aliases are unique per workspace, so a plain Comments alias would make comment creation abort in any workspace where the user already has a page of that name.

Where a thread lives is incidental, because the ref is what makes it a thread. A thread root that someone moves elsewhere by hand still works, since discovery never looks at the container.

The anchor

  • annotation:quote is a substring of the target's raw markdown. That is the same text an agent reads through the API, so an agent can annotate a range just by quoting it, and edit mode can decorate the range without any translation.
  • annotation:quoteStart records where the quote began when it was made. It is used only to choose between repeated occurrences.
  • No quote means the thread annotates the whole block.
  • A quote never splits a reference span ([[…]], ((…)), [label](((…)))). Creation widens the selection to cover whole spans, so the reference plugins always see complete spans inside a highlight.

On a workspace that stores properties as child blocks, each property becomes a field row under the root, and visibleChildrenOf already hides those. Every "descendants of a thread" query therefore uses the visible subtree (VISIBLE_SUBTREE_SQL), so field rows are never taken for comments.

A blockContentRendererFacet contribution renders the empty root as "comment on ⟨target excerpt⟩ · “quote”" wherever the root itself appears, for example on the container page or in a block ref.

Anchoring against changing text

Resolution is a pure, synchronous function of (content, quote, quoteStart). It is recomputed at render time and never persisted.

  1. No quote: anchor the whole block.
  2. Offset check: if content.slice(quoteStart, quoteStart + quote.length) === quote, anchor there.
  3. Nearest occurrence: otherwise, anchor at the occurrence of quote nearest quoteStart.
  4. No occurrence: stale. The thread stays on the block, and its card shows the original quote marked as changed. The user can select new text to re-anchor, or anchor the thread to the whole block.
Repeated text. The block was Ship the fix, then test the fix. and the second the fix was quoted at quoteStart = 24. Then someone edits the block:
•Please ship the fix, then test the fix.
The offset check fails, because the text at 24 is now en test. There are two occurrences, at 12 and at 31. 31 is nearer to 24, so the anchor stays on the second one, which is the one quoted.

Why the start hint, and not prefix and suffix context? Repeated occurrences are settled by whichever is nearest the hint. Blocks are short (on a large real graph they average under 100 characters), so ties are rare. Each extra property also costs two more rows on a children-stored workspace. Fuzzy matching, for small edits inside the quote, can be added later inside step 3 without changing storage.

Re-anchoring is an explicit user action, done in one transaction. Inside that transaction it re-finds the confirmed text in the content as of that transaction and computes the offsets from that same snapshot. If the text no longer matches, the transaction refuses, rather than storing whatever now sits at the old offsets.

Comments never write the target row, so commenting cannot conflict with someone editing the note. The one exception, deliberately, is accepting a suggestion (see Edit suggestions).

Comments and references

The anchor is a real reference: annotation:target projects into block_references like any ref property. That is what makes discovery cheap. It also means that, as things stand, a comment would be counted and listed as a backlink.

•We moved the launch to Thursday because the vendor slipped.2💬 1
  • Two pills, with counts that never overlap. The gutter shows references, then open threads.
    • Clicking the reference pill expands backlinks under the block, as it does now.
    • Clicking the comment pill focuses the block's threads in the margin. When the margin is off, it expands them inline under the block, using the same footer mechanism as the backlinks expansion.
  • One exclusion, owned by the backlinks plugin. The backlinks plugin declares a facet listing edge fields that have their own surface. The pill count, the inline expansion and Linked References (flat and grouped) all skip those fields, in sourceBatch.ts and the grouped query. annotation:target is the first entry. The attribution:* edges on contributor pages are the obvious second candidate. Changing those is out of scope here, but the same rule applies to them.
  • References inside a comment are ordinary mentions. A comment saying "see [[Paper X]]" shows up in Paper X's backlinks, with a breadcrumb through the container and the thread. That is correct: the comment does mention Paper X.
  • Mentions reach agents. A comment containing a dispatch watcher's target page ([[claude]]) is a backlink to that page, so the existing backlinks watcher fires (see Agents).

Later, the margin could also show a block's plain backlinks as "mentions" beside its threads. A note elsewhere that references this block is commentary that happens to live somewhere else. That would be a display toggle on top of this model, not part of it.

UI

Highlights

  • Edit mode. A CodeMirror extension, added through codeMirrorExtensionsFacet, turns resolved ranges into mark decorations. The offsets are exact, because the quote is raw content. Suggestions get a distinct style.
  • Read mode. A remark plugin, ordered before the reference plugins, splits positioned text nodes at the range boundaries and wraps the pieces in an annotation-mark node.
    • The risk is ordering: text slices that other plugins split out lose their positions, as src/markdown/blockSeparators.ts notes.
    • Spike this first. If it can't be made exact, read mode shows the pill but no inline highlight.
  • Where highlights render. Inline highlights appear only in a panel's primary outline and in the focused editor. Nested surfaces show none: backlinks, embeds, block refs and breadcrumbs. The comment pill follows the reference pill's rule (inline-counts/applies.ts).

The side margin

  • Toggle. The margin is per panel. It is switched by the action annotations.toggleMargin or a header item. The flag is stored on the panel's UI-state block, so it survives a reload.
  • Layout. A blockLayoutFacet contribution on the panel's top-level block adds the right column inside the same scroll container, so the cards scroll with the text.
  • Placement. Each card goes at the measured top of its target's row in that panel's primary render scope. The order is by target position, then by quote start. A card's top is its anchor's height or just below the previous card, whichever is lower.
  • Collapsed blocks. Threads anchored inside a collapsed subtree are shown as a single stub on the nearest rendered ancestor.
  • The card. A card renders the thread root through BlockComponent in a nested surface, so its comments are normal editable blocks. The header shows the quote ("whole block" when there is none), a stale badge, and Resolve. Suggestion cards also show the diff, with Accept and Reject. The footer has Reply.
  • Closed threads (resolved, accepted or rejected) are hidden behind "show closed".
  • Narrow panels and mobile have no margin. There, the comment pill expands the threads inline under the block.
  • "All comments" is an action that opens the container page, where the thread renderer shows each target. A filtered query view (open threads, by author, by scope) comes later.

Creating, replying, resolving

Comment on a selection

The action is annotations.commentOnSelection, in the edit-mode context. Its default binding is chosen against the shortcut-conflict check. It has an icon, so it also appears in the mobile keyboard toolbar.

  1. Call flushEditorContent(view). The stored row lags the editor by its debounce, and the anchor must be checked against what the user sees.
  2. Read the selection and widen it to whole reference spans.
  3. Open a composer, in the margin or inline. The draft lives in UI state and is written only on submit, so an abandoned comment leaves no empty thread behind.
  4. Ensure the container exists, before the transaction.
  5. On submit, run one repo.tx. It creates the root with createTypedChild, passing its references, then the first comment. Inside that transaction it re-checks that the quote still sits at its offsets, falling back to the nearest occurrence.

Other gestures

  • Block-level comment: the same action in normal mode, or the bullet context menu.
  • Highlight: the same flow without the composer, giving a thread with no comments.
  • Suggest edit: the composer opens with a replacement field prefilled with the selected text, plus an optional comment (see Edit suggestions).
  • Reply: creates an empty child of the root and focuses it. From there it is ordinary block editing.
  • Resolve and reopen: set annotation:status.
  • Delete:
    • Deleting a thread deletes the root's subtree.
    • Deleting the last comment from its card also deletes the thread. That is a UI rule only.
    • A root with no comments that arises any other way (sync, an agent, hand-editing) is simply a highlight, which is a valid state.

Not in v1

  • Commenting on a read-mode selection. It needs a mapping from the DOM selection to raw offsets, and none exists. It also needs a guard so that a drag-select does not end in the click that enters edit mode (plain-outliner/clickToEditAction.ts). That guard would decorate the action through the action-dispatch seam, the way vim-normal-mode does.
  • A selection spanning several blocks. One thread has one target.

Authorship

  • Author: the comment's first attribution:creators entry, resolved to its contributor profile. The name is the profile's content, and the kind (human, agent or automation) is shown as a glyph.
  • Time: relative, taken from created_at.
  • "Edited": shown when the comment has editors other than its creator.

Not created_by. Bridge and MCP writes run inside the tab and stamp the tab's human user id, so an agent's comment would show as the person's.

Nothing in the app has avatars or per-user colours yet, so the chip is initials plus the kind glyph.

Edit suggestions

A suggestion is a thread whose root carries annotation:replacement: "replace the quoted text with this". Everything else is shared with comments: the anchor, the resolver, the card, the discussion underneath, and the agent tools. The additions are one property, two status values, and one accept transaction.

Suggested edit
We moved the launch to ThursdayThursday 9am

AcceptRejectReply

Accept is one transaction, so it is one undo step:

  1. Re-resolve the anchor against the target's content as of this transaction.
  2. Require quote to sit exactly at the resolved range. If it is stale, refuse with "the text changed since this was suggested". Never apply a blind replacement.
  3. Splice replacement into the content, and set annotation:status = accepted.

Reject only sets rejected.

  • The editor guard. If the target is open in an editor on this client, a pending debounced write could later flush stale text over the accepted change.
    • A click on the card already blurs the editor, and blurring flushes it. Accept then runs after that.
    • A programmatic accept (an agent tool) refuses while the target is being edited on this client. The refusal is checked before anything is dispatched, as the gesture-guard checklist requires.
  • No anchor rewrite on accept. Accepted and rejected threads are closed and hidden. Their card in "show closed" reads "replaced “quote” with “replacement”" directly from the properties. #332 rewrote the anchor to the inserted text, so it could flag an accepted suggestion that no longer applies. That is declined: a closed suggestion needs no highlight.
  • Non-empty replacement. v1 requires the replacement to be non-empty, so telling an empty value from an absent one never decides whether a thread is a suggestion. To suggest a deletion, replace a slightly wider span (very large → large).
  • Attribution. The accepted text is attributed to whoever accepts it. The suggestion's own author stays on the thread.
  • Concurrent edits elsewhere. Another client editing the same block can still overwrite the accepted text with its next write. Ordinary content last-writer-wins applies, and the status stays accepted. This is accepted.
  • Not in scope. A "suggesting mode", where typing itself produces suggestions as in Google Docs, and suggestions spanning several blocks.

Queries and subscriptions

In the app

These are defineQuery handles, read with useHandle.

  • annotations.threadsForBlocks({workspaceId, ids, includeClosed}) returns thread roots grouped by target. It is batched over the rendered blocks the way the backlink count is, and it drives the pills, the highlights and the margin.
  • annotations.threadsInScope({workspaceId, rootId, includeClosed}) returns every thread anchored to a block under a scope: 
    WITH RECURSIVE scope(id) AS ( -- VISIBLE_SUBTREE_SQL from :rootId, rootId included
  ...
)
SELECT br.source_id AS thread_id, br.target_id
  FROM scope s
  JOIN block_references br ON br.target_id = s.id
                          AND br.workspace_id = :ws
                          AND br.source_field = 'annotation:target'
  JOIN block_types bt      ON bt.block_id = br.source_id AND bt.type = 'annotation:thread'
  JOIN blocks t            ON t.id = br.source_id AND t.deleted = 0
  • annotations.thread({id}) returns the root, its visible descendants, and their attribution.

The typed query language cannot express "the target lies under X". Its target operator matches the target's properties, not its ancestry (src/data/api/typedBlockQuery.ts). So scope gets a dedicated query rather than an extension of the compiler.

For agents: tools

These are km MCP tools, with matching bridge verbs.

  • comments({scope | block, includeClosed}) returns the threads. Each comes with its resolved or stale anchor, the quote, any replacement, an excerpt of the target, and the comments with author names and kinds.
  • add_comment({target, quote?, occurrence?, content}) creates a thread.
  • suggest_edit({target, quote, occurrence?, replacement, comment?}) creates a suggestion.
  • reply_comment({thread, content}) adds a comment to a thread.
  • set_comment_status({thread, status}) changes a thread's status. accepted runs the same accept transaction as the UI, guard included.
// an agent reviewing a page proposes a change
suggest_edit({target: "^3f2a9c1d", quote: "Thursday", replacement: "Thursday 9am",
              comment: "Matches the vendor's email."})

Writes go through the bridge, so contributor attribution records the agent automatically. Writing an anchor correctly is exactly what a dedicated tool should own: the exact raw substring, widened to whole reference spans, with the start hint. The agent-facing guide gets a comments topic.

For agents: being woken

There are two wake paths. Both follow one rule: a dispatch task that starts inside a thread is hosted on the thread root. The claim, session and completion state (agent:status, agent:session and the rest) are written to the root, and the reply becomes a child of the root.

The rule matters because today's engine writes all of that state to the source block (packages/agent-dispatch/src/engine.ts, the setTaskProps(sourceId, …) calls). agent:* properties are BlockDefault, and the attribution processor counts them as meaningful edits. A claim written onto a person's comment would therefore list the agent as one of its editors.

So the engine resolves a task host once: the nearest thread-root ancestor of the source, or the source itself. Every state write and reply then goes through that host. Session resume needs no change, because it already looks for the nearest ancestor agent:session, and that is now the root.

  1. A mention inside a thread. [[claude]] can you check this? in a comment is a backlink to the watcher's target page, so today's backlinks watcher picks it up.
    • The source's own agent:status can no longer say whether it was handled. Inside a thread, the mention is pending when it was edited after the root's last completed run.
    • The prompt builder adds the anchor context: the target block's content, the quote, the page path, and the thread so far with its authors. Without that, the agent would see only the container and the thread.
  2. A comments watcher kind, for monitoring a scope without being mentioned. It is configured as {kind: 'comments', name, scope: <page alias or block id>, quietMs}.
    • Pending means an open thread in scope whose latest comment is by someone other than the watcher's contributor and was written after the baseline. This is derived from the graph on every tick, so it needs no cursor and it survives restarts.
    • Detection is pushed through a watch-events sql watcher running the scope query. The poll stays as the backstop, as it does for the other watchers.

Tests

These follow the repo's testing rules.

  • Resolver: unchanged text, shifted text, repeated text, missing text, non-ASCII text, and widening to whole reference spans.
  • Flush before anchoring: an edit still waiting in the editor's debounce is anchored against what the editor shows, not against the stale row.
  • Backlinks exclusion: delete the clause, and a named count test and a named list test both fail.
  • Merge: a merge run through the production processor order moves the thread.
  • Target deletion: delete and restore the target.
  • Accept:
    • refuses when the quote is stale;
    • is one undo step;
    • refuses while the target is being edited on this client;
    • does not apply when the quote occurs elsewhere but not at the resolved range.
  • Dispatch:
    • the agent's own reply clears pending;
    • a mention inside a thread claims the root;
    • no claim makes the agent an editor of a person's comment;
    • a resumed mention finds the root's session.

Decisions

  1. Comments appear in search and recents. Decided 2026-10-28.
    • #332 hid threads from those surfaces instead, through an ancestor-based filter that each list of blocks routes through. That was rejected: it is a seam that every future list has to remember, and it leaks wherever one forgets it.
    • Showing them means a search for "fix the intro" finds the comment that says it, and a comment just written is one recents click away.
    • The accepted cost is agent replies in recents.
  2. Edit suggestions are in. Decided 2026-10-28. They are slice 4, and their data model ships with slice 1.
  3. Open: agents before the margin, or the margin first? The two slices are independent. My pick is agents first: the mention path needs little beyond the task-host rule and prompt context, while the margin waits on the read-mode spike.
  4. Open: the container alias. Comments (km) is unique but visible and ugly. The alternative, which #332 proposed, is a kernel-page variant with no alias. That is cleaner, but it is one more page mechanism to keep. My pick is the alias.

Compared with the earlier design (#332)

This design was drafted before reading #332.

Where they agree

  • Threads are blocks under a workspace container.
  • The anchor is stored as properties on the thread root, never as markers in the content.
  • Threads are found through a ref property and source_field.
  • Anchors resolve lazily, fall back to stale, and are never rewritten automatically.
  • Creation starts from an edit-mode selection.
  • Deleting the target orphans the thread, and restoring the target brings it back.
  • There is no synced annotations table.
  • Suggestions share the thread and anchor model.

Taken from #332

  • A metadata root with the comments as its children. This design first had the root double as the first comment. Attribution settled it.
  • Flushing the debounced editor write before anchoring.
  • Re-validating an anchor inside the transaction that saves it.
  • Showing highlights only on primary surfaces.
  • A status enum that can widen.
  • A container alias that cannot collide.
  • A suggestion accept that re-resolves and refuses on mismatch, inside one transaction.

Where this one differs

  • Storage of the anchor. One ref target plus scalar quote properties, instead of a refList mirror plus a JSON segments payload.
    • The generic merge retargeter rewrites ref-property values as well as their entries (mergeRetargetProcessor.ts:217-275, since 9d93fd9bfe8). So a block id that lives only in a ref property follows a merge with no help.
    • What the retargeter cannot see is a block id inside a JSON payload. That copy of the id is what forced #332's dedicated annotation merge processor, its mirror invariant, and the tests for both.
    • The cost: a comment spanning several blocks would need a new property, because changing ref to refList is a frozen codec change. But no model for selecting across blocks exists yet to need one.
  • No hiding seam. Comments are blocks, and search and recents show them (decision 1). The only special case is the anchor edge in the generic backlink surfaces, and that is one exclusion owned by the backlinks plugin.
