# Subtree sharing in the E2EE world — design options

> **Status:** design options — nothing here is shipped. Written 2026-06-24; **last verified against code 2026-08-19** (master `84501f6a`) — §1 records what changed since the original, §11 what was verified. This doc layers the **key-access plane** on top of [`subtree-sharing.md`](subtree-sharing.md)'s **access-control plane** (Plane 1) and revises the parts of that design that assumed a plaintext-reading server. Where the two disagree, prefer this doc for anything touching encryption or property storage, and the old doc for the RLS / `effective_share_ids` mechanics it still owns.

---

## 0. TL;DR

- **Sharing splits into two independent planes.** *Access control* — "which ciphertext rows may a recipient fetch" — is crypto-agnostic, and the old `subtree-sharing.md` *schema and sync-stream mechanics* carry over essentially unchanged (its RLS **structure** carries over too, but the `blocks_read` predicate must be *revised* to a membership-OR-share **union** — §3.1). *Key access* — "can the recipient decrypt those rows" — is the genuinely new problem and the only thing e2ee changes. Keeping these planes separate is the central idea of this doc. (Note: the access-control *mechanics* survive, but several server-plaintext *features* built on them — the snapshot RPC, server-rendered reference labels, anonymous read-only links — do **not** survive e2ee; see §4.)
- **The crux is a granularity conflict.** E2EE today is **one symmetric Workspace Key (WK) per workspace** ([`src/sync/transform.ts`](../src/sync/transform.ts), [`src/sync/keys/`](../src/sync/keys/)). Sharing wants **per-subtree** confidentiality. A single key cannot, by itself, express "you may read this subtree but not its siblings." Everything below is a way to resolve that conflict, each with a different cost.
- **The fetch boundary is RLS, not the sync stream.** `public.blocks` is reachable by direct PostgREST `SELECT` (`GRANT ALL … TO anon, authenticated`), and the *shipped* `blocks_read` policy is member-only with **no subtree predicate**. So a workspace member can already fetch every block in the workspace; the PowerSync stream (one auto-subscribed `workspace_data` stream, parameterized by membership) only narrows what *auto-syncs*. This single fact determines what handing over a key actually exposes (§3).
- **A whole-workspace e2ee share already ships.** Per [`shareWorkspace.test.ts`](../src/sync/keys/flows/shareWorkspace.test.ts), sharing an encrypted workspace with another *workspace member* needs no new crypto: invite (plaintext membership metadata) + send the WK out of band + unlock via the existing key-required gate — the workspace-scoped verification canary means an owner-minted WK validates for a different user (mechanism details: §11). Subtree sharing is the question of going **finer** than whole-workspace.
- **Properties are becoming blocks, and that changes what a subtree share carries.** On a flipped workspace (`workspaces.properties_migration` at-or-past `'children'`) each property is a **field row + value row(s)** — ordinary synced blocks under the owning block — so property values ride along with a shared subtree *by construction*. The **definitions** they point at do not: they live under root-level system pages outside every user subtree (§8.2). E2EE workspaces are server-pinned to cell-mode for now, so nothing changes for them yet (§1 item 4).
- **Recommendation (§7): a phased hybrid that does not over-promise.** Ship the crypto-agnostic access-control plane; plaintext workspaces get the full old design. On **e2ee** workspaces v1 offers only honest paths: **(D)** export-to-plaintext for read-only/public/anonymous links (deliberate declassification), the *already-shipped whole-workspace share* as the add-collaborator affordance, and a **manual second e2ee workspace (E)** when a collaborator must be confined to a confidential subtree. Option B ships in **no** form (it implies a confidentiality wall that does not exist — §3.1), and confidential subtree sharing (**C**) — the marquee capability — is deferred as the stated product bet (§7): an encryption-core project whose key *delivery* does not hinge on the e2ee doc's §13 hierarchy (§6.F). Until C ships, the only anonymous e2ee "share" is D, which gives up encryption for that copy.

## 1. What changed since `subtree-sharing.md`

`subtree-sharing.md` (2026-04-27) predates four things:

1. **E2EE shipped and is live in production** ([`e2ee-deploy.md`](e2ee-deploy.md)). It is real code, not a sketch:
   - The wire seam [`src/sync/transform.ts`](../src/sync/transform.ts) seals three columns — `content`, `properties_json`, `references_json` (`CONTENT_COLUMNS`) — independently with AES-256-GCM under a per-workspace key, keyed by a pluggable `getCek(workspaceId)` (`encodeForWire` / `decodeFromWire`). Ids and `workspace_id` stay in clear (`WireBlockColumns`); `parent_id`, `order_key`, and timestamps pass through untouched as extra columns — only the three content columns are sealed.
   - A server-side trigger `blocks_require_ciphertext_for_e2ee` ([`supabase/migrations/20260529120000_add_e2ee_workspace_columns.sql:201`](../supabase/migrations/20260529120000_add_e2ee_workspace_columns.sql)) *rejects* any plaintext write to an e2ee workspace's content columns — so the server provably never holds plaintext for those rows.
   - Per-column AAD binds `[block_id, workspace_id, column_name, schema_version]` ([`src/sync/crypto/aad.ts`](../src/sync/crypto/aad.ts)) — note it binds the **block id**, not merely the workspace, and (re-verified) still has **no key-domain field**; this matters for Option C (§6.C).
   - Authority over a workspace's mode is a durable, locally-immutable **mode pin** ([`src/sync/keys/modePin.ts`](../src/sync/keys/modePin.ts)), keyed per `(user, workspace)` and set the moment a pasted WK validates against the workspace-scoped `wk_canary` ([`src/sync/crypto/canary.ts`](../src/sync/crypto/canary.ts)). The entry decision now flows through a dedicated seam, [`resolveWorkspaceEntry.ts`](../src/sync/keys/resolveWorkspaceEntry.ts) → [`decideWorkspaceEntry`](../src/sync/keys/workspaceAccess.ts).
   - The whole design is **per-workspace, opt-in, one shared symmetric WK, no asymmetric crypto, no per-recipient wrapping** in v1. A passphrase/X25519 key hierarchy with per-member wrapping is explicitly deferred to e2ee §13, and none of it exists in code — nor does WK rotation.

2. **Media shipped — and its facts are now verified against code**, superseding the June draft's design-doc-sourced description. An asset is content-addressed at `<workspace_id>/<content_key>` ([`storagePaths.ts`](../src/plugins/attachments/storagePaths.ts)); on an **e2ee** workspace `content_key = hex(HMAC(K_id, sha256(plaintext)))` with `K_id = HKDF(WK, 'km/asset-content-key/v1')` ([`contentKey.ts`](../src/sync/crypto/contentKey.ts)) and the bytes are sealed `encb:v1:` (AES-256-GCM, [`binaryEnvelope.ts`](../src/sync/crypto/binaryEnvelope.ts) / [`byteTransform.ts`](../src/sync/byteTransform.ts)); on a **plaintext** workspace the path is raw `hex(sha256(plaintext))` and the bytes upload **unencrypted** (the June draft implied the keyed path was universal — it is e2ee-only). Storage RLS gates on the path's first segment (= `workspace_id`): read = member, insert/delete = writer, no UPDATE policy at all ([`20260625000000_add_attachments_storage.sql`](../supabase/migrations/20260625000000_add_attachments_storage.sql)). Dedup is per-workspace (the media block id is `uuidv5(workspaceId:content_key)`). The design's earmarked subtree-sharing hooks — an `effective_share_ids` storage-RLS branch and a `content_key → block` mapping — remain **unbuilt**, as does the export-to-plaintext / key-in-fragment public-share phase (both still vNext rows in `docs/media-attachments/design.html`). Encrypted subtree sharing stays an explicit non-goal there; the *rationale* ("needs the key hierarchy") is superseded by §6.F's decoupling — the deferral itself stands, on C's Axis-1 cost.

3. **Sharing itself never shipped.** The old design is design-only: there are **no** `block_shares` / `effective_share_ids` / `block_share_members` / `share_links` / `share_link_secrets` objects, no `get_shared_subtree` or `resolve_block_link_stubs` RPCs, and no `shared_blocks` stream — all absent from the migrations and `src/` (§11). So we are free to design the key-access plane *before* committing the access-control plane to schema, and to make the two planes fit each other.

4. **Properties are migrating from a JSON cell to child blocks** (PR #288, [`properties-as-blocks-migration.html`](properties-as-blocks-migration.html); machinery live on master since 2026-08-18). What a sharing design needs from it:
   - **Shape.** On a flipped workspace a property is a **field row** — an ordinary block child of the owner whose content is `::((fieldId))`, a marker plus an exact ref to the property-*definition* block — with the value(s) as the field row's own child block(s); a ref-typed value child's content is `((target-id))`. Field/value rows are normal rows in `blocks`: synced, sealed like any content when the workspace is e2ee, and dual-written alongside the cell (which stays the synchronous read surface) — so a recipient receives *both* representations ([`txEngine.ts`](../src/data/internals/txEngine.ts), [`propertyChildrenProcessor.ts`](../src/data/internals/propertyChildrenProcessor.ts)).
   - **Recognition is local.** `reference_target_id` and `is_field_form` are **local derived columns, never synced** ([`blockSchema.ts`](../src/data/blockSchema.ts) `BLOCK_LOCAL_COLUMNS`) — kept local *specifically* so field-ness and edge metadata never cross the wire in plaintext (props doc §8).
   - **The lever is per-workspace, operator-only, forward-only** — `workspaces.properties_migration` (`'cell' → 'children' → 'cell-off'`), synced to every client, trigger-guarded ([`20260716120000`](../supabase/migrations/20260716120000_add_workspaces_properties_migration.sql)) — and **e2ee workspaces are barred from flipping** until client-side flip tooling exists (props doc §8 "option 2"): on e2ee workspaces properties stay in the sealed `properties_json` cell, so this doc's e2ee analysis is unaffected by the migration *today*.
   - **The migration itself is graph-scoped operator machinery** — a chunked backfill coordinated by a synced, deliberately un-arbitrated claim under a root-level system page, gated on a settled sync view ([`propertyCellBackfill.ts`](../src/data/internals/propertyCellBackfill.ts), [`graphBackfillClaim.ts`](../src/data/internals/graphBackfillClaim.ts)); §8.3 develops why that whole class of machinery must refuse share-scoped devices.

The old doc's own framing — "RLS at Postgres + sync-rule enforcement at PowerSync are the actual security boundary; the client enforces only UX" (G4) — is exactly the assumption e2ee revokes. Under e2ee the server boundary is **not** trusted with confidentiality; that is the whole point. A design that leans on RLS for confidentiality is fine for plaintext and insufficient for e2ee. This doc is about closing that gap.

## 2. The two planes

Keeping these apart is what makes the rest tractable.

### Plane 1 — Access control (which rows a recipient may fetch)

This is the machinery `subtree-sharing.md` designs: `blocks.effective_share_ids text[]` (trigger-maintained, walking `parent_id` only — no content read), RLS on `blocks` unioning workspace membership with share membership, a `shared_blocks` PowerSync stream, and the `block_shares` / `block_share_members` / `share_links` / `share_link_secrets` tables.

**None of this reads block content.** It operates on ids, the tree shape (`parent_id`), and membership tables — all plaintext metadata in *both* plaintext and e2ee workspaces (e2ee seals only the three content columns; see `WireBlockColumns`). So the *mechanics* of access control work identically for e2ee and plaintext. The properties-as-blocks shape even helps here: field/value rows are ordinary `parent_id` descendants, so the `effective_share_ids` walk covers a block's properties with no special case.

But "works identically" is a statement about the *plumbing*, not about confidentiality. Two caveats the rest of the doc develops:

- **It is RLS — not the sync stream — that bounds what a key-holder can read** (§3.1): any "you only get the subtree" claim must hold against arbitrary PostgREST `SELECT`s, not just against the auto-sync stream.
- **The plumbing ships plaintext metadata** — tree shape, timestamps, author user-ids, and the `effective_share_ids` array — to both the recipient and the server. That metadata leakage is real and Option C does **not** close it (§8.6).

### Plane 2 — Key access (can the recipient decrypt the rows they fetched)

For a **plaintext** workspace there is no Plane 2; the rows are readable, and the old design is complete. For an **e2ee** workspace the recipient holds ciphertext they cannot read and needs *a key*. The only key that exists is the per-workspace WK. The entire design space below is "what key does the recipient get, and how," trading confidentiality granularity against complexity.

A consequence to bank now: **a share token conveys access, not a key.** Under e2ee, redeeming a link grants a `block_share_members` row and syncs ciphertext, but delivers no decryption material — so the old token-credential model is, by itself, inert for e2ee (§4).

## 3. The crux: per-workspace key vs per-subtree share

A single symmetric WK per workspace cannot, on its own, encode "may read subtree T but not its siblings." Whatever key decrypts T's rows decrypts every row sealed under the same key — and today every row in the workspace is sealed under the same WK. So there are only three structural ways out:

1. **Hand over the one key, and rely on a *non-cryptographic* boundary (RLS) to scope the recipient to the subtree.** → Option B.
2. **Give the shared subtree its own key**, so the key you hand over only opens the subtree — a *second encryption domain*. → Option C (and, manually, Option E).
3. **Don't hand over a key; produce a plaintext copy** at share time, governed by Plane 1 alone. → Option D (and trivially Option A for whole plaintext workspaces).

### 3.1 What "rely on RLS" actually buys — grounded in the shipped boundary

Every reviewer will probe this, so be exact. The fetch boundary is the `blocks_read` RLS predicate evaluated on direct PostgREST access, **not** the PowerSync stream. Two shipped facts set the stage:

- The recipient role can issue arbitrary `SELECT * FROM blocks` over PostgREST (`GRANT ALL … TO anon, authenticated`).
- The shipped `blocks_read` is **member-only** and narrows nothing to a subtree. The *revised* policy that subtree sharing must install (old §6.1) is a union: `is_workspace_member(...) OR <share covers this row for me>`.

So the guarantee depends entirely on **whether the recipient matches the member disjunct**:

| Adversary | What they can decrypt |
|---|---|
| **Share-member-only** recipient (not a `workspace_members` row) + **honest** server enforcing the *revised, union* `blocks_read` | **Only the shared subtree.** The member disjunct is false for them; the share disjunct matches only covered rows; even a direct `SELECT *` returns just those rows, and the WK opens only those. |
| Recipient who **is** a `workspace_members` row (e.g. B implemented by reusing the workspace-share invite→accept chain) + **honest** server | **The entire workspace.** The member disjunct is true → RLS returns every row → the WK opens all of it. Subtree scoping is *vacuous*. |
| Any WK-holder + **dishonest / compromised** server, or an RLS bug/regression | **The entire workspace.** The server holds all ciphertext; the recipient holds the master key; together they reconstruct everything. |

Three conclusions fall out, and the doc must carry all three loudly:

1. **Option B is only honest if the recipient is a pure share-member, never a workspace member.** It therefore **cannot** reuse the shipped whole-workspace share flow verbatim (that adds a `workspace_members` row → row 2). It needs a share-grant-only membership plus separate WK delivery, and the *revised* union `blocks_read` must be installed first (the shipped member-only policy gives row 2 unconditionally).
2. **Even done correctly, handing over the WK delegates the confidentiality of the *whole workspace* to RLS** — the very server-enforced boundary e2ee was adopted to remove (row 3). That does not make B useless; it makes it **not a confidential subtree share**. It is "give someone the workspace master key plus a row-filter scoping them, in normal operation, to a subtree." Appropriate for a recipient you'd trust with the whole workspace anyway; wrong as "share one page with a stranger without exposing my graph."
3. **"A workspace member whose sync view is narrowed" is the wrong mental model for B** and must not appear: sync-view narrowing is a PowerSync convenience, not an authorization boundary. The authorization boundary is RLS, and a *member* passes it for everything.

**The member-only shape is not unique to `blocks`, and the old design revises only part of it.** Old §6.1 replaces `blocks_read` **and** `blocks_write` with the union policies — the write side matters because `blocks_write` is workspace-writer-only and both write RPCs are `SECURITY INVOKER`, so an RW share recipient's edits land only once that union is installed. But `workspaces_read` and `workspace_members_read` have the identical member-only predicate and the `workspace_data` stream is parameterized by membership, and the old design touches none of them. A share-grant-only recipient never sees a roster (good — §8.6 wants exactly that) but also never receives the **`workspaces` row** — and on e2ee that row is where `encryption_mode` and `wk_canary` live, which the entry path reads from the *synced local row* ([`resolveWorkspaceEntry.ts`](../src/sync/keys/resolveWorkspaceEntry.ts) waits for it to replicate before it can gate or unlock anything). So without a share-scoped projection of the workspace row (mode + canary at minimum) and a share parameterization of the stream, conclusion 1's recipient — the only honest B recipient — **cannot bootstrap an e2ee share at all**. This gates B and C-in-place alike, and belongs in Plane 1 next to the union policies.

## 4. What the old design loses on an e2ee workspace

Several mechanisms in `subtree-sharing.md` assume the server can read content, or that a token is a sufficient credential. They are fine on plaintext workspaces and **must be disabled or rerouted on e2ee workspaces**:

- **old §3.3 / old §8.4 read-only snapshot RPC `get_shared_subtree(token)`** returns `{ blocks: [BlockData…] }` server-assembled. On e2ee the content columns are `enc:v1:` ciphertext, so a `SECURITY DEFINER` function returns only ciphertext — and worse, it returns *ciphertext sitting in the plaintext-typed `BlockData` fields*, which a naïve client would render as content. It must therefore be **hard-disabled** on e2ee, not merely "rerouted." Anonymous read-only e2ee sharing cannot go through it (replacement: Option D export, or Option C key-in-fragment).
- **old §8.6 reference-stub RPC `resolve_block_link_stubs(ids)`** returns `content_label` (leading text) for blocks the viewer can't fully access. On e2ee the server cannot produce a label — the content is ciphertext. Cross-scope labels must come from the *client*, and only for blocks the client can decrypt; references to rows the recipient never received render **id-only / "no access," no human-readable label** (§8.2).
- **old §3.3 / §3.7 ("`link_token` is a credential") link-token model is inert for e2ee.** The old RW link path (redeem token → anon sign-in → `block_share_members` row → `shared_blocks` stream) delivers *access* but **no key**. On an e2ee workspace a guest who redeems a link syncs ciphertext and then stalls at the key-required gate with nothing to decrypt and nothing to edit (an editor write must produce a valid `enc:v1:` envelope, which needs the key). **So link tokens are access-plane-only and convey no key; the token-row model is foreclosed for e2ee link sharing.** E2EE links require key-in-fragment (C) or export (D); see §8.8 for the anonymous-user consequence.
- **old §3.3 / old §9.5 anonymous link-snapshot render** (`SnapshotShareView` fed by the snapshot RPC) inherits the snapshot RPC's uselessness above for e2ee.

Also inherited from e2ee's standing boundary (e2ee §15): **no server-side features over e2ee shares** — no server search across a shared subtree, no AI/embedding/summary, no server-rendered public page or email preview. These were never promised for e2ee workspaces; sharing does not change that.

Two things **survive** e2ee untouched and are worth banking:
- **Read-write write-back works under a shared key — cryptographically.** A recipient editing under a key writes `enc:v1:` ciphertext, satisfying `blocks_require_ciphertext_for_e2ee`, which a holder of the same key decrypts. No new crypto (true for B under the WK; C needs its own machinery — §6.C). The *authorization* half is Plane 1's: `blocks_write` is workspace-writer-only and both write RPCs are `SECURITY INVOKER`, so a share editor's write is rejected until old §6.1's union revision — which covers `blocks_write`, not just `blocks_read` — is installed (§3.1). Operational caveats are real — reprojection §8.2; history and attribution §8.7.
- **The `effective_share_ids` / RLS / stream *plumbing*** is metadata-only and indifferent to encryption (§2).

## 5. Design dimensions

Two orthogonal axes generate the option space. Don't conflate them.

- **Axis 1 — key domain (confidentiality granularity).** *Whole-workspace* (the recipient's key opens the whole workspace; subtree scope is RLS-only) vs *per-share* (a fresh key opens only the shared subtree; subtree scope is cryptographic) vs *none* (plaintext copy; no key).
- **Axis 2 — key delivery (how the recipient obtains whatever key they get).** *Out-of-band* (the user transmits the key over Signal/paper/password-manager; what ships today for whole-workspace shares) vs *wrapped delivery* (server brokers a key wrapped to the recipient's public key; requires the deferred e2ee §13 X25519 hierarchy) vs *key-in-URL-fragment* (the key rides in the `#fragment`, never sent to the server; the anonymous-link pattern, with real hygiene hazards — §9).

Axis 2 is a pure "where does the key come from" upgrade and applies to whichever key domain you pick. The hard, security-defining choice is Axis 1. The options below are points in (Axis 1 × Axis 2) space. A **pure capability-token** (bearer-grant, server validates token → ships rows) is *not* a separate Axis-1 option under e2ee: a token alone ships only ciphertext, so it degenerates into token + key-in-fragment (→C) or token + export (→D). It survives as a distinct mechanism only on plaintext workspaces, where it *is* the old `share_links` design.

## 6. The options

### Option A — Plaintext-only sharing (capability-gate e2ee out)

**Mechanism.** Ship `subtree-sharing.md` exactly, gated to plaintext workspaces (the share affordance reads the local mode pin; e2ee → no subtree share, offer Export/Add-collaborator instead).

**Key domain:** none. **Delivery:** n/a. **Threat model:** identical to the old doc — RLS is the boundary, correct *because the workspace is plaintext and the server already reads it.* No regression, no new promise.

**Enables:** full-fidelity subtree sharing (nested shares, invites, RO/RW links, anonymous snapshot links, server labels) on every non-encrypted workspace — the bulk of today's value. **Complexity:** lowest — the old design plus a one-line capability gate.

**What the properties migration adds to A.** Plaintext workspaces are exactly the ones that *will* flip to child-backed properties, so A is where the migration bites: a shared subtree carries its field/value rows automatically (§2), and two acceptance gates come with that, both crypto-agnostic and both Plane-1 work — **definition visibility** (§8.2) and **graph-scoped machinery on share-scoped devices** (§8.3). Neither blocks A; both must be settled in it, or every later option inherits the gap.

### Option B — Whole-workspace key, RLS-scoped subtree

**Mechanism.** Plane 1 ships for e2ee too: the recipient gets a `block_share_members` grant (and is **not** added to `workspace_members` — §3.1 conclusion 1), the *revised union* `blocks_read` and the `shared_blocks` stream scope them to the covered subtree, and Plane 2 delivers the **workspace WK** out of band (→ wrapped delivery once §13 lands). The recipient pins the workspace `e2ee`, holds the WK, decrypts the covered rows. The WK also suffices for covered media: `K_id` is derived from it ([`contentKey.ts`](../src/sync/crypto/contentKey.ts); the key store records `{wk, contentKeyHmac}` together).

**Key domain:** whole-workspace. **Delivery:** out-of-band → wrapped.

**Threat model.** Per §3.1's table and conclusions: B hands over the workspace **master key**, so subtree scope is RLS-only — vacuous if the recipient is also a workspace member, void against a dishonest server or RLS regression. Not a confidential subtree share; revocation is cryptographically void (§8.4).

**Cost (not "near-zero").** Low *crypto* cost, but B inherits all of Plane 1 *plus* three non-trivial additions: a new client bootstrap state "I hold this WK but only a subtree synced" in the workspace resolver (§8.3); a share-scoped projection of the `workspaces` row plus stream parameterization, without which a non-member recipient can't even reach the unlock gate (§3.1); and — for shared media — a Storage-RLS extension that, with path-prefix RLS, can only grant per-*workspace* GET, not per-subtree (§8.1). So B's media is "free" only at workspace granularity, which is consistent with B not being subtree-confidential anyway.

**Verdict on B's existence.** Because B is cryptographically "hand over the master key," it is *barely distinguishable from adding a collaborator to the workspace* with a focused landing block — and Option E (below) gives a trusted collaborator strictly better confidentiality. The recommendation (§7) therefore ships **neither** B's construction (`block_share_members` + union `blocks_read` + subtree-scoped stream, all under the whole WK) **in any form**. On e2ee the only collaborator affordance is the *already-shipped whole-workspace share* (no `block_shares` machinery at all), with Option E as the confidential-subtree steer. B is retained here as a named point in the option space precisely so the reasoning against shipping it is on the record — and to keep it distinct from the shipped whole-workspace share, which is a *different*, simpler thing.

### Option C — Per-share key domain (cryptographically-isolated subtree)

**Mechanism.** Give the shared subtree its **own** symmetric Share Key `SK` (a fresh CSPRNG key, not derived from the WK — so a recipient given `SK` cannot derive the WK or any sibling key), so the key the recipient receives opens *only* the subtree. This is the only option that keeps the e2ee promise — "share a page without exposing the graph" — and the only one that admits anonymous links (the fragment carries `SK`, which unlocks only the share; fragment hygiene is a real hazard class, see §9). It does **not** close metadata leakage (§8.6). Two sub-variants:

- **C-in-place (multiple key domains per workspace).** The subtree's blocks stay in the origin workspace but are re-sealed under `SK`. This generalizes the e2ee core from *one key per workspace* to *a key domain per (workspace, key-id)*, and the ripple is wider than just the seam:
  - `getCek` must resolve per (workspace, key-id) — effectively widening key resolution from today's `(user, workspace)` to `(user, workspace, key-id)`.
  - The per-column AAD must additionally bind a **`key_id`**. This is *not cosmetic*: today the AAD pins `[block_id, workspace_id, column, schema_version]` but **not** which key domain sealed the column. The same-AAD collision arises exactly on **domain-transition rows** — a block moving into/out of a share, plus retained pre-transition ciphertext (history diffs, stale replicas) — and there a both-keys holder (or a server feeding one) can substitute an SK-sealed column where a WK-sealed one is expected and it still authenticates. AES-GCM fails closed for a single-key recipient (a wrong-key open rejects), so the realizable impact is **integrity/rollback confusion for a both-keys holder**, not a confidentiality break against a scoped recipient; binding `key_id` authenticates the domain — an integrity fix (and a `schema_version` bump).
  - The sealing domain must also be **visible on the wire, in clear** — a key-id column or envelope field the AAD binding then authenticates — because a downloader has to *choose* a key before it can open anything, and today's wire row carries nothing to choose by (`WireBlockColumns` is ids + ciphertext). Trial-decrypting against every held key is not an answer once rotation exists (old-SK ciphertext must be distinguishable from corruption).
  - **One row, one sealing domain — so nested/overlapping shares are foreclosed under C-in-place.** Plane 1 happily stamps multiple `effective_share_ids` on a row, but the row has a single ciphertext: seal it for the inner share and the outer share's audience loses it; seal it for the outer and the inner audience gets the wrong revocation domain. Making one ciphertext serve N audiences means per-row key-wrapping — §13-shaped machinery. Declare overlap out for C-in-place v1 (a casualty of the old design's nested-share support) and say so in the share UI.
  - **The workspace's own members need the SK too.** Re-sealing a subtree under `SK` makes it unreadable to WK-only *members* — RLS still serves them the rows (member disjunct), but their key no longer opens them — so C-in-place's key distribution includes the home audience, every current member and each future join, not just share recipients. That is per-member SK delivery (today: out of band, per device) or a dual-seal scheme, which is again §13-shaped wrapping.
  - The **mode pin** ([`modePin.ts`](../src/sync/keys/modePin.ts)) is per `(user, workspace)` and set-once/immutable — it has no slot for a sub-workspace domain, so "is this block's domain e2ee and is its SK loaded?" needs new sub-workspace authority machinery, exactly the authority the §8.3 entry gate is built on. The same workspace-shape holds for the redemption path: the `wk_canary` and the `(user, workspace)`-keyed key store have no share-scoped analogs, so *validating and storing* a delivered `SK` is new machinery too (§6.F). The asset-content key has the same shape problem: `K_id` derivation and its `{wk, contentKeyHmac}` store slot are WK-shaped, so an SK domain needs its own content-key derivation and slot (§8.1).
  - The **materializability resolver** ([`resolver.ts`](../src/sync/keys/resolver.ts) + the per-`workspace_id` cache in the observer's `materialize`) resolves per workspace; C-in-place forces per-block-domain resolution inside the decrypt loop.
  - The owner's client must hold the WK and every live `SK`; a **recipient holds only the SK(s) they were granted**.

  So this is **encryption-core surgery, not a follow-up commit** — it reaches the seam, the AAD format, the pin authority, and the observer.

- **C-projection (a share is a derived workspace).** The subtree is *mirrored* into a new lightweight workspace `W_share` sealed under `SK` (= that workspace's WK), and the recipient is a member of `W_share`. This reuses 100% of the per-workspace e2ee model with zero core changes — the cost moves to a **re-encryption relay**: origin (under WK) and mirror (under SK) are two ciphertext domains, and the current sync path is strictly single-workspace (upload seals under the payload workspace's key; download decrypts each row under its own workspace's key — there is no path to decrypt from A and re-seal into B). So only a holder of *both* keys (the owner) can reconcile them, on the client, online. Editor recipients' edits land in `W_share` under `SK`; the **owner's client is the relay** that re-projects them into the origin under WK and vice versa — offline, the domains diverge. Worse, the two rows have **independent `updated_at` lineages** (each server-clamped by [`20260612000000`](../supabase/migrations/20260612000000_add_user_updated_at_monotonic_clamp.sql), since made drift-aware by [`20260803000000`](../supabase/migrations/20260803000000_add_patch_base_version_drift_bump.sql)), so the relay cannot resolve conflicts by column last-write-wins and needs an explicit causal/version scheme. This is a genuine CRDT/relay subsystem — the heaviest part of the whole design.

**Key domain:** per-share. **Delivery:** out-of-band, wrapped (§13), or key-in-fragment (anonymous).

**Threat model.** Strong: a recipient (even colluding with a hostile server) decrypts only the shared subtree. Revocation for enumerated members is *cryptographically meaningful and cheap*: rotate `SK`, re-seal only the (small) shared scope of live rows, re-deliver to remaining members (hard caveats — un-re-sealable history, irrevocable anonymous links: §8.4). This asymmetry is the principal reason C is the *correct* long-term answer.

**Forecloses:** simplicity. C-in-place perturbs the encryption core (above); C-projection adds the owner-relay subsystem and duplicate storage (including duplicate media re-uploaded under `SK`, defeating workspace-wide dedup — §8.1). **Complexity:** high; defer behind a concrete requirement (§7, §9).

### Option D — Export-to-plaintext snapshot (read-only / public / anonymous)

**Mechanism.** At share time the **client** decrypts the subtree (it holds the WK) and writes a **plaintext** copy governed by Plane 1 alone — into a dedicated plaintext "published" surface (a published workspace or an immutable client-produced snapshot). The artifact is plaintext thereafter; the server can read/render/label/serve it; anonymous recipients need no key. This is the e2ee-world realization of the old snapshot path, with the decrypt moved to the *client* before publication, and matches the media design's "export-to-plaintext" plan (still unbuilt — §1 item 2).

**Key domain:** none after export. **Delivery:** n/a.

**Threat model.** Deliberate **declassification**: the exported copy is plaintext on the server under the old RLS-only boundary, and updates to the encrypted original do not propagate (it's a snapshot, or a separate plaintext workspace). **Footgun (per AGENTS.md public-table rule):** `blocks` is granted to `anon`, so the publish target's RLS must *positively allow* anon `SELECT` on exactly the published subtree and default-deny everything else, or export silently world-exposes more than intended. The UI must make declassification unmistakable, and it is **irreversible** — there is no un-publish that re-encrypts, and any media re-published as plaintext (§8.1) is a permanent independent artifact (§8.8).

**Enables:** "share read-only with the world / with someone with no account," server previews/labels/search *of the exported copy* — the things e2ee otherwise forecloses — at the cost of those bytes no longer being end-to-end encrypted. **Complexity:** low-to-moderate; client decrypt + a publish target; no encryption-core change.

### Option E — Manual second e2ee workspace (confidential, no relay)

**Mechanism.** The user creates a *second* e2ee workspace with its own WK (= a per-share key, achieved with zero core changes), hands that WK to collaborators out of band (the shipped whole-workspace share — `createEncryptedWorkspace` + `unlockWorkspaceWithKey`), and **moves or copies** the subtree into it, accepting that it is now a separate graph with no live link to the origin.

**Key domain:** per-share (it's a real separate workspace key). **Delivery:** out-of-band → wrapped (§13).

**Threat model.** Full cryptographic isolation — the collaborator's key opens only that second workspace, never the origin. This is **C-projection's confidentiality at Option A's implementation complexity**, trading away automation: the copy is divergent (no relay keeps it in sync with the origin), and the user maintains it by hand. For the "trusted collaborator on a confidential subtree" case, E is cryptographically *strictly better than B* with **no new code** — though at a real *manual-maintenance* cost (a divergent copy the owner keeps current by hand). That is why it, not B, is the recommended confidential path until C exists.

**Forecloses:** live two-way sync between origin and the shared copy; nested/overlapping shares; anonymous links. **Complexity:** essentially zero new code — but the copy's *fidelity* is bounded by what cross-workspace copy actually is today: **markdown-mediated** (serialize → parse → fresh creates; there is no structural cross-workspace move primitive, and the existing immutability trigger rejects cross-workspace *moves*). Fresh ids are minted by construction, but `((id))` reference spans ride the markdown **verbatim**, so intra-subtree references dangle in the destination or resolve back into the origin for anyone who can see both — the "copy resolves references" follow-up named in the props doc §7 is unbuilt, and this codebase's dangling-ref history says to treat that as a real footgun, not a nit. Properties don't survive the copy **at all** today: [`serializeBlock`](../src/utils/copy.ts) walks the subtree with `hidePropertyChildren: true` (an interim wholesale filter — the tier-aware version is a later slice) and never reads the cell, so property values — cell-backed or child-backed — simply never enter the clipboard payload; the owner re-enters every property by hand. Media does not ride along either: the origin's assets are unreachable under the second workspace's key and must be re-uploaded by hand (§8.1).

### 6.F — The delivery upgrade (Axis 2): a convenience, decoupled from C

The e2ee §13 hierarchy (per-user asymmetric keypair — X25519 *as currently sketched* in that doc, which is "superseded in places" — plus a per-workspace **CEK** (content-encryption key; structurally identical to today's WK, per e2ee §13) wrapped per member, with server-brokered delivery) removes the out-of-band step from **B/C/E** without changing their key-domain semantics: the owner wraps the relevant key (WK or SK) to the recipient's published public key; the server stores/relays the wrapped blob; the recipient unwraps locally. It generalizes cleanly to per-share keys — "a CEK wrapped per member, where the CEK belongs to a *workspace OR a share*" — and *that* is the precise sense in which a key hierarchy "helps share subtrees with their own key": it is the **delivery and revocation substrate**, not the thing that mints the per-share key. Minting the per-share key and re-sealing under it are C's Axis-1 change; **§13 is an Axis-2 convenience layered on B/C/E, never a prerequisite for C.** It does not reduce the bulk of C's Axis-1 cost (key-id AAD, per-domain key resolution, per-domain materializability) — at most it eases per-domain *authority bookkeeping*, since per-member wrapped keys make "which domains do I hold" first-class.

**C's out-of-band delivery is real, but the analogy to the shipped WK share is transmit-channel only.** A per-share `SK` can be handed over the way the shipped whole-workspace share hands over a WK, and a confidential subtree share is a *deliberate, low-N act* (like sharing a whole workspace), so per-share hand-delivery is no worse than the per-workspace step the design already accepts. What the analogy does **not** cover is redemption: the WK flow's out-of-band step terminates in machinery that is all workspace-shaped — a workspace-scoped canary validates the paste, a set-once `(user, workspace)` mode pin records authority, and the key store holds exactly one key record per `(user, workspace)`. A share domain has none of these; C-in-place must build a share-scoped canary analog, share-domain authority, and a share-keyed store slot — Axis-1 redemption machinery counted in §6.C, not delivery cost. (C-projection sidesteps this: its SK *is* `W_share`'s WK, so redemption is literally the shipped flow.) Anonymous C links use key-in-fragment and need no identity keys at all — but forfeit targeted revocation (§8.4).

**Subtree sharing therefore does *not* specially justify building §13.** The tempting intuition — "you'd be hand-delivering a key per shared *page*, so sharing forces the hierarchy" — imports a high-frequency sharing model this product doesn't have; a *subtree* is a deliberate unit, not a paragraph. Honest arithmetic: out-of-band delivery cost scales with *(distinct shares × recipients-per-share × devices-per-recipient × (1 + rotations + key-loss re-deliveries))*, every delivery gated on the owner being online holding the key — and the device term is the same per-device paste burden the e2ee doc itself names as its §13 trigger, which per-share keys multiply. At a handful of deliberate shares with one-or-two recipients each, every factor is small today, so the conclusion holds — but it starts failing *for sharing* once audiences, devices-per-recipient, or rotation frequency grow, where per-recipient-per-device redelivery compounds and automatic re-wrapping wins; revisit then. §13 otherwise stands on its **own** merits — multi-device unlock without re-pasting per workspace, and passphrase-rooted recovery — which sharing neither creates nor removes. Until then, keep the key-delivery call site on the existing `getCek`/key-store seam so a future §13 is a delivery swap, not a redesign.

## 7. Recommendation — a phased hybrid, with the bet stated

Make the planes explicit in the product, and be honest per workspace mode. This resolves the "does B exist" question (§6.B) rather than leaving it open.

**Phase 1 — ship the access-control plane; full sharing on plaintext; honest-only on e2ee.**
- Implement Plane 1 from `subtree-sharing.md` (schema, recompute, RLS *revised to the union policy*, `shared_blocks` stream, RPCs, routing, share-mode bootstrap, dialog). Crypto-agnostic; lands once and serves every later option.
- Plane 1 must also settle the two gates the properties migration opened, because plaintext workspaces — A's whole audience — are the ones that flip: **definition visibility for share recipients** (§8.2, §9 Q7) and **a membership-not-settledness gate on graph-scoped machinery** (§8.3, §9 Q8).
- On **plaintext** workspaces this delivers the entire old design (Option A): the bulk of user value, no e2ee risk.
- On **e2ee** workspaces, the "Share…" affordance does **not** offer a confidential subtree share, and does **not** ship Option B as a distinct feature. It offers exactly:
  - **Add a collaborator** — surfaced honestly as "shares the whole workspace key with this person." Mechanically this is the shipped whole-workspace share; for a confidential subtree the UI steers the user to **Option E** (a second e2ee workspace), which is cryptographically clean. No `block_shares` machinery is used on the e2ee path here, because at whole-WK granularity it would only imply a confidentiality wall that does not exist.
  - **(D) Publish a read-only copy** — client decrypts and exports to a plaintext surface (declassification, explicit and irreversible); covers public/anonymous read-only links.

**Phase 2 (deferred, requirement-gated) — confidential subtree sharing on e2ee (Option C).**
- Build only when there is a real need for "share a page, not my graph" *on encrypted workspaces with live collaboration*. Its cost is the Axis-1 encryption-core change, **not** delivery: a per-share `SK` can ship out of band, so C does **not** wait on the §13 hierarchy (an optional Axis-2 convenience — §6.F). Prefer **C-in-place** only if its encryption-core change (key-id AAD, per-domain `getCek`, sub-workspace pin authority, per-domain materializability) proves cheaper than **C-projection**'s owner-relay reconciliation; prototype both against the media-dedup and offline-collaboration constraints before committing. Note metadata leakage (§8.6) still isn't closed even by C.

**The bet, stated plainly.** v1 deliberately does **not** deliver the marquee capability — confidential subtree sharing on e2ee. We accept that because (a) plaintext workspaces cover most real sharing; (b) for trusted collaborators on confidential material, Option E already gives cryptographic isolation with no new code; (c) the fleet is small and coordinatable, so there is no pressure for anonymous-stranger confidential sharing yet; and (d) C is a substantial project that should be bought by a concrete requirement, not built speculatively. A reader who believes confidential subtree sharing is needed *now* should disagree with this bet directly (§9, Q1) — it is the load-bearing product decision, not an obvious "do the easy thing first."

**Why this ordering.** Most value (plaintext sharing) with least risk first; never a confidentiality promise the crypto doesn't keep (the e2ee path ships only declassification and explicit whole-key trust); consistent with the media design's deferral of encrypted subtree sharing; and the hard cryptographic work (C) sequenced behind a concrete requirement — with §13 an independent, optional delivery upgrade (§6.F), not a dependency.

## 8. Cross-cutting concerns

### 8.1 Media inside a shared subtree

An asset lives at `<workspace_id>/<content_key>`; on e2ee `content_key = hex(HMAC(K_id, sha256(plaintext)))` with `K_id = HKDF(WK, 'km/asset-content-key/v1')` and the bytes sealed `encb:v1:`; on plaintext the path is raw `hex(sha256(plaintext))` and the bytes are stored unencrypted (all verified in code — §11).

- **Option A:** plaintext media under the old boundary — the storage-RLS extension for share members is the whole cost, and it is the same per-workspace-vs-per-subtree problem as below.
- **Option B:** the recipient holds the origin WK, derives the same `K_id`, computes the path, fetches, decrypts. But path-prefix Storage RLS keys on `workspace_id` (the path's first segment), so extending it to share members grants per-*workspace* GET, **not** per-subtree — honoring share membership at subtree granularity requires the media design's deferred `content_key → block` mapping (its earmarked `effective_share_ids` storage-RLS branch); both remain unbuilt (§1 item 2). Consistent with B not being subtree-confidential anyway.
- **Option C:** hard. Bytes were uploaded under the WK with a WK-derived path/key. `K_id` is a one-way HKDF output — sharing it does **not** yield the WK and does **not** decrypt anything (assets stay sealed under WK), so it is not a "WK capability." What it *is* is a **workspace-wide path/existence oracle**: a holder of `K_id` can recompute any asset's path from a guessed plaintext and test its presence across the whole workspace. So C must **re-seal the asset under `SK`** (so an `SK`-only recipient can open it — it cannot open WK-sealed bytes) and **re-upload at an `SK`-derived path**; the path change specifically buys namespace + dedup-domain separation, not plaintext confidentiality (which `SK`/`WK` key separation already provides). This defeats workspace-wide dedup and duplicates bytes per share — and the client key machinery is WK-shaped (`K_id` derivation + the `{wk, contentKeyHmac}` store record), so an SK content-key is new machinery, counted with §6.C's redemption costs. C-projection makes the duplication explicit: the mirror re-uploads its media.
- **Option D:** the client decrypts the bytes and re-publishes them as plaintext objects — standard, irreversible declassification (§8.8).
- **Option E:** the collaborator holds only the *second* workspace's WK — which derives the second workspace's `K_id` and locates nothing in the origin's storage prefix (and Storage RLS wouldn't serve origin objects to a non-member regardless). So E's manual copy must **re-upload every referenced asset into the second workspace** — re-sealed under its WK, at its own content-address — or the copy silently drops its media; today's markdown-mediated copy does not do this (§6.E), so count it as part of E's by-hand cost, never as a reason to hand over the origin WK.

### 8.2 References, labels, and property definitions crossing the share boundary

The old §8.6 server-label RPC is dead for e2ee (§4). Three distinct problems now, one of them new with child-backed properties:

- **Display of references.** A reference whose target row the recipient received and can decrypt → render normally. A reference to a row outside the share → an **id-only / "no access" chip, no label** (neither server nor client can produce one). Strictly worse than the plaintext experience; surface it as a known limitation. Presentation-root clipping (old §3.8) is unchanged (tree-shape metadata).
- **Display of properties — the definition gap (new, crypto-agnostic, hits Option A first).** On a flipped workspace a field row's content is `::((fieldId))` — the property's *name* lives on the definition block the ref points at, and definition blocks (`'property-schema'`, likewise user block types) are parented under root-level singleton system pages (Properties / Types), **outside every user subtree**. The blast radius is precise: the registry composes code-declared seeds with definition blocks ([`propertyDefinitionRegistry.ts`](../src/data/propertyDefinitionRegistry.ts)), and a share-scoped recipient is missing only the block half — so **kernel/plugin properties still resolve and render**, while the workspace's **user-declared and import-promoted** keys are the ones the recipient can detect but not *name* (an unresolvable marker), with typed reads/writes degraded for exactly the vocabulary the user made themselves. Plane 1 has to pick a shape: **include** the workspace's definition pages in every share cover (cheap, but discloses every schema name in the workspace to every recipient — a §8.6-class over-share), **mint per-share definition stubs** for exactly the keys the covered rows use, or **ship labels out of band** (a share manifest). This is a real design decision, not a rendering nit — §9 Q7. (On e2ee workspaces there is no such gap today: they are cell-pinned, and a cell travels inside the owning block's sealed `properties_json`.)
- **Reprojection write-back (a deriver-availability gate, *not* a partial-view problem).** `references_json` holds a block's **outgoing** refs, recomputed post-commit from that block's **own** content grammars (`[[alias]]` / `((id))`) plus its **own** cell's ref-typed values, classified by the resolved property-definition registry ([`referencesProcessor.ts`](../src/plugins/references/referencesProcessor.ts) → `projectPropertyReferences` in [`referenceProjection.ts`](../src/plugins/references/referenceProjection.ts); the registry is [`buildPropertyDefinitionRegistry`](../src/data/propertyDefinitionRegistry.ts) — `propertySchemasFacet` is retired), merged through the add-only `reconcileDerived` chokepoint (contract: [`derived-data-add-only.md`](contracts/derived-data-add-only.md)) and written to the **owner's** row. An editor recipient can fully decrypt the block they are editing, so recomputing *its* refs from *its own* in-view content is **complete, not partial** — a narrowed sync view does not by itself make the recompute lossy. On a flipped workspace the hazard actually *narrows*: a ref-typed value also exists as a value row whose content is `((target-id))`, and that row's own content-ref derivation is pure grammar, no registry needed. What remains is the deriver-availability gate, and the definition gap above **widens its trigger**: a recipient's registry can now be empty not because a plugin is off or `?safeMode` is on, but because the definition *blocks* never synced. The add-only / retain-on-absence contract is what protects stored refs in all these cases; the gate is "confirm the editor recipient's client can resolve the definitions the covered rows use" — which collapses into the same §9 Q7 decision. Backlinks pointing *into* a shared subtree from outside are computed on the owner's full-context client and are simply invisible to the recipient — acceptable, but state it.

### 8.3 Client state: multi-workspace, multi-device, key loss — and graph-scoped machinery

- **Partial-key state.** Under B a recipient holds a WK and a mode pin for a workspace where only a subtree synced. The entry decision ([`src/bootstrap/resolveWorkspace.ts`](../src/bootstrap/resolveWorkspace.ts), [`resolveWorkspaceEntry.ts`](../src/sync/keys/resolveWorkspaceEntry.ts) → [`decideWorkspaceEntry`](../src/sync/keys/workspaceAccess.ts)) keys off membership/pin/key presence and does **not** model "WK present but only a subtree available"; that must become a first-class state, not "key-presence ⇒ full membership." Entering an e2ee share must drive the same unlock/canary gate a normal e2ee entry does — and that gate reads `encryption_mode`/`wk_canary` off the synced `workspaces` row, which a share-grant-only recipient never receives today (§3.1).
- **Graph-scoped machinery must refuse share-scoped devices (new).** The data layer now runs machinery whose correctness *presumes the device sees the whole graph*: per-graph data migrations coordinated by a synced, deliberately un-arbitrated claim block under a root-level system page ([`graphBackfillClaim.ts`](../src/data/internals/graphBackfillClaim.ts), [`propertyCellBackfill.ts`](../src/data/internals/propertyCellBackfill.ts)), and audit surfaces that qualify their answers by sync-view completeness (`audit-properties` / `syncGap`). A share-scoped device breaks the presumption twice: its scan of "all rows" covers a fraction, and its gates can't tell — **the sync-settled preconditions measure quiescence, not coverage**, and a drained share-stream reads exactly like a drained workspace. The claim offers no backstop either: it converges by ordinary sync with no server arbitration, and the claim block's home page sits outside every share cover, so a share-scoped device would act on a claim view that is simply absent. Plane 1 therefore owes the client a first-class, queryable distinction — *workspace membership vs share grant* — and every graph-scoped pass gates on it, not on settledness. The same gate owes a stop to **seed materialization**: `Repo.scheduleWorkspaceSeedMaterialization` → [`materializePropertySeeds`](../src/data/definitionSeeds.ts) *creates* missing definition blocks and their root-level system pages at deterministic ids, and on a share-scoped device every seed looks missing (the pages sit outside the cover — §8.2). Today that pass happens to hang before writing — `awaitLocalMemberRole` never resolves without a `workspace_members` row — but that is an accident of how membership is queried, not a designed guard, and it evaporates the moment shares get any membership-row representation. (All of this is §8.2's registry point in another costume: "the data I derive from is all present" is an assumption sharing breaks for the first time.)
- **Multi-device recipient.** A recipient's *second* device obtains the key the same way the first did — out of band again, or via §13 wrapped delivery once it exists. State this; it's the same property the whole-workspace share already relies on (the canary is workspace-scoped, so any device validates the same WK).
- **Key loss.** Recipient loses their device key → for B, re-paste the WK; for C/E, the owner re-shares the `SK`/second-workspace WK. There is no recovery of lost keys (inherited e2ee property). The lock-and-wipe panic delegates to the platform's "clear site data" — a coarse, origin-wide wipe of all local data and keys for the profile (not a per-workspace or per-share operation) — so a recipient who triggers it simply re-enters via this same key-loss path; no share-specific recovery is needed.

### 8.4 Revocation differs sharply by option — say so

- **Plaintext (A) / export (D):** revocation = RLS stops new fetches; the recipient keeps whatever already synced; exported plaintext stays readable wherever it landed.
- **Option B (whole-WK):** revocation is **cryptographically void**. Because `blocks` is reachable by direct PostgREST `SELECT` under RLS, revocation that leaves *any* RLS-passing path open lets the WK-holder keep pulling and decrypting **new** edits, not just re-reading local copies. True revocation requires rotating the workspace WK — re-encrypting the *entire* workspace and redistributing the new WK to all legitimate members — exactly the expensive op e2ee otherwise avoids, and one that is itself **unbuilt today** (`wk_canary` is immutable; rotation is explicitly deferred to post-v1 in [`20260529120000`](../supabase/migrations/20260529120000_add_e2ee_workspace_columns.sql)). The strongest argument against treating B as real subtree sharing.
- **Option C (per-share SK):** for an **enumerated-member** share, revocation is **meaningful and cheap** — rotate `SK`, re-seal only the (small) shared scope of **live** rows, and re-deliver the new `SK` to remaining members (one out-of-band step per member-device, or an automatic re-wrap if §13 exists). The recipient keeps what they already pulled but is cryptographically locked out of everything after rotation. Two hard qualifications. **History cannot be re-sealed:** `blocks_history` is append-only and trigger-written with no UPDATE path ([`20260522062437`](../supabase/migrations/20260522062437_add_blocks_history.sql)), so rotation retires the old `SK` only for live rows — the owner must retain every prior `SK` to keep the shared scope's history readable (§8.7). **Anonymous key-in-fragment links have no targeted revocation:** the key is baked into distributed URLs and the audience is not enumerable, so revoking one leak means re-keying the share and breaking *every* outstanding link — an anonymous C link is effectively irrevocable short of that (§9 Q6). The cheap part is the scoped re-seal; redelivery scales with remaining audience × devices — the one place §13's automatic re-wrapping starts to earn its keep (§6.F).
- **Option E (second workspace):** revocation is **membership removal, not key rotation** — `remove_workspace_member` (shipped; owner-or-self-gated) ends the recipient's RLS access to the second workspace, cutting off future manually-pushed updates. WK rotation is as unbuilt for the second workspace as for the first (Option B, above), so a genuine cryptographic re-key means standing up a *third* workspace and re-copying. And row 3's caveat applies here as everywhere: the recipient keeps what already synced, and a dishonest server plus the still-valid WK reconstructs whatever the second workspace held at removal time. Since v1 E is a divergent manual copy there are few post-copy updates, so removal mostly governs whether the owner keeps pushing new material.

### 8.5 Threat-model statement (one place, aligned with §3.1)

E2EE's invariant is "the server never holds plaintext or a usable key." Per option:
- **A:** unaffected (plaintext workspace; invariant didn't apply).
- **B:** the invariant now rests on the three §3.1 conditions (share-member-only recipient, honest server enforcing the union RLS, no direct-PostgREST escape) — and even then on the recipient's trustworthiness for the whole workspace, since they hold the master key. A deliberate, scoped relaxation; acceptable for fully-trusted collaborators, unacceptable as a general primitive.
- **C / E:** invariant preserved; the recipient is cryptographically confined to the shared scope. (Metadata still leaks — §8.6.)
- **D:** the **exported copy** is deliberately declassified to plaintext; the original workspace's invariant is untouched.

### 8.6 Metadata leakage — what a recipient and the server learn beyond content

Plane 1 ships plaintext metadata to both the recipient and the server, and **no option here closes it — not even C.** For any covered block a recipient receives (the `blocks_synced` columns, plus Plane 1's designed `effective_share_ids` and what plain arithmetic derives): the `id`, `workspace_id`, `parent_id` (→ tree *shape* and sibling structure), `created_at`/`updated_at`/`user_updated_at` (→ edit cadence, including the client-supplied edit stamp), `created_by`/`updated_by` (→ co-author identities), the `deleted` tombstone (→ the *fact* of an in-scope deletion), the `effective_share_ids` array, the plaintext `order_key` (→ sibling ordering and reorder/insert cadence), per-column **ciphertext lengths** (AES-GCM is length-preserving: plaintext sizes leak), and the block **count** of the shared scope. For a "share a page, not my graph" (C) framing this is a real disclosure: structure, timing, and authorship of the shared subtree leak even though content is sealed under `SK`.

The properties migration shifts this surface, in both directions. **Against leakage:** the recognition columns (`reference_target_id`, `is_field_form`) are local-only and never sync — the edge-metadata leak that shape originally implied was engineered out (props doc §8), which is also why e2ee's cell-pin is sequencing, not a standing confidentiality gap. **Toward leakage:** on a flipped workspace every property is a row, so the per-block *property count*, value-list shape, and per-property edit cadence become visible as row metadata (`parent_id`/`order_key`/timestamps) — where cell-mode hid all of that inside one sealed column, modulo its ciphertext length. If an e2ee workspace ever flips (the future client-side path), that structural disclosure comes with it; a future C should say so. (`workspaces.properties_migration` itself is a synced plaintext column — trivial, it's an operator lever, but it is one more thing a recipient learns.)

Two concrete actions:

- **Disclose it.** Any "confidential" framing for C must state that *content* is confidential but *structure/timing/authorship metadata of the shared subtree* is not.
- **Filter `effective_share_ids`.** A covered row's array contains *all* share-ids reaching it, including shares the recipient is not a member of — leaking the existence and ids of sibling/overlapping shares. The `shared_blocks` projection must ship **only the recipient's own reaching share-ids**, or accept this as a disclosed leak. Likewise re-examine `block_shares` / `block_share_members` stream visibility (old §6.3 restricted member enumeration to writers): a scoped recipient must not be able to enumerate the whole workspace's share audience.

### 8.7 Write-back: history, attribution, concurrency

Editor write-back is "free" cryptographically but carries operational tails:
- **History.** Every blocks write fires the server `blocks_history` trigger ([`20260522062437`](../supabase/migrations/20260522062437_add_blocks_history.sql)), stamping `actor` and copying the content columns verbatim — i.e. **ciphertext under whatever key sealed the live row at write time** (SK-domain writes produce SK-sealed diffs; there is no separate design choice to make). Consequences: a block that transitions WK↔SK accumulates **mixed-domain history**, fully readable only by holding every domain that ever sealed it; history rows are append-only with no UPDATE path, so an SK rotation **cannot re-seal them** (§8.4); and `blocks_history_read` is workspace-member-only, so a pure share-member recipient reads **no history at all** — a confinement win, but their own edits' history is invisible to them while landing in the *owner's* workspace history. (The same append-only property is why any future plaintext→e2ee *mode conversion* must also purge or encrypt the pre-flip plaintext history — a standing constraint on that flow, noted in the props doc §8, not on sharing.)
- **Attribution.** `created_by`/`updated_by` are client-supplied in **both** write RPCs — `apply_block_patches` (`COALESCE(patch->>'created_by', …)`, current revision in [`20260803000000`](../supabase/migrations/20260803000000_add_patch_base_version_drift_bump.sql)) and the newer `apply_block_creates` ([`20260709000000`](../supabase/migrations/20260709000000_add_apply_block_creates_rpc.sql)) — so an editor recipient can spoof authorship. Pre-existing, but sharing widens the trust boundary to non-workspace recipients — if attribution matters for shares, stamp it server-side from `auth.uid()`.
- **Concurrency.** Within one key domain, block-granular LWW is unchanged (the server-side `updated_at` clamp is now drift-aware — [`20260803000000`](../supabase/migrations/20260803000000_add_patch_base_version_drift_bump.sql) — but that changes stamping, not the domain analysis). Across domains (C-projection) it is meaningless (§6.C — independent `updated_at` lineages).

### 8.8 Lifecycle / GC

- **Anonymous-user GC still rides along.** Plaintext RW links (Option A) still mint anon Supabase users with the old deferred-GC debt — the e2ee work doesn't remove it, it inherits it. For e2ee, RW *anonymous* links are foreclosed entirely (anon users hold no key; B can't forward the WK to a public URL; C key-in-fragment is deferred), so anonymous e2ee sharing is read-only export (D) only.
- **Revoked-share / deleted-subtree cleanup.** For C-in-place, when a share is revoked and `SK` rotated, blocks that *left* the share need re-sealing under the WK — name who runs that and when. For C, the duplicate `SK`-media must be GC'd on revoke or it orphans. Deleting a shared subtree cascades `block_shares` (old §4.2 `on delete cascade`), but a D export snapshot and a C `W_share` mirror survive independently. Spell these out before building C.
- **Declassification is permanent.** D has no recall that re-encrypts; exported plaintext (text and media) is a permanent independent artifact — relevant to any "right to be forgotten" expectation.
- **Share creation is online-only.** Plane-1 share mutations are security-definer RPCs (old §8), so a share initiated offline can't mint a grant/token until reconnect — the established mutation pattern, but worth surfacing in the share UI rather than failing silently.

## 9. Open questions

1. **Is confidential subtree sharing on e2ee actually needed now?** This is the §7 bet. If the small, coordinatable fleet never needs "share one encrypted page with an untrusted stranger, live," C may never ship and the design is "A + D + E." Answer by product need.
2. **C-in-place vs C-projection** if C is built: which is cheaper given (a) media-dedup and (b) offline collaboration (owner-relay vs always-online)? Prototype before choosing.
3. **`effective_share_ids` / share-table stream filtering** (§8.6): ship only the recipient's own reaching share-ids and confirm a scoped recipient can't enumerate the workspace's share audience — part of Plane 1, not an afterthought.
4. **Storage-object RLS for shared media** (§8.1): the `content_key → block` mapping the media design defers is the real subtree-granular hook; scope it into Plane 1 or the media design.
5. **Deriver availability for editor recipients** (§8.2): how do we confirm an editor recipient's client can classify the covered rows' ref-typed properties? Crypto-agnostic — gates the *shipping* plaintext Option A editor path too, and on flipped workspaces it reduces to Q7.
6. **Key-in-fragment links** (any future C anonymous link): hygiene (Referer/history/paste leakage, no forward secrecy once the URL leaks) *and* the harder property — **no targeted revocation**: re-keying breaks every outstanding link and there is no audience to re-deliver to (§8.4).
7. **Definition blocks in the share cover** (§8.2, new): include the workspace's definition pages (over-shares every schema name), mint per-share definition stubs (new machinery, keeps disclosure minimal), or ship labels in a share manifest (a read-only fix that still leaves the registry blind to user-declared keys)? The choice sets what a share-scoped editor can *write*, not just render — settle it inside Plane 1.
8. **The membership-vs-share-grant gate** (§8.3, new): make "this device holds a share grant, not workspace membership" a first-class client fact, and audit every graph-scoped pass (data migrations, backfill claims, workspace audits, derivation passes) to gate on it. Which existing gates wrongly read a settled share-stream as a settled workspace?
