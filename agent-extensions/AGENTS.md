agent extensions: authoring, verifying, installing (the data-model rules in the root AGENTS.md apply first):

scaffold and layout:
- new extension: `pnpm agent new-extension "<Name>" agent-extensions/<slug>` scaffolds the block-per-record shape (namespaced types, a ref property, todo composition, a pure read path with a test). The scaffold is STANDALONE by default (own deps + a copy of the `@/` declarations, for authors who have only the published CLI). Inside this repo, delete its `types/` and `devDependencies` and point tsconfig at `agent-extensions/kernel-types/src/*` like the neighbours do.

verifying (a green test here proves less than it looks):
- `pnpm run check` does NOT typecheck or lint this directory. Typecheck the flat files with `npx tsc --noEmit -p agent-extensions/tsconfig.flat.json`, and read that config's header before writing your own: a `baseUrl` there makes tsc exit 2 on the CONFIG, which reads as a clean run.
- the gate DOES run flat-file tests (`agent-extensions/*.{test,spec}.{ts,tsx}`). A throwaway probe goes in `tmp/` or as a gitignored `*.probe.*` file, never as a `*.test.*` next to the extension. vitest skips both, so a scratch test you need vitest to run goes under `src/` and is deleted before you commit. A new `agent-extensions/<pkg>/` subpackage gets no CI until its step is added to `run-tests.yml`.
- a green flat-extension test does NOT prove the installed module loads. vitest resolves `@/…` through the root alias, while the app resolves through the page importmap (exact emitted filenames only). The live extension also runs a DB-stored copy, so fixing the repo file reaches the user only via `pnpm agent install-extension`. Full discipline (importmap vs vitest resolution, preview-build probes, install sequence): `bd recall reference_agent_extensions_verification`.
- an extension that imports a NEW kernel export breaks until the app is deployed: deploy first, then install (`bd recall project_extension_install_needs_deploy_first`).

installing and auditing:
- `pnpm agent install-extension` reports `running`. An install that stores source nothing executes registers no schemas, and every write that depends on them lands raw.
- `pnpm agent audit-extension <label>` then checks the DATA: block ids parked in non-ref properties, records buried in JSON cells, properties with no registered schema. `install-extension --verify` lints the source for the same mistakes at declaration level; each warning names the catalog pattern that fixes it.
- an install REFUSES when it changes which codec a value preset id resolves to on that device. That happens when a core the extension registers builds a different codec than the one live under that id (its own previous version, another plugin's core, or a kernel one), or when the update DROPS an id it currently registers, which falls the id back to whatever was underneath, or to nothing. Either way every value stored under the preset is re-typed with no definition row edited, so nothing migrates it. The refusal names what moved and the definitions and cell counts at stake.
  - Fix: give the new codec a NEW preset id and repoint the definitions (an edit per definition row, which `core.migratePropertyDefinition` fans out), or pass `--allow-preset-change` if the values are disposable.
  - It sees the change only while the core it replaces is LIVE here.
  - It only looks when the install itself makes the new source live — the block passes BOTH loader gates here, approved AND enabled — because looking means EXECUTING the source, which an install deliberately does not do for source nothing will run (#67). Pass `--verify` to check a block that does not pass both gates. The enable that later makes it run is not covered (#1046).
  - Both gates are stores that can fail to READ, and a failed read is not a "no". When the block IS approved here (or under `--verify`), an install that cannot read the approval record or the override map REFUSES rather than skipping the check, because skipping it would also re-pin the source it skipped. Retry, or pass the flag.
  - An install re-pins this device's approval ONLY on the path that ran the check. An install onto a block that is disabled here, or one made in SAFE MODE (where no extension contributes anything and there is no live core to compare), stores the source without pinning it and reports `running: false`.
  - `enable-extension` re-approves unconditionally, so install-then-enable still ships an update — and that enable is the uncovered path above, now the only way unchecked source goes live.
  - A codec that changes what it PARSES under an unchanged `type` string is invisible to this check, exactly as it is to the seed ledger: bump the type string when the encoding moves.
