waiting on background subagents / tasks (they die more often than you think):
- a USER INTERRUPTION of the main session kills in-flight background subagents too — their transcript ends with `[Request interrupted by user]` and the completion notification NEVER arrives. After any interruption, before resuming a wait, re-verify liveness of everything you were waiting on.
- Vlad interrupts to STEER, not to cancel: an interruption is normally new input for the main thread, not a verdict on background work. After handling the steer, resume the killed background agents by default (only drop them if the new input supersedes their task).
- never wait open-ended on a notification alone. Pair every wait with a scheduled fallback wakeup, and when the fallback fires (or after an interruption), check liveness instead of re-waiting: stat the agent's transcript/output file — a small size or minutes-stale mtime with no notification means presume dead. Confirm by tailing the transcript's last entries (bounded `tail -c`, don't read the whole JSONL) for `[Request interrupted by user]` or an error.
- a dead agent may have made partial edits — `git status` its target files before deciding. Prefer resuming the SAME agent via SendMessage (general-purpose subagents resume with full context; Explore/Plan are one-shot and can't) over re-spawning from scratch; re-spawn only if resume fails or the agent had barely started.
- background Bash tasks piped through `| tail`/`| head` report the PIPE's exit code — the harness "completed (exit 0)" line can mask a failing command. Capture the real status explicitly (`; echo "EXIT:$?"` before any pipe, or write to a log file and tail that) and read the output before declaring success.

testing:
- don't add tests that just re-state the code (like testing what is our default shortcut binding is. this just duplicates the shortcut string for no benefit)
- fuzz suites (`*.fuzz.test.ts`, fast-check) run as a small fixed-seed smoke tier inside the normal gate and as random-seed deep runs via `pnpm fuzz` + the nightly `fuzz-nightly.yml` workflow. Reproduce failures with `FUZZ_SEED`/`FUZZ_PATH`; conventions + oracle discipline in `docs/fuzzing.md`. Never weaken a failing property to make it pass — diagnose (real bug vs wrong oracle) first.
- share one DB per test file: open with `createTestDb()` once in module scope / `beforeAll`, reset with `resetTestDb()` in `beforeEach`. Don't call `createTestDb()` per test.
- don't `await new Promise(r => setTimeout(r, N))` to wait on a DB/subscription/BroadcastChannel round-trip — it's slow and flaky. Poll the outcome with `vi.waitFor`.
- timeout budgets under load (this is the #1 source of "a disjoint set of files failed each run" flakes — measured across the full suite, a test's wall-clock stretches ~3x at p99 and ~6x at p99.9 versus running it alone, because the gate runs one worker per core):
  - budget for the 6x. A test measured over ~800ms has no real headroom under vitest's 5000ms default and WILL eventually time out in someone else's PR. Give it an explicit `it(…, 20_000)` or `describe(name, {timeout: 30_000}, …)` with a comment saying what the measured cost is; fuzz properties use `fuzzTestTimeout()` from `@/test/fuzz`. Don't raise the global `testTimeout` — the tail is a handful of files, and a global raise makes every genuine hang cost that much before it reports.
  - every INNER budget must be strictly below the enclosing test's timeout. A `vi.waitFor(…, {timeout: 5000})` inside a 5000ms test can never report its own failure — the test timeout always wins and you get "Test timed out in 5000ms" with no clue which assertion never settled. `vi.waitFor` defaults to 1000ms per call site; Testing Library's `findBy*`/`waitFor` are configured to 3000ms globally in `src/test/setup.ts`.
- setting up a row that a PROCESSOR would otherwise fix before your assertion runs: a raw `db.writeTransaction` still maintains the trigger-backed side indexes (`block_aliases`, `block_references`) but fires NO post-commit processor — which is also exactly the shape a sync-applied or pre-upgrade row has. Creating the row already in its final state instead usually means some processor normalized it on the way in, and the test then passes with the code under test deleted.
- when the test needs a row CROWDED OUT of a bounded window, order by rank, not recency: a fast test stamps every row in the same millisecond, so a `user_updated_at DESC` tiebreak floats whatever you created last to the top — including the row you meant to bury. Use the id, or a lower match bucket, whichever the query actually orders by.
- two race shapes that only bite under load, both of which look like a timeout:
  - a fixed sleep before a ONE-SHOT event (a keydown, a single dispatch) is a bet you lose. Dispatched early the event isn't late, it's *gone* — nothing re-delivers it, so no `waitFor` afterwards can recover the outcome. Fence on the observable precondition instead: a flag the handler sets, plus `await act(async () => {})` when what you need is a React commit + passive-effect flush.
  - a real timer left armed while the test awaits a `repo.tx` is a race: under contention the tx outlasts the timer, which then fires against pre-change state. If the test drives the callback itself, cancel the real timer at capture time, not after the awaits (see `captureDebounceTimer`'s `neutralize` in `src/extensions/PanelContentRecovery.test.tsx`).
- proving a write does NOT fire/invalidate: for loader-backed query handles assert the loader-invalidation COUNTER, never `fired.length` — subscriber dedup hides erroneous invalidations; for raw listeners a FIFO fence is sound. Recipe + the preconditions that make the counter complete: `bd recall testing_prove_write_does_not_fire`.

verifying a guard or fix (a green suite is weak evidence on its own):
- after adding or changing a guard, REVERT it and confirm a specific named test fails. If nothing fails, the guard is unpinned and will regress silently. Do this per-CLAUSE, not per-commit: a narrow clause hides behind a broader one in the same predicate (a content check masked an identity check that was the actual fix).
- DELETE the clause; do not SUBSTITUTE a value for it. A mutation that swaps a guard's return for a stand-in is STRONGER than removing the guard, and will report as pinned something that isn't. Measured: deleting `exact.kind === 'alias'` from the ref-value decode failed NOTHING for a required ref, because `codecs.ref().decode(undefined)` throws downstream anyway — a stand-in return had made it look load-bearing. Only `optionalRef` exposed it (`decode(undefined)` returns undefined, which `firstProjectedFieldValue` reads as "nothing parsed"). If deleting the clause fails nothing, it is defence in depth and must be LABELLED so at its declaration.
- and per-POSITION, when the guard is an early return added to an existing function. Where it sits relative to the checks already there is load-bearing and invisible to a green suite: an `isReadOnly` short-circuit placed one line too early skipped the caller-facing spec validation, and placed two lines too early skipped the cross-workspace occupant refusal — handing back another workspace's block. Both were correct code in the wrong slot, and each shipped a round before being caught. Mutate the POSITION (move it above each preceding check in turn) and confirm a different named test fails for each.
- four ways a test passes for the wrong reason, all hit in single sessions:
  - another layer independently catches the case, so the guard is unpinnable through the public path. Pin it with a direct unit test and say at the declaration that it is defence in depth rather than leaving a comment that implies it is load-bearing.
  - a repair path launders the damage before the assertion runs — a re-claim through `repo.tx` queues its own rename that reverts the bad rewrite; dropping a reference schedules a re-parse that rebuilds it. Write the setup so no repair is scheduled: a RAW `db.writeTransaction` write still maintains the trigger-backed side indexes (`block_aliases`, `block_references`) but fires no post-commit processor, which is also the shape a sync-applied row has.
  - the scenario never reached the code under test (un-flipped workspace, unstamped derived column, wrong branch of a disjunction) so an unrelated leg vetoed first. Assert the precondition explicitly in the test.
  - **an "it is absent" assertion ran before the thing that would make it PRESENT had resolved.** Any `expect(x).toBeNull()` on a surface fed by a query, an effect-driven fetch, or a subscription passes trivially on first render — so it stays green with the guard under test deleted. Hit three times in one session (a date gate, a read-only guard, a count stamp). Fixes, cheapest first: PRIME the async precondition and prove it (`vi.waitFor` the positive case, then `cleanup()`, then render the negative); or assert on the CAUSE instead of the absence (`expect(repo.tx).not.toHaveBeenCalled()`, an unchanged `queryBlocks` spy count). A negative test that has never once been seen to fail is not evidence — mutate the guard away and watch it stay green.
- when the claim is "X renders wrong", drive the REAL plugin and assert on node VALUES, not node counts. Counting nodes ("one blockref came out, so it's fine") hid a mangled label for two review rounds.

when review rounds stop converging (the fixes are generating the findings):
- COUNT THE ROUNDS. At about four, stop fixing and diagnose the SHAPE instead. The signal is not the number of findings, it's the ratio: findings naming new consumers mean a design still being mapped; findings naming the PREVIOUS round's own guards mean the work is now reviewing itself, and answering them adds surface at the rate it removes it. A green gate and a correct fix each round is exactly what a treadmill looks like from the inside.
- what to produce at that point, in place of round five: what is this actually trying to do, in one sentence; why each fix spawns more surface; and whether there is a shape where the whole class of finding stops existing (usually: move the check to where the data is produced or stored, not to each of N consumers). Bring that to Vlad as a decision — including "this isn't worth it, discard" as a real option.
- a corner case being REAL does not make handling it correct. A guard is permanent weight: new code can be wrong in its own right, and every site is one a future edit has to remember. Weigh reachability and blast radius against what the fix costs forever. ACCEPTING the case (with a line saying it's accepted) or SIMPLIFYING so it cannot arise are both legitimate answers, and past the first few special cases usually the better trade. This cuts both ways — being asked for a check does not settle it, and neither does the check being small.
- record the call either way, on the thread and to Vlad. A decline needs its reason on the record; repeating the same decline every round without saying so is how a settled question keeps costing review cycles.

cloud / remote sessions (Claude Code on the web) and git worktrees:
- when running in a cloud/remote execution environment, OR working in a non-main git worktree (a checkout that isn't the primary repo dir), open a ready-for-review pull request as soon as the branch has its first commit — don't wait to be asked — then subscribe to the PR's activity so review comments and CI failures come back into the session and can be addressed. - `refs/stash` is SHARED across all worktrees (git keeps only HEAD, `refs/bisect/*`, `refs/worktree/*`, `refs/rewritten/*` per-worktree), so every worktree pushes/pops one global stack: a bare `git stash` / `git stash pop` races every other session and can apply a diff from another branch cleanly. A PreToolUse hook (`scripts/check-stash-worktree.mjs`) blocks the ambiguous forms; a throwaway wip commit is per-worktree and has no such race.
- the index is per-worktree but shared by every agent in that directory, and `git commit --amend` commits whatever is staged, not what you changed — the same hook blocks an amend whose file set grows beyond the commit being amended (`AMEND_OK=1` overrides). The scope check that catches both this and stale-base history reverts is `git diff --name-status origin/master...HEAD` before any push, confirming it names only intended files — a green gate and a self-consistent tree do not (a revert takes the tests with it).
- in a CLOUD session, read `docs/cloud-sessions.md` before trusting git history, running any `bd` command, or probing pushes. The traps it holds, each learned the expensive way: shallow-clone graft boundaries make `git log` answers confidently wrong; the beads tracker LOOKS empty and is not (the first bd command would create an empty DB that then refuses to pull); `bd dolt push` is blocked and a self-supplied PAT is inert (route out via `bd backup` + plain `git push`); and a `--atomic` push probe can abort client-side, proving nothing. (Local worktrees are NOT cloud sessions — they share the main checkout's beads DB and git objects and need none of that.)

kernel/plugin boundary (the central architecture principle — enforced, not advisory):
- **core cannot depend on plugins; plugins may depend on core and on each other.** Core declares seams (facets, mutators, queries, actions, renderers) and plugins fill them. `src/plugins/<name>/**` is the plugin layer; everything else under `src/` is core/kernel.
- a core file reaching into `@/plugins/...` is a `boundary/no-core-to-plugin-imports` ESLint error. Covered: static import, `export … from`, dynamic `import()`, type-position `import('…')`, `import type` (a contract core NAMES belongs in core), `import X = require('…')`, `require()`, and `import.meta.glob` over the plugin layer. Relative (`../plugins/x`) and root-relative (`/src/plugins/x`) specifiers are resolved, not pattern-matched. When you hit it, do one of: move the shared contract DOWN into core (`@/facets`, `@/data/api`, `@/utils`); INVERT it — declare a facet in core the plugin contributes to; or move your module INTO the plugin layer. Do not reach for the disable first.
- exempt: the composition root (`src/extensions/staticAppExtensions.ts` / `staticDataExtensions.ts` — wiring every plugin in is their job, put new plugin registrations there), tests, and `scripts/`/`packages/` (top-level consumers above both layers). Genuine unavoidable edges opt in per-site with `// eslint-disable-next-line boundary/no-core-to-plugin-imports -- <why>`; there are currently ZERO such opt-outs in `src/`, so adding the first one should feel like a defeat, not a step. (The three that used to exist were retired by moving their modules into the plugin layer — issue #493.)

extension api surface (we are EARLY — do not over-protect it):
- `src/extensions/apiCatalog.ts` lists what extensions are encouraged to import. It is a DISCOVERY surface, not a frozen contract. Removing or reshaping a listed symbol is allowed, and "an installed extension might be reading it" is not on its own a reason to keep a shape that is wrong — extensions live in the DB where no sweep reaches them, but there are ~2 users and a handful of extensions, so a break is a fixable error while a bad shape is permanent. Prefer fixing the design.
- but SAY SO, every time. Name the break in the commit/PR and to Vlad directly: what was removed, and what an extension reading it would see (a `TypeError`, a silently wrong value, a blank subtree). That is a WARNING, not a migration plan — don't design a compat shim, a deprecation window or an upgrade path for it unless a real consumer is known to exist and Vlad asks. Deleting is the default. The call is his; surfacing it is yours. Never remove quietly, and never argue the break away because it seems unlikely to bite.
- this relaxes NOTHING about user DATA. Live data and history stay paramount — see the memory on alpha not meaning disposable. A schema/property/derived-column change that can lose or mangle stored blocks is a different question with a different answer.

ui event channels (audit B3 — do not reintroduce the untyped window.CustomEvent UI bus):
- dialogs / pickers / one-shot prompts: `openDialog(Component, props)` from `@/utils/dialogs` (returns a promise; the component takes `resolve`/`cancel` via `DialogContextProps`). The plugin must pull in `dialogAppMountExtension` so DialogHost is mounted.
- toggle/open surfaces (palette, sidebar, search overlays): a module store from `createToggleStore` (`@/utils/toggleStore`) read with `useSyncExternalStore`; the action/header flips it directly. - `window.dispatchEvent(new CustomEvent(...))` is reserved for GENUINE broadcast and is blocked in non-test `src/` by a `no-restricted-syntax` ESLint error — opt in per-site with `// eslint-disable-next-line no-restricted-syntax -- genuine broadcast: <why>`.

supabase / hosted database:
- never create a table in the `public` schema of the hosted Supabase project without RLS. Supabase grants `anon`/`authenticated` full CRUD on public tables by default, and `CREATE TABLE` / `CREATE TABLE AS` do NOT enable RLS — so the table is immediately world-readable/writable via the anon key until locked down. This includes ad-hoc backup/snapshot/staging tables created via `db query` or `psql`, not just app tables in migrations.
- create such tables with `enable row level security` (no policy = default-deny) + `revoke all ... from anon, authenticated` in the same transaction, or in a schema PostgREST doesn't expose. After any ad-hoc table creation, confirm `select relname from pg_class c join pg_namespace n on n.oid=c.relnamespace where n.nspname='public' and c.relkind='r' and not c.relrowsecurity` returns zero rows. beads (`bd`) — how the two generated blocks above apply HERE (installed 2026-08-14, prefix `km`):
- those blocks are written by `bd init` / `bd setup` and are REWRITTEN on upgrade. This section is repo-authored, survives, and wins wherever they conflict.
- **beads is the source of truth for issues; GitHub is a bidirectional mirror.** Each bead keeps an `External:` link to its GitHub issue; type/priority/labels carry over. Sync needs a token it does not store (`GITHUB_TOKEN=$(gh auth token)`). Judge sync state from a REAL run's output, never `--dry-run` — dry-run over-reports (it lists every timestamp-dirty pair; a real push then skips the content-identical ones), and even a converged full sync takes ~60s (a per-issue GET compare), which is why the pre-PR hook below doesn't run one.
- **sync is automated; prefer `pnpm bd:sync` over bare `bd github sync`.** The wrapper (`scripts/bd-github-sync.mjs`) guards four verified traps a bare sync has: (1) it adopts GitHub-side closes into beads BEFORE pushing — an open bead otherwise clobbers a GitHub-side close, including a merged "Fixes #N", and RE-OPENS the issue; (2) it re-derives priority from the `P0–P4`/`priority::*` labels for beads a pull left at the flattened default — pull assigns P2 to anything without a `priority::*` machine label, which silently rots `bd ready` ordering; (3) it pushes out the close of a bead that was closed before its first sync (the initial push mints the issue OPEN regardless of bead status); (4) it pushes local state out BEFORE the pull and restores + re-pushes any newer local row the pull still reverts — a bare sync's pull applies a strictly OLDER GitHub copy over newer local edits, claims and closes despite the documented prefer-newer default (#647, measured live: a close made locally and left unpushed reappears open after the next full sync). Deliberate asymmetry: GitHub-side CLOSES are adopted (they come from PR merges); GitHub-side REOPENS do not stick — reopen the bead instead. Triggers wired in `.claude/settings.json`: SessionEnd runs the full sync; a PreToolUse hook gates the publishing `gh` commands (`pr create/edit/comment/review/merge`, `issue create/edit/comment/close`, `release create/edit` — only with `gh` in command position, so text merely mentioning them passes), minting issues for referenced beads that lack one and BLOCKING bead ids in the command text with a km→#N substitution table; and a PostToolUse hook (`scripts/bd-publish-verify.mjs`, issue #672) verifies what a publish ACTUALLY shipped — it reads the created/edited object back from the GitHub API (including `gh api` mutations, the channel review replies use), rewrites published bead ids to their #N in place, and echoes every published #N with its real title into context. Codex runs no Claude hooks — run `pnpm bd:sync` at session close there.
- **public text references GitHub issue numbers, never bead ids — and never a #N you haven't READ this session.** PR bodies, PR/issue comments, commit messages. `Fixes km-xxxx` is auto-close syntax GitHub cannot act on, and a bead id is opaque to every GitHub reader; but a GUESSED `#N` is worse than either — it usually resolves to a real, unrelated issue and reads as correct to every reviewer (the top hallucination since this policy; a wrong "Fixes #N" closes a stranger's issue on merge). Get the number by reading it: the bead's `External:` line (`bd show <id>`), or `gh issue list --search`. **If you only know the bead id, write the bead id** — the pre-PR gate blocks once and hands you the real mapping (and for bead ids that reach a published body anyway, the post-publish verifier rewrites them to #N in place); that block is the cheap path, not a failure. The `#N` title-echo comes in two flavors: BEFORE publishing only where repair can't reach — `gh pr merge` text and `git commit` close keywords (both land in commits; read the table, check each title, re-run with `KM_ISSUE_REFS_OK=1` prefixed) — and AFTER publishing for everything else, where `bd-publish-verify` puts each published #N's real title into context; if a title is not the issue you meant, fix the published body immediately (`gh pr edit` / `gh api PATCH`). The pre-gate's parsing surface is FROZEN (#672): it scans raw command text only, and coverage findings about bodies it can't see (files, stdin, expansion) are declined — the verifier reads the published object instead. "Fixes #N" is the RIGHT pattern: when the merge closes #N, the next sync closes the bead to match — don't hand-close either side before the merge.
- **the READ rule covers ALL text, not just what the hooks gate.** Chat summaries and reports to Vlad, handoff notes, memories, and `gh api` calls (review replies go through `gh api`, which no hook sees) have each shipped a guessed number — five instances across two sessions, every one wrong, every one resolving to a real unrelated issue or PR. A hedged number ("#654-ish") is still a guess; the hedge doesn't stop it being copied forward (actual: #672, off by 18). If you haven't read the number this session, write the bead id or no number at all. A bead with no `External:` line has NO number yet — `pnpm bd:sync` mints it and prints the `minted: km-x → #N` mapping; read the number from that output, never anticipate it.
- **the label taxonomy is deliberately DUAL** (Vlad's call). A push mints `type::*` / `priority::*` labels in the public repo alongside the hand-maintained `bug`/`P2`/`ui` ones; there is no config to disable it. Don't "clean these up" — they are the machine half, and new work filed in beads will carry only them.
- **memory lives in beads ONLY** (migrated 2026-08-14; Vlad's call — no dual system, no sync step). This **overrides the harness default** of writing memory files: do NOT create or edit `.md` files under `~/.claude/projects/<project>/memory/` (that directory holds only a pointer `MEMORY.md` and a frozen recovery copy). Write with `bd remember --key <slug> -- <content>` (update-in-place on the same key), read with `bd memories <keyword>` / `bd recall <key>`. There is **no index to maintain**: session start lists every key automatically, so the memory's own first line IS its index entry. Convention: first line is a one-line description, blank line, then the body; cross-reference as `[[key]]`. Read these first, in this order, since the flat list can't express precedence: `feedback_fable_handoff_collaboration_texture` (how collaboration here actually works), then `feedback_no_backcompat_in_alpha` and `feedback_no_pii_in_commits` (the two hard constraints on live data and on what may be published). Why beads and not files: `~/.claude` is per-machine and unsynced, so a memory written on one machine was invisible everywhere else and to Codex. Four mechanics that are easy to get wrong:
  - content starting with `---` (frontmatter) is parsed as a flag — the payload MUST come after a `--` separator.
  - a memory is capped at **65,535 bytes** (Dolt TEXT); oversized ones are split into `<slug>` + `<slug>-part2`, each carrying a nav header naming its siblings.
  - **session start injects a clipped one-line preview of EVERY memory — the index is for discovery, `bd recall` is for content.** The SessionStart hook is `scripts/bd-prime-hook.mjs`, which wraps `bd prime --hook-json --mcp` and re-renders it to fit Claude Code's 10,000-char inline limit for hook context — raw bd prime output (~27KB, growing with every memory) NEVER arrived: the host persisted it to a file and sessions saw only a 2KB preview, ~10 of 135 keys (issue #643, fixed 2026-08-19). The wrapper keeps every key and clips previews just enough to fit (~25 chars at 135 memories, shrinking as the count grows), and drops bd's close-protocol boilerplate (this file already carries it). Consequence for how you WRITE a memory: the first ~25 characters of the first line are all an agent sees unprompted, so LEAD with the rule's subject — and never open with YAML frontmatter, which consumes the whole preview.
  - a memory that grows into an append-only project log should be REFACTORED, not left to accrete: keep state, deferred work and traps; drop what git and the PRs already record; lift reusable lessons into their own memories. Archive the pre-refactor text verbatim under `memory/archive/` first, and **re-verify every live-state claim while you are in there** — stale claims survive precisely by sitting buried in oversized memories (see `reference_coverage_claims_rot`).
- **memory vs issue — the split that matters.** A bead has STATE and a lifecycle (open/closed, history, close reason, dependencies); a memory has none. bd memories carry **no timestamps at all**, so an agent treats a two-year-old memory with the same authority as one written yesterday — upstream measured 40% of memories stale within a day and agents following stale memories over corrected instructions (gastownhall/beads#4605, #5153). Therefore: **anything that can become false — current status, what's deployed, what's merged, what's next — belongs in a bead, which can be closed.** Memories are for what stays true: preferences, conventions, invariants, traps ("do NOT rebuild X, here's why"), and hard-won lessons. A project memory should read as traps + decisions + a pointer to its tracking issue, never as a status report. Date every claim you do put in a memory; it is the only staleness signal available.
- **a bead becomes a PUBLIC GitHub issue.** Bidirectional sync pushes every bead to `Stvad/knowledge-medium`, which is public, and there is no per-issue exclusion mechanism. So the PII rule for commits applies verbatim to bead titles, descriptions and comments: no workspace or page names, no block ids/uuids, no local paths, device or browser-profile names, no personal context. If state can't be scrubbed enough to publish, it stays in a memory (which syncs only to the private Dolt remote) and you say so. Publication is AUTOMATIC now (the SessionEnd sync), so a bead must be publishable at CREATION — there is no later human checkpoint before it becomes a public issue.
- **model dependencies when you file or discover them** — `bd dep <blocker> --blocks <blocked>` (or `bd dep add <blocked> <blocker>`), one command at filing time. Deps are what make `bd ready` mean "actually unblocked" instead of just "open" — without them the queue view is noise, and ordering work means re-deriving the graph from prose every time. The moments to wire one: filing a follow-up that can't land until the parent PR merges; splitting work into slices; noticing mid-task that an open bead is waiting on another. `bd dep tree <id>` to read a chain; `relates_to` (`bd dep relate`) for association without blocking.
- **a "worth looking at separately" note in a PR body is not tracking — it is losing it.** If you notice something adjacent while working, there are exactly two acceptable endings: LOOK at it now, or FILE it (`bd create`, with the reproduction and the fix direction). A PR description is read once, during review of something else, by someone whose attention is on the diff; the note is then buried in a merged PR nobody reopens. The same goes for "flagging it" in a message to Vlad and moving on, and for a TODO comment in the diff. Cost of filing is one command; cost of the note is that the finding evaporates and is rediscovered months later by whoever it eventually bites.
- **task tracking split:** beads owns durable work — anything that must survive a thread reset, a handoff, or that another person or agent should be able to resume. The harness task list (TodoWrite/TaskCreate) is for the CURRENT turn's execution checklist only. The generated block above says never to use them at all; that is beads' house convention, and the beads skill itself draws the same line this bullet does.
- commit policy is this repo's, not beads': commit after each requested change, stay on the current branch. `agent.profile` is set to `team-maintainer` so `bd prime` stops telling agents to wait for commit approval. `pnpm run check` is the gate — `bd preflight` is not a substitute.
- **beads data syncs to a PRIVATE remote, and must keep doing so.** `Stvad/knowledge-medium` is public: a ref pushed there is fetchable by anyone via `git fetch origin 'refs/dolt/*'` — invisible in the web UI, but not private. Beads data therefore goes to `Stvad/knowledge-medium-beads` (private) via `bd dolt push` / `bd dolt pull`. A plain `git push` never carries beads data (verified: it moves `refs/heads/*` only).
- **worktrees SHARE the one database** (verified): `bd` resolves through the worktree's git common-dir, so a worktree anywhere — under `.claude/worktrees/`, a sibling directory, or `~/.codex/worktrees/` — sees the same issues, memories and remote registry as the main checkout, with no setup. Concurrent writes from two worktrees both land (tested). A separate CLONE (a cloud session, another machine) is the case that starts empty — the cloud specifics (bootstrap sequence, why `bd dolt push` 403s and a PAT is inert, the `bd backup` route out, the push-probe trap) live in `docs/cloud-sessions.md`.
- **the Dolt remote registry is NOT `sync.remote`, and it self-adopts.** `bd dolt push` reads `bd dolt remote list`; with the registry empty — every fresh clone, since it lives in gitignored `.beads/embeddeddolt/` — it silently ADOPTS git origin, which is how beads data briefly landed on the public repo during setup. In a new clone, BEFORE any `bd dolt push`:
  ```bash
  bd dolt remote add origin git+ssh://git@github.com/Stvad/knowledge-medium-beads.git
  ```
  and prefer `BD_NO_REMOTE_ADOPT=1 bd dolt push` so a missing registry fails loudly instead of adopting.
- **`bd config set` auto-commits to the current branch.** Changing config writes a `bd: …` commit without asking. Expect stray commits on your branch after config changes; that is bd, not you.
- `.beads/hooks/` is wired through `core.hooksPath`, so it OVERRIDES `.git/hooks` for this clone. Anything that installs git hooks later (husky et al.) must chain into it rather than replace it. Hook cost is ~130ms per commit.
- `bd init` stages whole tool directories (`.beads/`, `.claude/`, `.codex/`, `.agents/`) and commits them itself. That is why `.codex/worktrees/` is gitignored — without it, re-running init would commit three full worktree checkouts.
- never `bd edit` (opens `$EDITOR` and hangs an agent); use `bd update` flags.
